The Security Mental Model

A complete framework to understand, categorize, and secure ANY organization. This is your anchor for all security thinking.

The One-Line Model (Memorize Forever)

Business→ Assets→ Risks→ Controls→ Signals→ Detections→ Response→ Evidence

Everything else is just details. This is your anchor.

The Complete Security Flow

Business Capabilities→ Technology Streams→ Assets→ Risks→ Planes (Lens)→ Controls→ Signals→ Detections→ Response→ Evidence
StepQuestion It AnswersOutput
1. Business CapabilitiesWhat must this company do to operate and make money?List of core functions (authenticate users, deliver app, process data)
2. Technology StreamsWhat technology categories support those capabilities?7 streams: Identity, Application, Data, Cloud, CI/CD, Network, Security
3. AssetsWhat actually exists within each stream?Concrete inventory: users, apps, databases, repos, services
4. RisksIf each asset is misused/compromised — what goes wrong?Risk register derived from assets (NOT from MITRE)
5. Planes (Lens)At what LEVEL does this risk happen?Data / Control / Management plane — applied to EACH stream
6. ControlsWhat prevents or detects those risks at each plane?Preventive, detective, corrective controls placed where risks exist
7. SignalsWhat telemetry do controls produce?Logs, events, metrics — inputs to detection
8. DetectionsWhat logic identifies bad things in signals?XDR alerts (Bucket 1), SIEM correlations (Bucket 2/3)
9. ResponseWhat do we do when something is detected?Playbooks, automation, escalation, containment
10. EvidenceHow do we prove we did the right thing?Audit trails, incident reports, compliance artifacts

Critical Insight: Planes Are a LENS

Planes do NOT create risks. Assets create risks.

Planes tell you where those risks live within each technology stream. You apply the plane lens AFTER identifying assets and risks, not before.

❌ Wrong: "Let's organize everything by Data/Control/Management planes"
✅ Right: "Let's identify streams and assets, derive risks, then use planes to pinpoint where each risk lives"

Step 1: Start With Business Capabilities

Every security program exists to protect business operations. The first question is NOT about technology — it's about what the business must do to operate and make money.

The Only Question for Step 1

"What must this company do to operate and make money?"

This is business language, not security language. Don't mention controls, detections, or MITRE. Just list what the business does.

Example: B2B SaaS Health Platform

#Business CapabilityBusiness Outcome
1Authenticate usersCustomers can log in and access their accounts
2Deliver the applicationPlatform is available and functional for customers
3Store and process user health dataCustomer data is protected and processed correctly
4Manage infrastructureCloud resources are provisioned and maintained
5Deploy codeUpdates and fixes reach production safely
6Support customersIssues are resolved, customers stay happy
7Monitor and secure the environmentProblems are detected and addressed

Step 2: The Seven Technology Streams

Streams are the bridge between business language and technology. They're vendor-agnostic and stable across time.

StreamWhat It CoversExample Components
1. Identity & AccessWho can access what, authentication, authorizationIdP (Entra ID, Okta), MFA, SSO, service accounts
2. ApplicationThe software that delivers business valueWeb apps, mobile backends, APIs, admin dashboards
3. Data & StorageWhere business data livesDatabases, file storage, data lakes, backups, logs
4. Cloud InfrastructureThe platform everything runs onCloud projects, compute, storage, IAM roles, logging
5. CI/CD & DevOpsHow code gets to productionSource repos, pipelines, secrets management, artifacts
6. Network & ConnectivityHow things communicatePublic endpoints, API gateways, firewalls, service mesh
7. Security ToolingThe tools that protect everything elseSIEM, XDR/EDR, logging pipelines, alerting, CSPM

Step 3: Assets Within Each Stream

The Critical Principle

If an asset does not exist, the risk does not exist.
You can't have Kerberoasting risk without Active Directory. You can't have LSASS dumping risk without Windows endpoints.

Step 4: Derive Risks From Assets

Ask ONE question repeatedly for each asset:

"If this asset is misused, compromised, or misconfigured — what can go wrong?"

StreamAssetsDerived Risks
Identity & AccessUsers, admins, service accounts, tokensAccount takeover, admin abuse, token theft, MFA bypass
ApplicationWeb app, APIs, admin dashboardBusiness logic abuse, unauthorized admin actions, API abuse
Data & StorageDatabase, health data, backupsUnauthorized data access, data exfiltration, compliance violations
Cloud InfrastructureCloud projects, IAM, loggingProject takeover, logging disabled, IAM misconfiguration
CI/CD & DevOpsRepos, pipelines, secretsMalicious code deployment, secrets leakage, backdoor insertion
NetworkEndpoints, firewall rulesUnauthorized access paths, exposed services
Security ToolingSIEM, logging, alertsMonitoring disabled, alerts suppressed, evidence destroyed

Step 5: The Three Planes (Lens)

NOW apply planes. Planes answer: "At what LEVEL does this risk happen?"

Data Plane

What happens: Normal business activity — users accessing data, apps processing transactions, APIs exchanging information.

Examples: Login events, API calls, data reads/writes, user actions in apps

Risk level: High volume, individual events often benign

Control Plane

What happens: Access decisions — who can do what, under what conditions.

Examples: Role assignments, MFA enforcement, access policies, authorization checks

Risk level: Changes here affect many users/systems

Management Plane

What happens: System changes — configuration, creation, deletion, admin actions.

Examples: Creating/deleting users, granting admin privileges, disabling logging, changing security settings

⚠️ HIGHEST RISK: Can disable all other controls

Applying Planes to Identity Stream

PlaneWhat Happens HereExample Risks
Data PlaneLogin events, token usage, session activityCredential stuffing, session hijacking
Control PlaneRole assignments, MFA enforcement, access policiesPrivilege escalation, MFA bypass
Management PlaneCreating/deleting users, granting admin, disabling identity logsBackdoor account creation, audit log tampering

Control → Produces Signal → Signal enables Detection

Step 8: XDR-First Strategy

Modern detection strategy starts with XDR because it has the best visibility into endpoint activity. SIEM fills gaps.

What XDR Sees Well

DomainCoverageExamples
Endpoint Execution🟢 ExcellentMalware, ransomware, suspicious processes, LOLBins
Identity (Basic)🟡 GoodSign-in anomalies, impossible travel, MFA bypass
Email Threats🟢 ExcellentPhishing, malicious attachments, BEC
Cloud App Access🟡 GoodShadow IT, risky OAuth apps

What XDR Misses (SIEM Territory)

DomainCoverageWhy SIEM Needed
Management Plane🔴 WeakXDR doesn't see cloud console actions, IaC changes, CI/CD
Application Layer🔴 WeakXDR doesn't understand business app logic, API abuse
Cross-Domain Correlation🔴 WeakIdentity + endpoint + network + app requires SIEM
Network Infrastructure🔴 WeakFirewall, VPN, proxy logs need SIEM
OT/IoT🔴 WeakNo XDR agent on OT devices

Step 9: The Three Buckets

Bucket 1: RETIRE

XDR already detects this → Don't duplicate in SIEM

Malware execution, common endpoint behaviors, known attack tools (Mimikatz, Cobalt Strike), email phishing, basic identity anomalies, ransomware indicators

Action: Retire SIEM rule, ensure XDR alert flows to SIEM for correlation if needed.

Bucket 2: KEEP/REWRITE

SIEM adds value via correlation → Optimize for SIEM

Identity + endpoint correlation, VPN + sign-in + privilege changes, SaaS admin action + data spike, multi-stage attack sequences, business context enrichment

Action: Rewrite with optimal SIEM logic, incorporate XDR signals as inputs.

Bucket 3: BUILD IN SIEM

XDR doesn't cover this → SIEM is the only option

Cloud management plane misuse, application/API abuse, logging/audit tampering, CI/CD pipeline attacks, network infrastructure changes, OT/IoT threats

Action: Build new detection in SIEM, ensure signals are available.

Step 10: When to Write SIEM Correlations

Write SIEM correlation when:

  • Multiple asset classes are involved (identity + endpoint + network)
  • Sequence/time/context matters (A then B within X minutes)
  • Actions look legitimate individually but risky in combination
  • Blast radius is high (admin actions, sensitive data)
  • XDR sees only part of the story
  • Business context is required

The Golden Rule

If misuse can happen without malware, SIEM correlation is usually required.
XDR excels at detecting malicious binaries. It struggles with "living off the land" attacks using legitimate tools and credentials.

Step 11: Where MITRE ATT&CK Fits

MITRE is a labeling and communication tool, not a detection enumeration checklist.

The MITRE Mindset Shift

❌ Wrong approach: "Let's write detections for all 200+ techniques"

✅ Right approach: "Let's label our detections with MITRE and identify coverage gaps"

No Asset = No Risk = No Detection

MITRE TechniqueRequired AssetIf You Don't Have It...
T1558 - KerberoastingActive DirectorySkip — No AD means no Kerberos attacks
T1003.001 - LSASS DumpingWindows EndpointsSkip — Mac/Linux only? Not applicable
T1021.002 - SMB/Admin SharesWindows File ServersSkip — Cloud storage only? Not applicable
T1053.005 - Scheduled TasksWindows SystemsSkip — Linux? Use cron job detection instead
OT/ICS TechniquesIndustrial Control SystemsSkip — No OT? Entire category irrelevant

The 30-45 Second Interview Answer

"My approach to security analysis starts with business capabilities, not MITRE techniques. First, I ask: what must this company do to operate? Then I map those capabilities to technology streams — Identity, Application, Data, Cloud Infrastructure, CI/CD, Network, and Security Tooling.

Within each stream, I inventory the actual assets that exist. From those assets, I derive risks by asking: if this is misused or compromised, what goes wrong? Then I apply the plane lens — Data, Control, or Management — to localize where each risk lives.

Controls go where risks exist. Signals come from controls. Detections are built from signals — with XDR handling what it does well, and SIEM covering cross-stream correlation and management plane visibility.

MITRE comes at the end — to label and communicate coverage, not to drive what we build. If an asset doesn't exist, like Active Directory in a cloud-native company, the MITRE technique doesn't matter.

The flow is: Business → Streams → Assets → Risks → Planes → Controls → Signals → Detections → MITRE Label."
