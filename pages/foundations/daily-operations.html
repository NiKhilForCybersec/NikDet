SOC Daily Operations - Hour by Hour

Experience exactly what a SOC analyst does during a shift. This isn't theory - it's a detailed walkthrough of real operations with examples, thought processes, and pro tips.

07:00 - 08:00 Shift Start & Handoff

The first hour sets up your entire shift. Do it right and you'll be in control. Rush through it and you'll miss important context.

SHIFT HANDOFF PROCESS ═══════════════════════════════════════════════════════════════════════════════ STEP 1: VERBAL HANDOFF (5-10 minutes) ───────────────────────────────────────────────────────────────────────────── Night Shift (Sarah): "Hey, pretty eventful night. Three things:" 1. "We had a ransomware attempt on FINANCE-DC02. EDR contained it, but there's an open ticket #4521 - L2 is investigating scope." 2. "New phishing campaign targeting execs. I added IOCs to blocklist. Template: 'Your DocuSign document is ready' with malicious link." 3. "Ticket #4518 needs follow-up - user was traveling and got flagged for impossible travel, waiting for user to confirm." Day Shift (You): "Got it. Any aged alerts I should prioritize?" Sarah: "Yeah, there's one from 3 AM that I didn't get to - looks like possible data exfil, but could be backup software. Check queue, it's flagged high." STEP 2: SYSTEM CHECK (5 minutes) ───────────────────────────────────────────────────────────────────────────── Open your tools and verify: ┌─────────────────────────────────────────────────────────────────────────────┐ │ SIEM DASHBOARD │ │ │ │ Alert Queue: 47 pending (12 high, 20 medium, 15 low) │ │ Oldest Alert: 3 hours ago (⚠️ needs attention) │ │ Incidents Open: 3 (1 critical, 2 medium) │ │ │ │ System Health: All collectors online ✓ │ │ Last log received: 2 seconds ago ✓ │ └─────────────────────────────────────────────────────────────────────────────┘ STEP 3: THREAT INTEL CHECK (5 minutes) ───────────────────────────────────────────────────────────────────────────── Review overnight updates: • Check threat intel feed: Any new IOCs added? • Check security news: Any major attacks reported? • Check Slack/email: Any urgent notifications? Example finding: "New Emotet campaign detected - targeting invoices IOCs: [list of domains and IPs]" Action: Verify these IOCs are in our blocklist

💡 Pro Tip: The Handoff Ritual

Good SOCs have a structured handoff. Write notes DURING your shift, not at the end. Use a shared doc or wiki that both shifts can see. Include:

  • Open incidents and their status
  • Anything weird you noticed
  • Pending actions that need follow-up
  • Who you contacted and what they said

08:00 - 11:00 Alert Triage - The Core of SOC Work

This is what you'll spend 60-70% of your time doing. Let's walk through exactly how to triage an alert.

🔍 Complete Alert Triage Walkthrough

ALERT APPEARS IN YOUR QUEUE ═══════════════════════════════════════════════════════════════════════════════ ┌─────────────────────────────────────────────────────────────────────────────┐ │ 🔴 HIGH SEVERITY │ │ │ │ Title: Encoded PowerShell Execution │ │ Time: 2025-01-04 08:15:23 UTC │ │ Host: WORKSTATION-JD042 │ │ User: john.doe │ │ │ │ Details: │ │ PowerShell.exe executed with -EncodedCommand parameter │ │ Parent Process: OUTLOOK.EXE │ │ Command (decoded): IEX(New-Object Net.WebClient).DownloadString(...) │ │ │ └─────────────────────────────────────────────────────────────────────────────┘ STEP 1: UNDERSTAND THE ALERT (1-2 minutes) ───────────────────────────────────────────────────────────────────────────── Ask yourself: • What triggered this? → PowerShell with encoded command • Why is that bad? → Attackers encode to hide malicious commands • What's the context? → Parent is Outlook (email = possible phishing) Red flags I see: ✓ Encoded PowerShell (common attacker technique) ✓ Launched from Outlook (macro/link clicked?) ✓ DownloadString (downloading something from internet) STEP 2: GATHER CONTEXT (3-5 minutes) ───────────────────────────────────────────────────────────────────────────── Who is this user? ┌─────────────────────────────────────────────────────────────────────────────┐ │ USER LOOKUP: john.doe │ │ │ │ Department: Accounting │ │ Title: Senior Accountant │ │ Manager: jane.smith │ │ Risk Score: Low (no previous incidents) │ │ │ │ Does this user typically run PowerShell? NO ⚠️ │ │ Is this user on any watch list? NO │ └─────────────────────────────────────────────────────────────────────────────┘ What else happened on this host? ┌─────────────────────────────────────────────────────────────────────────────┐ │ TIMELINE: WORKSTATION-JD042 (last 1 hour) │ │ │ │ 08:10:15 Outlook opened email from: invoice-12345@company-billing.com │ │ 08:10:45 User clicked link in email │ │ 08:11:02 Word document downloaded: Invoice_Dec2024.docm │ │ 08:11:30 Word opened document │ │ 08:15:20 WINWORD.EXE spawned cmd.exe │ │ 08:15:23 cmd.exe spawned powershell.exe ← OUR ALERT │ │ 08:15:25 PowerShell attempted connection to 185.220.101.34 - BLOCKED │ │ │ │ THIS IS A PHISHING ATTACK CHAIN! │ └─────────────────────────────────────────────────────────────────────────────┘ STEP 3: INVESTIGATE DEEPER (5-10 minutes) ───────────────────────────────────────────────────────────────────────────── Check the IOCs: IP: 185.220.101.34 VirusTotal: 47/90 vendors flag as malicious Threat Intel: Known Emotet C2 server First seen: 2024-12-15 Domain: company-billing.com Registration: 3 days ago (⚠️ newly registered) Registrar: Suspicious registrar in Russia File: Invoice_Dec2024.docm Hash: a1b2c3d4e5f6... VirusTotal: 52/70 detect as Emotet loader STEP 4: MAKE A DECISION ───────────────────────────────────────────────────────────────────────────── Verdict: TRUE POSITIVE - Active phishing/malware attack Evidence: • Phishing email from newly registered domain • Macro-enabled document downloaded • Classic attack chain: Outlook → Word → PowerShell • C2 communication attempted (blocked by EDR) Severity: HIGH - Malware executed, though C2 was blocked STEP 5: RESPOND (varies by playbook) ───────────────────────────────────────────────────────────────────────────── Immediate actions: □ Isolate WORKSTATION-JD042 from network □ Reset john.doe's password □ Block sender domain company-billing.com □ Add C2 IP to firewall blocklist □ Search for other users who received same email □ Escalate to L2 for full scope analysis Create incident ticket: Title: "Emotet Phishing - WORKSTATION-JD042" Severity: High Status: Contained Assigned: L2 Team Timeline: [paste above] Actions taken: [list above] Pending: Scope analysis, user notification STEP 6: DOCUMENT (2-3 minutes) ───────────────────────────────────────────────────────────────────────────── Ticket notes: "08:45 - Confirmed malware infection via phishing. Attack chain: Phishing email → Word macro → PowerShell → C2 attempt (blocked). Host isolated, password reset, IOCs blocked. 5 other users received same email - all unopened. Escalated to L2 for forensic imaging."
💡 The Mental Model for Triage:
  1. What happened? (Understand the alert)
  2. Is it normal? (Context: user, host, behavior)
  3. Is it bad? (IOC checks, reputation)
  4. What do I do? (Playbook, escalation)
  5. What did I learn? (Documentation)

❌ Common Mistakes New Analysts Make

  • Rushing to close: Taking 30 seconds to dismiss as FP without context checking. You'll miss real attacks.
  • Over-escalating: Sending everything to L2 "just in case." Do your investigation first.
  • Not documenting: "I looked and it was fine" isn't documentation. Write what you checked and why you concluded it was fine.
  • Tunnel vision: Only looking at the alert, not the context around it.

11:00 - 12:00 Incident Follow-up & Coordination

INCIDENT FOLLOW-UP WORKFLOW ═══════════════════════════════════════════════════════════════════════════════ CHECK OPEN INCIDENTS: ───────────────────────────────────────────────────────────────────────────── ┌─────────────────────────────────────────────────────────────────────────────┐ │ INCIDENT DASHBOARD │ │ │ │ #4521 [CRITICAL] Ransomware Attempt - FINANCE-DC02 │ │ Status: Containment │ │ Owner: L2-Maria │ │ Last update: 2 hours ago │ │ → ACTION: Check if scope analysis is complete │ │ │ │ #4523 [HIGH] Emotet Phishing - WORKSTATION-JD042 │ │ Status: Escalated (your escalation from this morning) │ │ Owner: L2-John │ │ Last update: 30 minutes ago │ │ → ACTION: Check if other recipients were identified │ │ │ │ #4518 [MEDIUM] Impossible Travel - user.name │ │ Status: Pending user response │ │ Owner: You │ │ Last update: 8 hours ago │ │ → ACTION: Follow up with user │ │ │ └─────────────────────────────────────────────────────────────────────────────┘ SAMPLE FOLLOW-UP ACTIONS: ───────────────────────────────────────────────────────────────────────────── For #4518 (your ticket): 1. 12:00 - 13:00 Meetings & Collaboration

COMMON SOC MEETINGS ═══════════════════════════════════════════════════════════════════════════════ DAILY STAND-UP (15 min) ───────────────────────────────────────────────────────────────────────────── Purpose: Quick sync on incidents and priorities Format: Each analyst: "Yesterday I worked on X. Today I'm focusing on Y. Blockers: Z" Example: You: "Yesterday handled 45 alerts, escalated the Emotet case. Today I'm following up on three open tickets and working through the backlog. No blockers." WEEKLY CASE REVIEW (1 hour) ───────────────────────────────────────────────────────────────────────────── Purpose: Learn from interesting incidents Format: - Someone presents a recent incident - Walk through detection → investigation → response - Discuss what went well, what could improve - Action items for improvements Great for learning! Ask questions, take notes. THREAT INTEL BRIEFING (30 min, weekly) ───────────────────────────────────────────────────────────────────────────── Purpose: Stay aware of current threats Content: - New campaigns targeting our industry - New vulnerabilities announced - IOCs to watch for - Changes to detection rules

🏠 Analogy: Hospital Rounds

SOC meetings are like hospital rounds. Doctors discuss cases together to ensure nothing is missed and everyone learns from complex cases. Same idea - sharing knowledge makes the whole team better.

💡 Pro Tip: The Clean Handoff

Good analysts hand off clean - updated tickets, clear notes, no surprises.

Great analysts anticipate what the next shift needs to know, even if it's not their ticket.

"Hey, I noticed the network team is doing maintenance at 2 AM - you might see some connectivity alerts."

Queue Management - The Art of Prioritization

HOW TO PRIORITIZE YOUR ALERT QUEUE ═══════════════════════════════════════════════════════════════════════════════ You have 50 alerts. Where do you start? PRIORITY MATRIX: ───────────────────────────────────────────────────────────────────────────── HIGH IMPACT LOW IMPACT ┌─────────────────────────┬─────────────────────────┐ │ │ │ HIGH │ DO FIRST │ DO SECOND │ SEVERITY │ │ │ │ • Malware detected │ • Policy violation │ │ • C2 communication │ • Failed login (admin)│ │ • Data exfiltration │ • USB device │ │ │ │ ├─────────────────────────┼─────────────────────────┤ │ │ │ LOW │ DO THIRD │ DO LAST (or batch) │ SEVERITY │ │ │ │ • Suspicious login │ • Info-level alerts │ │ • Recon activity │ • Known FP patterns │ │ • Anomaly detection │ • Low-risk hosts │ │ │ │ └─────────────────────────┴─────────────────────────┘ ALSO CONSIDER: ───────────────────────────────────────────────────────────────────────────── AGE: Older alerts first (SLA compliance) Exception: New HIGH severity trumps old LOW severity VIP: Executives, IT admins, service accounts get priority (Higher risk if compromised) CAMPAIGNS: If you see 10 similar alerts, might be an attack Investigate as a group, not individually PRACTICAL APPROACH: ───────────────────────────────────────────────────────────────────────────── 1. Scan queue for anything CRITICAL → Handle immediately 2. Check for patterns → Same alert on many hosts = investigate together 3. Work HIGH severity by age (oldest first) 4. Work MEDIUM severity by age 5. Batch-close obvious FPs (same root cause) 6. LOW severity if time permits

Documentation - Your Future Self Will Thank You

WHAT GOOD DOCUMENTATION LOOKS LIKE ═══════════════════════════════════════════════════════════════════════════════ BAD DOCUMENTATION: ───────────────────────────────────────────────────────────────────────────── "Checked, looks fine. Closing as FP." Problems: • What did you check? • Why does it look fine? • If this happens again, we learn nothing GOOD DOCUMENTATION: ───────────────────────────────────────────────────────────────────────────── "Alert: PowerShell encoded command on WORKSTATION-042 Investigation: - Checked parent process: SCCM client (ccmexec.exe) - Checked command: Software deployment script for Adobe Reader - Verified with IT: Scheduled deployment for this workstation - Checked user: Standard user, no anomalous behavior - Checked host: No other suspicious activity in last 24 hours Conclusion: False Positive - legitimate SCCM software deployment Recommendation: Consider tuning rule to exclude SCCM parent process Tuning ticket: #REQ-1234" WHY THIS MATTERS: ───────────────────────────────────────────────────────────────────────────── 1. KNOWLEDGE SHARING Next analyst sees same alert → reads your notes → closes faster 2. PATTERN IDENTIFICATION "We've closed 50 of these as SCCM deployments" → time to tune! 3. AUDIT TRAIL If there's ever a breach investigation: "What did the SOC do?" Your notes are evidence of due diligence 4. YOUR OWN LEARNING "What did I miss in that incident last month?" Your notes help you improve

Key Takeaways

The SOC Analyst Mindset

  • Be methodical: Follow a consistent process for every alert
  • Be curious: "That's weird" is the start of every good investigation
  • Be thorough: Don't just close - document WHY
  • Be collaborative: Share what you learn, ask when stuck
  • Be proactive: See patterns? Suggest improvements
