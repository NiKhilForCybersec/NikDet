Detection Lifecycle

The complete journey of a detection rule: from identifying a threat to retiring an outdated rule.

What is the Detection Lifecycle?

The Detection Lifecycle is a structured process for creating, maintaining, and eventually retiring detection rules. Just like software has a development lifecycle, detections need proper management to stay effective.

Why it matters: Without a lifecycle process, you end up with:

  • Outdated rules that no longer catch attacks
  • Rules nobody understands or maintains
  • Alert fatigue from untested/untuned rules
  • Gaps in coverage you don't know about

1 Identify - "What should we detect?"

Before writing any code, you need to identify WHAT threat you're trying to detect and WHY it matters to your organization.

Where Detection Ideas Come From:

Real Example

Situation: Threat intel reports a new ransomware group using encoded PowerShell to download their payload.

Detection Need: We need to detect PowerShell with encoded commands making network connections.

MITRE Mapping: T1059.001 (PowerShell), T1105 (Ingress Tool Transfer)

2 Research - "Do we have the data?"

Before writing a rule, verify you have the telemetry (logs/data) needed to see the attack.

Key Questions to Answer:

  • ☐ What logs/events would show this attack? (Process creation? Network connection?)
  • ☐ Are those logs being collected in our SIEM?
  • ☐ What fields are available? (CommandLine? ParentProcess?)
  • ☐ Are there gaps in logging we need to fix first?
  • ☐ Has someone already written this detection? (Check SigmaHQ, vendor rules)
Continuing Our Example

Research Findings:

  • ✓ We have Sysmon Event ID 1 (Process Creation) with CommandLine
  • ✓ We have Sysmon Event ID 3 (Network Connection)
  • ✓ Data is in Sentinel, indexed properly
  • ✓ SigmaHQ has a basic encoded PowerShell rule we can build on

3 Develop - "Write the detection"

Now write the actual detection query. Start simple, then add complexity.

Development Process:

  1. Start broad: Find all instances of the behavior
  2. Analyze results: What's malicious vs legitimate?
  3. Add filters: Exclude known good patterns
  4. Test against historical data: How many alerts would this generate?
  5. Document: Write description, false positive notes, response steps
Our Detection (KQL)
// Encoded PowerShell with Network Connection
let EncodedPS = DeviceProcessEvents
| where FileName in~ ("powershell.exe", "pwsh.exe")
| where ProcessCommandLine has_any ("-enc", "-encodedcommand", "-e ")
| project DeviceId, EncodedTime = Timestamp, CommandLine = ProcessCommandLine;

DeviceNetworkEvents
| where InitiatingProcessFileName in~ ("powershell.exe", "pwsh.exe")
| where RemoteUrl !endswith ".microsoft.com"  // Exclude MS updates
| join kind=inner EncodedPS on DeviceId
| where Timestamp between (EncodedTime .. (EncodedTime + 5m))
| project Timestamp, DeviceName, CommandLine, RemoteUrl, RemoteIP

Logic: Find encoded PowerShell that makes network connections (excluding Microsoft) within 5 minutes.

4 Test - "Does it actually work?"

A detection that isn't tested is just a guess. You must verify it catches real attacks.

Testing Methods:

MethodHow It WorksWhen to Use
Atomic Red TeamRun pre-built attack simulationsQuick validation of common techniques
Manual TestingExecute the attack yourself in a labWhen no atomic test exists
Historical DataRun query against past incidentsVerify would have caught known attacks
Purple TeamRed team runs attack while blue watchesRealistic validation

Testing Checklist:

  • ☐ Does it catch the attack it's designed for? (True Positive)
  • ☐ Does it catch variations of the attack?
  • ☐ What's the false positive rate? (Run against 7-30 days of data)
  • ☐ Is the alert actionable? (Can analyst understand what happened?)
  • ☐ Are the right entities extracted? (User, device, IP, etc.)
Testing Our Detection

Atomic Test: Invoke-AtomicTest T1059.001 -TestNumbers 1

Result: ✓ Detection fired within 30 seconds

Historical Check: 3 alerts over 30 days - all were legitimate admin activity

Adjustment: Added exclusion for IT admin accounts doing approved maintenance

5 Deploy - "Put it into production"

Tested detection goes live. But don't just flip it on and walk away!

Deployment Steps:

  1. Start in monitoring mode: Alert fires but doesn't page anyone
  2. Watch for 1-2 weeks: Track true positive vs false positive rate
  3. Tune as needed: Add exclusions for legitimate activity
  4. Promote to production: Enable full alerting once confident
  5. Train analysts: Brief the team on what the detection catches and how to respond

6 Maintain - "Keep it working"

Detections degrade over time. Attackers evolve, environments change, false positives emerge.

Ongoing Maintenance Activities:

ActivityFrequencyPurpose
Review Alert VolumeWeeklyCatch sudden spikes in FPs
Check True Positive RateMonthlyEnsure detection is still effective
Re-test with AtomicsQuarterlyVerify still catches attacks
Review for EvasionsWhen threat intel arrivesUpdate for new attacker techniques
Retirement ReviewAnnuallyRetire obsolete detections

When to Retire a Detection:

  • The attack technique is no longer used
  • Better detection exists
  • The detection never fires (and testing shows it should)
  • Technology it monitors is decommissioned
