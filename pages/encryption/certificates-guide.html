Certificate Management Complete Guide

Everything you need to know about certificates: where to get them, how to create them, configure them, and deploy them for any application or security tool - both on-premises and in the cloud.

Why Do I Need Certificates?

Certificates are needed whenever you want:

  • Encrypted communication: HTTPS, TLS - data in transit
  • Identity verification: "This really is google.com, not a fake"
  • Code signing: "This software really came from Microsoft"
  • Email signing: "This email really came from the CEO"
  • VPN/Authentication: Client certificates for user/device auth

Almost every security tool needs certificates: SIEM (log ingestion), firewalls (SSL inspection), proxies, EDR, SOAR, and all web applications.

Certificate Formats Explained

Common Formats

FormatExtensionContainsUsed By
PEM .pem, .crt, .cer, .key Base64 encoded, text readable Linux, Apache, Nginx, most tools
DER .der, .cer Binary format Java, Windows
PFX/PKCS#12 .pfx, .p12 Cert + private key + chain (password protected) Windows, IIS, Azure
JKS .jks Java KeyStore Java applications, Tomcat

What's in a PEM File?

# Certificate (public)
-----BEGIN CERTIFICATE-----
MIIDXTCCAkWgAwIBAgIJAJC1HiIAZAiUMA0Gcz...
(Base64 encoded certificate data)
-----END CERTIFICATE-----

# Private Key (KEEP SECRET!)
-----BEGIN PRIVATE KEY-----
MIIEvgIBADANBgkqhkiG9w0BAQEFAASCB...
(Base64 encoded private key)
-----END PRIVATE KEY-----

# Or RSA Private Key format
-----BEGIN RSA PRIVATE KEY-----
MIIEowIBAAKCAQEA0Z3VS5JJcds3xfn...
-----END RSA PRIVATE KEY-----

Format Conversions (OpenSSL)

# ========== PEM CONVERSIONS ==========

# PEM to DER
openssl x509 -in cert.pem -outform DER -out cert.der

# DER to PEM
openssl x509 -in cert.der -inform DER -outform PEM -out cert.pem

# ========== PFX/PKCS12 CONVERSIONS ==========

# PEM (cert + key) to PFX (for Windows/IIS)
openssl pkcs12 -export -out cert.pfx -inkey private.key -in cert.pem -certfile chain.pem
# You'll be prompted to create a password

# PFX to PEM (extract certificate)
openssl pkcs12 -in cert.pfx -clcerts -nokeys -out cert.pem

# PFX to PEM (extract private key)
openssl pkcs12 -in cert.pfx -nocerts -nodes -out private.key

# PFX to PEM (extract everything)
openssl pkcs12 -in cert.pfx -out everything.pem -nodes

# ========== KEY CONVERSIONS ==========

# Convert encrypted key to unencrypted
openssl rsa -in encrypted.key -out decrypted.key

# Convert PKCS#8 to traditional RSA
openssl rsa -in pkcs8.key -out rsa.key

# ========== JAVA KEYSTORE (JKS) ==========

# PFX to JKS
keytool -importkeystore -srckeystore cert.pfx -srcstoretype PKCS12 \
  -destkeystore keystore.jks -deststoretype JKS

# PEM to JKS (need to convert to PFX first, then to JKS)
openssl pkcs12 -export -in cert.pem -inkey key.pem -out temp.pfx
keytool -importkeystore -srckeystore temp.pfx -srcstoretype PKCS12 \
  -destkeystore keystore.jks -deststoretype JKS

Creating Certificates

Option 1: Let's Encrypt (FREE, Public, Automated)

Best for: Public websites, auto-renewal

Let's Encrypt provides FREE SSL certificates that auto-renew every 90 days.

# Install Certbot
sudo apt install certbot python3-certbot-nginx  # For Nginx
sudo apt install certbot python3-certbot-apache # For Apache

# Get certificate (Nginx)
sudo certbot --nginx -d example.com -d www.example.com

# Get certificate (Apache)
sudo certbot --apache -d example.com -d www.example.com

# Get certificate (standalone - no web server)
sudo certbot certonly --standalone -d example.com

# Get certificate (DNS challenge - for wildcards)
sudo certbot certonly --manual --preferred-challenges dns -d "*.example.com"

# Certificate location after issuance:
# /etc/letsencrypt/live/example.com/fullchain.pem  (cert + chain)
# /etc/letsencrypt/live/example.com/privkey.pem    (private key)
# /etc/letsencrypt/live/example.com/cert.pem       (cert only)
# /etc/letsencrypt/live/example.com/chain.pem      (CA chain)

# Test auto-renewal
sudo certbot renew --dry-run

# Renewal is automatic via cron/systemd timer

Option 2: Self-Signed Certificate (Testing Only!)

WARNING: Never use in production!

Self-signed certificates cause browser warnings and aren't trusted. Use ONLY for testing.

# Generate self-signed certificate (valid 365 days)
openssl req -x509 -nodes -days 365 -newkey rsa:2048 \
  -keyout private.key \
  -out certificate.crt \
  -subj "/C=US/ST=State/L=City/O=Company/CN=server.local"

# Generate with Subject Alternative Names (SAN) - required for modern browsers
openssl req -x509 -nodes -days 365 -newkey rsa:2048 \
  -keyout private.key \
  -out certificate.crt \
  -subj "/C=US/ST=State/L=City/O=Company/CN=server.local" \
  -addext "subjectAltName=DNS:server.local,DNS:*.server.local,IP:192.168.1.100"

Option 3: Create Your Own CA (Internal PKI)

Best for: Internal services, SSL inspection, client certificates

Create a private CA to issue certificates for internal use. Clients must trust your CA.

# ========== STEP 1: CREATE ROOT CA ==========

# Create CA directory structure
mkdir -p ~/myCA/{certs,crl,newcerts,private}
chmod 700 ~/myCA/private
touch ~/myCA/index.txt
echo 1000 > ~/myCA/serial

# Generate CA private key (protect this!)
openssl genrsa -aes256 -out ~/myCA/private/ca.key 4096
chmod 400 ~/myCA/private/ca.key

# Generate CA certificate (valid 10 years)
openssl req -new -x509 -days 3650 -key ~/myCA/private/ca.key \
  -sha256 -out ~/myCA/certs/ca.crt \
  -subj "/C=US/ST=State/L=City/O=MyCompany/CN=MyCompany Root CA"

# ========== STEP 2: CREATE SERVER CERTIFICATE ==========

# Generate server private key
openssl genrsa -out server.key 2048

# Create Certificate Signing Request (CSR)
openssl req -new -key server.key -out server.csr \
  -subj "/C=US/ST=State/L=City/O=MyCompany/CN=server.internal.local"

# Create config file for SAN (Subject Alternative Names)
cat > server_ext.cnf << EOF
authorityKeyIdentifier=keyid,issuer
basicConstraints=CA:FALSE
keyUsage = digitalSignature, nonRepudiation, keyEncipherment, dataEncipherment
subjectAltName = @alt_names

[alt_names]
DNS.1 = server.internal.local
DNS.2 = server
DNS.3 = *.internal.local
IP.1 = 192.168.1.100
EOF

# Sign the CSR with your CA
openssl x509 -req -in server.csr -CA ~/myCA/certs/ca.crt -CAkey ~/myCA/private/ca.key \
  -CAcreateserial -out server.crt -days 365 -sha256 -extfile server_ext.cnf

# Verify the certificate
openssl x509 -in server.crt -text -noout

# ========== STEP 3: DISTRIBUTE CA CERTIFICATE ==========
# Clients must trust your CA certificate (ca.crt)
# See deployment section below

On-Premises: Windows AD Certificate Services

Why Use AD CS?

  • Integrates with Active Directory
  • Auto-enrollment via Group Policy
  • Templates for different certificate types
  • Trusted automatically by domain-joined machines

Step 1: Install AD CS Role

# PowerShell - Install AD CS
Install-WindowsFeature AD-Certificate -IncludeManagementTools

# Or via Server Manager:
# Add Roles → Active Directory Certificate Services
# Select: Certification Authority, CA Web Enrollment

# Configure as Enterprise CA (integrates with AD) or Standalone CA

Step 2: Request Certificate via Web Enrollment

# Access CA Web Enrollment
https://ca-server.domain.local/certsrv

# Steps:
# 1. Click "Request a certificate"
# 2. Click "Advanced certificate request"
# 3. Either:
#    - Submit a CSR (paste your CSR)
#    - Create and submit a request (fill out form)

Step 3: Request Certificate via certreq (Command Line)

# Create request file (request.inf)
[Version]
Signature="$Windows NT$"

[NewRequest]
Subject = "CN=webserver.domain.local,O=Company,L=City,S=State,C=US"
KeyLength = 2048
KeySpec = 1
KeyUsage = 0xA0
MachineKeySet = TRUE
ProviderName = "Microsoft RSA SChannel Cryptographic Provider"
RequestType = PKCS10

[EnhancedKeyUsageExtension]
OID=1.3.6.1.5.5.7.3.1  ; Server Authentication

[Extensions]
2.5.29.17 = "{text}"
_continue_ = "dns=webserver.domain.local&"
_continue_ = "dns=webserver&"
_continue_ = "ipaddress=192.168.1.50"

# Generate CSR
certreq -new request.inf request.csr

# Submit to CA
certreq -submit -config "CA-Server\CA-Name" request.csr certificate.cer

# Install certificate
certreq -accept certificate.cer

# Computer Configuration → Policies → Windows Settings → 
#   Security Settings → Public Key Policies → Certificate Services Client - Auto-Enrollment

# Settings:
# - Configuration Model: Enabled
# - Renew expired certificates: Checked
# - Update certificates that use certificate templates: Checked

# Also configure the certificate template in AD CS:
# 1. Open Certification Authority console
# 2. Right-click Certificate Templates → Manage
# 3. Duplicate a template (e.g., Web Server)
# 4. Configure Security tab: Allow "Enroll" for target computers/users
# 5. Right-click Certificate Templates → New → Certificate Template to Issue

Deploying CA Certificates to Clients

Why Deploy CA Certificates?

When you use an internal CA or SSL inspection, clients must trust your CA certificate. Otherwise, they'll get certificate warnings.

Windows: Deploy via GPO

# Group Policy path:
# Computer Configuration → Policies → Windows Settings → 
#   Security Settings → Public Key Policies → Trusted Root Certification Authorities

# Steps:
# 1. Right-click "Trusted Root Certification Authorities"
# 2. Import your CA certificate (ca.crt)
# 3. Link GPO to appropriate OUs
# 4. Run "gpupdate /force" on clients or wait for refresh

Windows: Manual Installation

# Command line (as Administrator)
certutil -addstore -f "Root" ca.crt

# Or double-click the .crt file:
# 1. Click "Install Certificate"
# 2. Select "Local Machine"
# 3. Select "Place all certificates in the following store"
# 4. Browse → "Trusted Root Certification Authorities"
# 5. Finish

# Verify installation
certutil -store Root | findstr "MyCompany"

Linux: Trust CA Certificate

# Ubuntu/Debian
sudo cp ca.crt /usr/local/share/ca-certificates/mycompany-ca.crt
sudo update-ca-certificates

# RHEL/CentOS/Fedora
sudo cp ca.crt /etc/pki/ca-trust/source/anchors/mycompany-ca.crt
sudo update-ca-trust

# Verify
openssl verify -CApath /etc/ssl/certs/ server.crt

macOS: Trust CA Certificate

# Command line
sudo security add-trusted-cert -d -r trustRoot -k /Library/Keychains/System.keychain ca.crt

# Or via GUI:
# 1. Double-click the .crt file (opens Keychain Access)
# 2. Add to System keychain
# 3. Double-click the certificate
# 4. Expand "Trust" section
# 5. Set "When using this certificate" to "Always Trust"

Cloud Certificate Management

AWS Certificate Manager (ACM)

FREE certificates for AWS services

ACM provides free public certificates that auto-renew. Works with CloudFront, ALB, API Gateway, etc.

# Request public certificate via CLI
aws acm request-certificate \
  --domain-name example.com \
  --subject-alternative-names "*.example.com" \
  --validation-method DNS \
  --region us-east-1

# Returns CertificateArn - use for validation

# Get DNS validation records
aws acm describe-certificate --certificate-arn arn:aws:acm:...

# Add the CNAME record to your DNS, then ACM validates automatically

# Import existing certificate (if you have one from another CA)
aws acm import-certificate \
  --certificate fileb://certificate.pem \
  --private-key fileb://private.key \
  --certificate-chain fileb://chain.pem

# Use certificate with ALB
aws elbv2 create-listener \
  --load-balancer-arn arn:aws:elasticloadbalancing:... \
  --protocol HTTPS \
  --port 443 \
  --certificates CertificateArn=arn:aws:acm:... \
  --default-actions Type=forward,TargetGroupArn=arn:aws:...

Azure Key Vault

# Create Key Vault
az keyvault create --name MyKeyVault --resource-group MyRG --location eastus

  --vault-name MyKeyVault \

Certificates for Security Tools

Firewall SSL Inspection (FortiGate)

How SSL Inspection Works

The firewall acts as a man-in-the-middle: it decrypts traffic with its CA cert, inspects it, then re-encrypts. Clients must trust the firewall's CA certificate.

# FortiGate: Import CA certificate for SSL inspection

# Via CLI
config vpn certificate ca
    edit "SSL-Inspection-CA"
        set ca "-----BEGIN CERTIFICATE-----
MIIDXTCCAkWgAwIBAgIJAJC1HiIAZAiU...
-----END CERTIFICATE-----"
    next
end

# Or import via GUI:
# System → Certificates → Import → CA Certificate

# Create SSL inspection profile using your CA
config firewall ssl-ssh-profile
    edit "deep-inspection"
        config ssl
            set inspect-all deep-inspection
        end
        set caname "SSL-Inspection-CA"
    next
end

Proxy Server (Squid)

# Squid SSL Bump (SSL inspection)

# 1. Generate CA certificate for Squid
openssl req -new -newkey rsa:2048 -days 3650 -nodes -x509 \
  -keyout squid-ca.key -out squid-ca.crt \
  -subj "/CN=Squid Proxy CA/O=Company"

# 2. Create DER format for Squid
openssl x509 -in squid-ca.crt -outform DER -out squid-ca.der

# 3. Initialize SSL database
/usr/lib/squid/security_file_certgen -c -s /var/spool/squid/ssl_db -M 4MB

# 4. Configure Squid (squid.conf)
http_port 3128 ssl-bump \
  cert=/etc/squid/ssl/squid-ca.crt \
  key=/etc/squid/ssl/squid-ca.key \
  generate-host-certificates=on dynamic_cert_mem_cache_size=4MB

sslcrtd_program /usr/lib/squid/security_file_certgen -s /var/spool/squid/ssl_db -M 4MB

acl step1 at_step SslBump1
ssl_bump peek step1
ssl_bump bump all

# 5. Deploy squid-ca.crt to all clients

VPN (OpenVPN)

# OpenVPN requires CA cert, server cert, and optionally client certs

# 1. Create PKI structure (using easy-rsa)
cd /usr/share/easy-rsa
./easyrsa init-pki
./easyrsa build-ca
./easyrsa gen-req server nopass

# 3. For client certificates

./easyrsa sign-req client client1

# 4. Client config includes
ca ca.crt
cert client1.crt
key client1.key
tls-auth ta.key 1

Web Server Configuration

Nginx

# /etc/nginx/sites-available/mysite
server {
    listen 443 ssl http2;
    server_name example.com www.example.com;

    # Certificate and key
    ssl_certificate /etc/nginx/ssl/fullchain.pem;      # Cert + intermediate chain
    ssl_certificate_key /etc/nginx/ssl/private.key;    # Private key

    # Modern SSL configuration
    ssl_protocols TLSv1.2 TLSv1.3;
    ssl_ciphers ECDHE-ECDSA-AES128-GCM-SHA256:ECDHE-RSA-AES128-GCM-SHA256:ECDHE-ECDSA-AES256-GCM-SHA384:ECDHE-RSA-AES256-GCM-SHA384;
    ssl_prefer_server_ciphers off;

    # HSTS (optional but recommended)
    add_header Strict-Transport-Security "max-age=31536000" always;

    # OCSP Stapling
    ssl_stapling on;
    ssl_stapling_verify on;
    ssl_trusted_certificate /etc/nginx/ssl/chain.pem;
    resolver 8.8.8.8 8.8.4.4 valid=300s;

    location / {
        root /var/www/html;
        index index.html;
    }
}

# HTTP to HTTPS redirect
server {
    listen 80;
    server_name example.com www.example.com;
    return 301 https://$server_name$request_uri;
}

# Test configuration
sudo nginx -t

# Reload
sudo systemctl reload nginx

Apache

# Enable SSL module
sudo a2enmod ssl

# /etc/apache2/sites-available/mysite-ssl.conf

    ServerName example.com
    ServerAlias www.example.com
    DocumentRoot /var/www/html

    SSLEngine on
    SSLCertificateFile /etc/apache2/ssl/certificate.crt
    SSLCertificateKeyFile /etc/apache2/ssl/private.key
    SSLCertificateChainFile /etc/apache2/ssl/chain.crt

    # Modern configuration
    SSLProtocol all -SSLv3 -TLSv1 -TLSv1.1
    SSLCipherSuite ECDHE-ECDSA-AES128-GCM-SHA256:ECDHE-RSA-AES128-GCM-SHA256
    SSLHonorCipherOrder off

    # HSTS
    Header always set Strict-Transport-Security "max-age=31536000"


# HTTP redirect

    ServerName example.com
    Redirect permanent / https://example.com/


# Enable site and restart
sudo a2ensite mysite-ssl
sudo systemctl restart apache2

Certificate Monitoring & Lifecycle

Check Certificate Expiration

# Check remote server certificate
echo | openssl s_client -servername example.com -connect example.com:443 2>/dev/null | \
  openssl x509 -noout -dates

# Check local certificate file
openssl x509 -in certificate.crt -noout -dates

# Check certificate details
openssl x509 -in certificate.crt -noout -text

# Check certificate chain
openssl s_client -showcerts -connect example.com:443 /dev/null

# Verify certificate matches private key
openssl x509 -noout -modulus -in certificate.crt | openssl md5
openssl rsa -noout -modulus -in private.key | openssl md5
# Both MD5 hashes should match!

PowerShell Certificate Check

# Check certificate expiration on remote server
$url = "https://example.com"
$request = [System.Net.WebRequest]::Create($url)
$request.GetResponse() | Out-Null
$cert = $request.ServicePoint.Certificate
$cert.GetExpirationDateString()

# Check all certificates in local store expiring within 30 days
Get-ChildItem -Path Cert:\LocalMachine\My | Where-Object {
    $_.NotAfter -lt (Get-Date).AddDays(30)
} | Select-Object Subject, NotAfter, Thumbprint

# Export certificate inventory
Get-ChildItem -Path Cert:\LocalMachine\My | 
  Select-Object Subject, Issuer, NotAfter, Thumbprint | 
  Export-Csv -Path "certificate-inventory.csv"

#!/bin/bash
# check-certs.sh - Monitor certificate expiration

DOMAINS="example.com internal.company.local api.company.com"

CRIT_DAYS=7

for domain in $DOMAINS; do
    expiry=$(echo | openssl s_client -servername $domain -connect $domain:443 2>/dev/null | \
             openssl x509 -noout -enddate 2>/dev/null | cut -d= -f2)
    
    if [ -z "$expiry" ]; then
        echo "CRITICAL: Cannot connect to $domain"
        continue
    fi
    
    expiry_epoch=$(date -d "$expiry" +%s)
    now_epoch=$(date +%s)
    days_left=$(( ($expiry_epoch - $now_epoch) / 86400 ))
    
    if [ $days_left -lt $CRIT_DAYS ]; then
        echo "CRITICAL: $domain expires in $days_left days ($expiry)"
    elif [ $days_left -lt $WARN_DAYS ]; then
        echo "WARNING: $domain expires in $days_left days ($expiry)"
    else
        echo "OK: $domain expires in $days_left days ($expiry)"
    fi
done

Certificate Checklist

Before Deploying a Certificate

  • ✅ Certificate matches hostname (check CN and SAN)
  • ✅ Certificate is not expired
  • ✅ Private key matches certificate (compare modulus)
  • ✅ Full chain included (cert + intermediate + root)
  • ✅ Private key is secure (chmod 600, restricted access)
  • ✅ CA is trusted by all clients that need to connect
  • ✅ Monitoring/alerting set up for expiration
  • ✅ Renewal process documented
  • ✅ Using TLS 1.2 or 1.3 (not older versions)
