Log Parsing - Complete Guide

Understand how raw logs become searchable data. Learn parsing in both Sentinel (KQL) and Splunk (SPL).

What is Log Parsing?

Parsing is extracting useful fields from raw log text so you can search and filter by specific values.

Without parsing: Logs are just long text strings - you can only search for keywords

With parsing: Logs have structured fields - you can filter by IP, user, action, etc.

Before vs After Parsing

❌ Raw Log (Unparsed)

Jan 15 10:23:45 webserver01 sshd[12345]: Failed password for invalid user admin from 192.168.1.100 port 52413 ssh2

Problem: To find all failed logins from 192.168.1.100, you'd have to search for "192.168.1.100" as text - but this might match other fields too!

✓ Parsed Log (Structured)

timestamp: 2025-01-15 10:23:45
host: webserver01
process: sshd
action: Failed password
user: admin
src_ip: 192.168.1.100
src_port: 52413

Benefit: Now you can query src_ip == "192.168.1.100" to get ONLY events from that source IP!

When Does Parsing Happen?

TimingDescriptionProsCons
Ingest-Time Parsing happens when log is received Faster searches, fields always available Can't change later, costs storage
Query-Time Parsing happens when you search Flexible, can change parsing anytime Slower searches, must parse each time
In Practice

Most parsing is done at ingest-time by data connectors, agents, and SIEM configurations. You typically only do query-time parsing for:

  • Ad-hoc analysis of unusual fields
  • Testing new parsing logic before deploying
  • Fields that weren't extracted at ingest

Parsing in Microsoft Sentinel (KQL)

In Sentinel, most common log sources come pre-parsed through data connectors. For custom logs or additional extraction, use KQL.

Pre-Parsed Tables (Already Done for You)

When you enable data connectors, logs arrive in tables with fields already extracted:

// SigninLogs - already parsed by Azure AD connector
SigninLogs
| where TimeGenerated > ago(1h)
| project TimeGenerated, UserPrincipalName, IPAddress, ResultType, Location
// These fields are automatically available - no parsing needed!

Query-Time Parsing with KQL

For logs that need additional parsing, use these KQL operators:

parse - Extract fields using pattern
// Parse a syslog message
Syslog
| where SyslogMessage contains "Failed password"
| parse SyslogMessage with * "Failed password for " user " from " src_ip " port " src_port:int " " *
| project TimeGenerated, user, src_ip, src_port

How it works: * matches any text, named fields (user, src_ip) capture the values between patterns.

extract - Regex extraction
// Extract IP address using regex
Syslog
| extend src_ip = extract(@"from (\d+\.\d+\.\d+\.\d+)", 1, SyslogMessage)
| where isnotempty(src_ip)

How it works: Uses regex pattern to extract matching text. The 1 means capture group 1.

parse_json - Parse JSON data
// Parse JSON in a field
AzureActivity
| extend Properties = parse_json(Properties)
| extend statusCode = Properties.statusCode
| extend requestUri = Properties.requestUri
split - Split by delimiter
// Split a comma-separated field
CommonSecurityLog
| extend IPList = split(DestinationIP, ",")
| mv-expand IPList  // Creates row for each IP

Parsing in Splunk (SPL)

In Splunk, parsing is configured through sourcetypes. Technology Add-ons (TAs) provide pre-built parsing for common sources.

Pre-Parsed Data (via Sourcetypes)

When you set up inputs with the right sourcetype, fields are automatically extracted:

// WinEventLog - parsed automatically
index=security sourcetype=WinEventLog:Security EventCode=4625
| table _time, Account_Name, Source_Network_Address, Logon_Type
// Fields already available because sourcetype handles parsing

Query-Time Parsing with SPL

rex - Regex field extraction
// Extract username and IP from syslog
index=linux sourcetype=linux_secure "Failed password"
| rex "Failed password for (?\S+) from (?\d+\.\d+\.\d+\.\d+)"
| stats count by user, src_ip

How it works: (?<fieldname>pattern) captures matching text into named field.

spath - Parse JSON/XML
// Parse JSON log
index=app sourcetype=json_logs
| spath input=_raw
| table user, action, status
rex mode=sed - Find and replace
// Clean up a field value
| rex mode=sed field=username "s/DOMAIN\\\\//g"  // Remove domain prefix

Ingest-Time Parsing (props.conf)

For permanent parsing, configure in props.conf:

# $SPLUNK_HOME/etc/apps/myapp/local/props.conf

[my_custom_log]
# Timestamp extraction
TIME_FORMAT = %Y-%m-%d %H:%M:%S
TIME_PREFIX = ^

# Line breaking
SHOULD_LINEMERGE = false
LINE_BREAKER = ([\r\n]+)

# Field extractions
EXTRACT-user = user=(?\w+)
EXTRACT-action = action=(?\w+)
EXTRACT-src_ip = src=(?\d+\.\d+\.\d+\.\d+)

Common Parsing Patterns

PatternKQL (Sentinel)SPL (Splunk)
Extract IP address extract(@"(\d+\.\d+\.\d+\.\d+)", 1, field) rex field=_raw "(?<ip>\d+\.\d+\.\d+\.\d+)"
Extract key=value parse field with * "user=" user " " * rex "user=(?<user>\S+)"
Parse JSON parse_json(field) spath
Split by comma split(field, ",") makemv delim="," field
Extract between quotes extract(@'"([^"]+)"', 1, field) rex "\"(?<value>[^\"]+)\""
Parsing Best Practices
  1. Check if fields already exist - Don't re-parse what's already parsed!
  2. Use existing TAs/Connectors - Don't write custom parsing if a solution exists
  3. Test with sample data first - Make sure your pattern works before deploying
  4. Handle missing data - Not every log will match; use isnotempty()
  5. Document your parsing - Future you will thank present you
