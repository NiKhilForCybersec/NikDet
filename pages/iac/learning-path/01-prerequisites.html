Lesson 1: Prerequisites & Core Concepts

Before we touch any tools, let's understand WHAT Infrastructure as Code is and WHY it exists. This foundation will make everything else click.

What You'll Learn
  • What "Infrastructure" means in cloud computing
  • The problems IaC solves (and why you should care)
  • Key terminology you'll see everywhere
  • The difference between imperative and declarative approaches

Time: ~20 minutes | Prerequisites: None

First: What is "Infrastructure"?

Infrastructure = The Stuff Your Applications Run On

When we say "infrastructure," we mean:

  • Compute: Virtual machines (VMs), containers, serverless functions - where code runs
  • Network: Virtual networks, subnets, firewalls, load balancers - how things connect
  • Storage: Disks, blob storage, databases - where data lives
  • Identity: Users, service accounts, permissions - who can do what

In the old days, this was physical hardware. Now it's virtual resources in the cloud (AWS, Azure, GCP).

Think of it like building a house

Infrastructure = The house itself (foundation, walls, plumbing, electrical)

Application = The furniture and people living in the house

You need the infrastructure (house) before you can run your application (live in it).

The Problem IaC Solves

Let's see what life was like BEFORE Infrastructure as Code:

❌ The Old Way (Manual)

  1. Log into cloud console (Azure Portal, AWS Console)
  2. Click through menus to create a VM
  3. Remember (or forget) to configure security settings
  4. Do it again for each environment (dev, staging, prod)
  5. 3 months later: "Wait, what settings did I use?"
  6. Someone else joins team: "How do I recreate this?"

Problems:

  • No record of what was done
  • Environments drift apart
  • Easy to make mistakes
  • Can't review changes before they happen
  • Disaster recovery = rebuild from memory

✓ The IaC Way (Code)

  1. Write a text file describing what you want
  2. Store it in Git (version control)
  3. Run a command to create the infrastructure
  4. Same code = same infrastructure everywhere
  5. 3 months later: "Let me check the code"
  6. New team member: "I'll read the code"

Benefits:

  • Complete history of all changes
  • Environments are identical
  • Automated, repeatable
  • Changes reviewed before deployment
  • Disaster recovery = run the code again

What IaC Actually Looks Like

Here's a simple example. Don't worry about understanding every detail - just see the concept:

Creating a VM: Manual vs Code

Manual Way (Azure Portal):

  1. Go to portal.azure.com
  2. Click "Create a resource"
  3. Search for "Virtual Machine"
  4. Fill in 15+ fields across 7 tabs
  5. Click "Create"
  6. Wait and hope you didn't miss anything

IaC Way (Terraform code):

# This file describes a VM - that's it!
resource "azurerm_virtual_machine" "web_server" {
  name                = "web-server-01"
  location            = "East US"
  resource_group_name = "my-project"
  vm_size             = "Standard_B2s"
  
  # Security: encrypted disk
  storage_os_disk {
    name              = "web-server-disk"
    caching           = "ReadWrite"
    managed_disk_type = "Premium_LRS"
  }
}

Then run: terraform apply

That's it. The VM is created with the exact settings specified.

Key Terminology

You'll see these terms constantly. Let's define them clearly:

Infrastructure as Code (IaC)

Managing and provisioning infrastructure through machine-readable definition files, rather than physical hardware configuration or interactive configuration tools.

In plain English: Writing text files that describe what infrastructure you want, then using tools to create it automatically.

Declarative

You describe WHAT you want (the end state), not HOW to get there.

Example: "I want a VM with 4GB RAM" - the tool figures out the steps.

Tools: Terraform, CloudFormation, ARM templates

Imperative

You describe the exact STEPS to take.

Example: "First create a network, then create a disk, then attach the disk to a VM..."

Tools: Bash scripts, PowerShell scripts, Ansible (can be both)

State

A record of what infrastructure currently exists. IaC tools compare desired state (your code) to current state to determine what changes to make.

Think of it like: A checklist that tracks "VM exists: yes, Firewall configured: yes"

Idempotent

Running the same operation multiple times produces the same result.

Why it matters: You can run terraform apply 10 times - it only makes changes if needed.

Drift

When actual infrastructure differs from what's defined in code (someone made manual changes).

Why it's bad: Your code no longer represents reality. Security settings might be wrong.

Declarative vs Imperative: A Deeper Look

Restaurant Analogy

Declarative (Terraform): "I'd like a medium-rare steak with mashed potatoes."
The kitchen figures out how to make it. You get what you asked for.

Imperative (Scripts): "First, take a ribeye from the fridge. Season with salt. Heat pan to 450°F. Sear for 3 minutes per side..."
You're telling them exactly what to do, step by step.

Why Declarative is Usually Better for IaC

AspectDeclarativeImperative
Handling existing resources Automatically detects what exists, only changes what's needed You must write logic to check if things exist
Running multiple times Safe - only makes needed changes Might fail or create duplicates
Understanding what will happen Shows a plan before executing You have to trace through the script
Destroying resources Knows what it created, can cleanly destroy You must write separate cleanup scripts

Why Security Teams Should Care

IaC is a Security Enabler

As a security professional, IaC gives you superpowers:

Security BenefitHow IaC Helps
Review before deployment See infrastructure changes in pull requests BEFORE they go live
Automated scanning Tools can check code for misconfigurations before deployment
Audit trail Git history shows who changed what and when
Consistent security baseline All environments built from same secure templates
Rapid incident response Check code to see what firewall rules SHOULD be vs what they ARE
Compliance Prove infrastructure meets requirements - it's all documented in code
