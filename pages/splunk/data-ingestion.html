Splunk Data Ingestion & Parsing

Complete guide to getting data into Splunk: inputs, sourcetypes, props.conf, transforms.conf, CIM normalization, and index tiers.

How Data Gets Into Splunk

Data flows through Splunk's pipeline:

📊 Log Source → 📤 Forwarder → ⚙️ Parsing (props/transforms) → 💾 Indexer → 🔍 Search Head

Key concepts:

  • Input = How data enters Splunk (file monitor, syslog, API)
  • Sourcetype = Tells Splunk how to parse the data
  • Index = Where data is stored (like a database)
  • props.conf = Parsing rules for each sourcetype
  • transforms.conf = Advanced transformations and field extractions

Section 1: Data Inputs

The first step is getting data INTO Splunk. There are several input methods:

Input TypeUse CaseConfiguration
monitor:// Watch files/directories [monitor:///var/log/messages]
WinEventLog:// Windows Event Logs [WinEventLog://Security]
tcp:// / udp:// Syslog, network inputs [tcp://514]
HTTP Event Collector API-based ingestion POST to :8088/services/collector
scripted:// Custom scripts [script://./bin/myscript.sh]

Scenario: Configure Windows Event Log Collection

Step 1: Create inputs.conf on Universal Forwarder
$SPLUNK_HOME/etc/apps/myapp/local/inputs.conf
# Collect Windows Security Events
[WinEventLog://Security]
disabled = 0
index = wineventlog
sourcetype = WinEventLog:Security
# Only collect specific Event IDs (reduces volume)
whitelist = 4624,4625,4648,4672,4688,4720,4726,4728,4732,4756

# Collect Windows System Events
[WinEventLog://System]
disabled = 0
index = wineventlog
sourcetype = WinEventLog:System

# Collect Sysmon Events
[WinEventLog://Microsoft-Windows-Sysmon/Operational]
disabled = 0
index = sysmon
sourcetype = XmlWinEventLog:Microsoft-Windows-Sysmon/Operational
renderXml = true
Step 2: Configure outputs.conf (Where to send)
$SPLUNK_HOME/etc/apps/myapp/local/outputs.conf
[tcpout]
defaultGroup = indexer_cluster

[tcpout:indexer_cluster]
server = indexer1.company.com:9997, indexer2.company.com:9997
compressed = true
useACK = true
Step 3: Restart and Verify
# Restart forwarder
$SPLUNK_HOME/bin/splunk restart

# On search head, verify data
index=wineventlog sourcetype=WinEventLog:Security | head 10

Section 2: Sourcetypes (Pre-Built Parsing)

What is a Sourcetype?

A sourcetype tells Splunk:

  • How to break data into events (line breaking)
  • How to extract the timestamp
  • What fields to extract

For common log formats, Technology Add-ons (TAs) provide pre-built sourcetypes with all parsing configured.

Common Security Sourcetypes

SourcetypeSourceTA RequiredKey Fields
WinEventLog:Security Windows Security Log Splunk Add-on for Windows EventCode, Account_Name, Logon_Type, Source_Network_Address
XmlWinEventLog:Microsoft-Windows-Sysmon/Operational Sysmon Splunk Add-on for Sysmon EventID, Image, CommandLine, ParentImage, Hashes
pan:traffic Palo Alto Firewall Palo Alto Networks Add-on src_ip, dest_ip, dest_port, action, app, rule
cisco:asa Cisco ASA Firewall Cisco ASA Add-on src_ip, dest_ip, action, protocol
linux_secure Linux /var/log/secure Splunk Add-on for Unix user, src_ip, process, action
aws:cloudtrail AWS CloudTrail Splunk Add-on for AWS eventName, userIdentity, sourceIPAddress
ms:o365:management Microsoft 365 Audit Splunk Add-on for O365 Operation, UserId, ClientIP, Workload
Best Practice

Always check Splunkbase for a Technology Add-on (TA) before writing custom parsing. TAs are tested, maintained, and include CIM compliance.

Section 3: props.conf (Parsing Configuration)

What is props.conf?

props.conf defines how Splunk parses a specific sourcetype:

  • Time extraction - Where is the timestamp? What format?
  • Line breaking - Where does one event end and another begin?
  • Field extraction - What fields to extract (at search-time or index-time)
  • Field aliases - Map custom names to CIM names

Key props.conf Settings

SettingPurposeExample
TIME_FORMAT Timestamp format TIME_FORMAT = %Y-%m-%d %H:%M:%S
TIME_PREFIX Text before timestamp TIME_PREFIX = ^ (start of line)
MAX_TIMESTAMP_LOOKAHEAD How far to look for timestamp MAX_TIMESTAMP_LOOKAHEAD = 25
SHOULD_LINEMERGE Merge multiple lines into one event? SHOULD_LINEMERGE = false
LINE_BREAKER Regex for event boundaries LINE_BREAKER = ([\r\n]+)
EXTRACT-<name> Regex field extraction EXTRACT-user = user=(?<user>\w+)
FIELDALIAS-<name> Create field alias FIELDALIAS-src = source_ip AS src_ip
REPORT-<name> Use transform from transforms.conf REPORT-fields = my_extraction

Scenario: Create Custom Sourcetype for Application Logs

Your application produces logs like:

2025-01-04 10:23:45.123 [INFO] [user=john.doe] [action=login] [status=success] [ip=192.168.1.100] Login completed
2025-01-04 10:24:12.456 [WARN] [user=jane.smith] [action=file_download] [status=blocked] [ip=10.0.0.50] Download blocked by policy
Step 1: Create props.conf
$SPLUNK_HOME/etc/apps/myapp/local/props.conf
[custom_app_log]
# Timestamp extraction
TIME_FORMAT = %Y-%m-%d %H:%M:%S.%3N
TIME_PREFIX = ^
MAX_TIMESTAMP_LOOKAHEAD = 24

# Line breaking - each line is one event
SHOULD_LINEMERGE = false
LINE_BREAKER = ([\r\n]+)

# Field extractions (search-time)
EXTRACT-level = \[(?<log_level>INFO|WARN|ERROR|DEBUG)\]
EXTRACT-user = \[user=(?<user>[^\]]+)\]
EXTRACT-action = \[action=(?<action>[^\]]+)\]
EXTRACT-status = \[status=(?<status>[^\]]+)\]
EXTRACT-src_ip = \[ip=(?<src_ip>\d+\.\d+\.\d+\.\d+)\]

# CIM field aliases
FIELDALIAS-src = src_ip AS src
FIELDALIAS-user_name = user AS user_name

# Add vendor/product for CIM
EVAL-vendor_product = "MyApp"
Step 2: Create inputs.conf
$SPLUNK_HOME/etc/apps/myapp/local/inputs.conf
[monitor:///var/log/myapp/app.log]
disabled = 0
index = application
sourcetype = custom_app_log
Step 3: Verify Parsing
index=application sourcetype=custom_app_log
| table _time, log_level, user, action, status, src_ip
| head 20

Section 4: transforms.conf (Advanced Transformations)

What is transforms.conf?

transforms.conf handles complex transformations that can't be done in props.conf alone:

  • Complex regex extractions with multiple capture groups
  • Lookups - enrich events with external data
  • Routing - send events to different indexes based on content
  • Masking - hide sensitive data (credit cards, SSNs)

Scenario: Route Logs to Different Indexes by Severity

Goal: Send ERROR logs to a high-priority index, INFO logs to standard index.

transforms.conf
# Route ERROR events to priority index
[route_errors]
REGEX = \[(ERROR)\]
DEST_KEY = _MetaData:Index
FORMAT = priority_logs

# Route INFO events to standard index
[route_info]
REGEX = \[(INFO)\]
DEST_KEY = _MetaData:Index
FORMAT = application_logs
props.conf
[custom_app_log]
# Apply the routing transforms
TRANSFORMS-routing = route_errors, route_info

Scenario: Mask Credit Card Numbers

transforms.conf
[mask_credit_cards]
REGEX = (\d{4})[- ]?(\d{4})[- ]?(\d{4})[- ]?(\d{4})
FORMAT = XXXX-XXXX-XXXX-$4
DEST_KEY = _raw
props.conf
[payment_logs]
TRANSFORMS-mask = mask_credit_cards

Result: 4111-1111-1111-1234 becomes XXXX-XXXX-XXXX-1234

Section 5: CIM Normalization

What is CIM?

The Common Information Model (CIM) is Splunk's normalization standard. It maps different log formats to common field names.

Why CIM matters:

  • Splunk Enterprise Security (ES) requires CIM-compliant data
  • One search works across all sources
  • Pre-built dashboards and content work automatically

CIM Data Models

Data ModelUse ForKey CIM Fields
AuthenticationLogins, auth eventsuser, src, dest, action, app
Network TrafficFirewall, netflowsrc_ip, dest_ip, dest_port, bytes, action
EndpointProcess, file, registryprocess, file_name, user, action
WebProxy, web serverurl, http_method, status, src, dest
MalwareAV, EDR alertssignature, file_name, action, dest

Scenario: Make Custom Logs CIM-Compliant

props.conf - Add CIM field aliases and tags
[custom_firewall_log]
# Your custom parsing
EXTRACT-src = src=(?<source_ip>\d+\.\d+\.\d+\.\d+)
EXTRACT-dst = dst=(?<destination_ip>\d+\.\d+\.\d+\.\d+)
EXTRACT-port = dport=(?<destination_port>\d+)
EXTRACT-act = action=(?<firewall_action>\w+)

# Map to CIM field names
FIELDALIAS-src_ip = source_ip AS src_ip
FIELDALIAS-dest_ip = destination_ip AS dest_ip
FIELDALIAS-dest_port = destination_port AS dest_port
FIELDALIAS-action = firewall_action AS action

# Add CIM-required fields
EVAL-vendor_product = "Custom Firewall"
EVAL-dvc = host
tags.conf - Tag for data model
# Tag this sourcetype for Network Traffic data model
[sourcetype=custom_firewall_log]
network = enabled
communicate = enabled
Verify CIM Compliance
# Check if data appears in data model
| datamodel Network_Traffic All_Traffic search
| table src_ip, dest_ip, dest_port, action
| head 20

# Or use tstats (faster)
| tstats count from datamodel=Network_Traffic by All_Traffic.src_ip, All_Traffic.dest_ip

Section 6: Index Tiers (SmartStore)

Splunk indexes have storage tiers that data moves through over time:

Hot Bucket

What: Actively receiving new data

Storage: Fast local SSD

Searchable: Yes, fastest

Typical age: Current data being indexed

Warm Bucket

What: No longer receiving data, but recent

Storage: Local disk (SSD or HDD)

Searchable: Yes, fast

Typical age: Hours to days old

Cold Bucket

What: Older data, accessed less frequently

Storage: Slower/cheaper storage (HDD, NAS)

Searchable: Yes, slower

Typical age: Days to months old

Frozen Bucket

What: Archived data

Storage: Archive storage, SmartStore (S3)

Searchable: Must thaw first (restore)

Typical age: Months to years old

Configuring Index Retention

indexes.conf
# Security index - keep longer
[security]
homePath = $SPLUNK_DB/security/db
coldPath = $SPLUNK_DB/security/colddb
thawedPath = $SPLUNK_DB/security/thaweddb

# Retention settings
frozenTimePeriodInSecs = 31536000  # 365 days before freezing
maxTotalDataSizeMB = 500000        # 500 GB max

# Data moves to cold after 7 days
maxWarmDBCount = 300

# SmartStore for frozen (S3)
remotePath = volume:s3_archive/security

# Firewall index - shorter retention, high volume
[firewall]
homePath = $SPLUNK_DB/firewall/db
coldPath = $SPLUNK_DB/firewall/colddb
thawedPath = $SPLUNK_DB/firewall/thaweddb

frozenTimePeriodInSecs = 7776000   # 90 days
maxTotalDataSizeMB = 1000000       # 1 TB max

Section 7: Complete Parsing Pipeline

End-to-End Example: Ingest Palo Alto Firewall Logs

1. Install Technology Add-on

Download "Palo Alto Networks Add-on for Splunk" from Splunkbase. Install on:

  • Search Heads (for field extractions at search time)
  • Indexers (for index-time parsing)
  • Heavy Forwarder (if doing syslog collection there)
2. Configure Syslog Input
inputs.conf (on Heavy Forwarder or Indexer)
[tcp://514]
connection_host = dns
sourcetype = pan:traffic
index = firewall
3. Configure Firewall to Send Logs

On Palo Alto: Device → Server Profiles → Syslog

  • Server: Your Splunk Heavy Forwarder IP
  • Port: 514
  • Format: BSD
4. Verify Data
index=firewall sourcetype=pan:traffic
| stats count by action, app
| sort -count
5. Verify CIM Compliance
| tstats count from datamodel=Network_Traffic where nodename=All_Traffic.Traffic_By_Action by All_Traffic.action

Summary: When to Use What

ScenarioApproach
Common log source (Windows, Palo Alto, AWS) Install TA from Splunkbase → Configure input with correct sourcetype
Custom application logs Create custom sourcetype in props.conf with extractions
Complex parsing with multiple patterns Use transforms.conf with REPORT in props.conf
Route logs to different indexes transforms.conf with DEST_KEY routing
Enterprise Security compatibility Add CIM field aliases and tags for data models
Cost optimization Configure shorter retention for high-volume, low-value indexes
