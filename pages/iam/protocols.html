Authentication Protocols Deep Dive

Comprehensive guide to SAML, OAuth 2.0, OpenID Connect, Kerberos, LDAP, and RADIUS. How they work, when to use them, and how they compare.

Protocol Quick Reference

ProtocolWhat It DoesUse When
SAML 2.0 Web SSO, exchanges XML assertions Enterprise apps, legacy SSO
OAuth 2.0 Authorization (API access) APIs, "Login with X" buttons
OpenID Connect Authentication + OAuth Modern apps, mobile, SPAs
Kerberos Network authentication Windows domain, on-prem
LDAP Directory access/auth Directory queries, legacy apps
RADIUS Network access auth VPN, WiFi, network devices

SAML 2.0

SAML Analogy

SAML is like a notarized letter of introduction:

  1. You go to a government office (IdP) and prove who you are
  2. They give you a signed, sealed letter saying "This is John Doe, he's authorized for X"
  3. You take this letter to a business (SP)
  4. The business checks the seal is valid and lets you in

Key Concepts

TermMeaning
Identity Provider (IdP)System that authenticates users (Entra ID, Okta)
Service Provider (SP)Application user wants to access (Salesforce, ServiceNow)
AssertionXML document with identity claims, signed by IdP
MetadataXML file describing IdP/SP endpoints and certificates
ACS URLAssertion Consumer Service - where IdP sends the assertion
Entity IDUnique identifier for IdP or SP

SAML Assertion Example

<saml:Assertion xmlns:saml="urn:oasis:names:tc:SAML:2.0:assertion"
    ID="_abc123" IssueInstant="2024-01-15T10:00:00Z" Version="2.0">
    
    <saml:Issuer>https://login.microsoftonline.com/tenant-id/</saml:Issuer>
    
    <ds:Signature>...digital signature...</ds:Signature>
    
    <saml:Subject>
        <saml:NameID Format="emailAddress">john.doe@company.com</saml:NameID>
    </saml:Subject>
    
    <saml:Conditions NotBefore="2024-01-15T10:00:00Z" NotOnOrAfter="2024-01-15T10:05:00Z">
        <saml:AudienceRestriction>
            <saml:Audience>https://salesforce.com</saml:Audience>
        </saml:AudienceRestriction>
    </saml:Conditions>
    
    <saml:AuthnStatement AuthnInstant="2024-01-15T10:00:00Z">
        <saml:AuthnContext>
            <saml:AuthnContextClassRef>urn:oasis:names:tc:SAML:2.0:ac:classes:PasswordProtectedTransport</saml:AuthnContextClassRef>
        </saml:AuthnContext>
    </saml:AuthnStatement>
    
    <saml:AttributeStatement>
        <saml:Attribute Name="email">
            <saml:AttributeValue>john.doe@company.com</saml:AttributeValue>
        </saml:Attribute>
        <saml:Attribute Name="groups">
            <saml:AttributeValue>Sales</saml:AttributeValue>
            <saml:AttributeValue>Marketing</saml:AttributeValue>
        </saml:Attribute>
    </saml:AttributeStatement>
</saml:Assertion>

OAuth 2.0

OAuth Analogy

OAuth is like giving a valet parking key:

  • You don't give the valet your house keys, just the car key
  • The valet can move your car (limited access) but can't open your house
  • You can revoke access anytime

OAuth is for authorization (what you can do), NOT authentication (who you are)!

Kerberos

Kerberos Analogy

Kerberos is like an amusement park ticket system:

  1. You buy a day pass at the entrance (TGT from KDC)
  2. For each ride, you exchange the day pass for a ride ticket (Service Ticket)
  3. Show ride ticket to ride operator (service)
  4. You never show your ID again after getting the day pass

Kerberos Components

ComponentWhat It Is
KDC (Key Distribution Center)Central auth server (Domain Controller in AD)
AS (Authentication Service)Issues initial TGT
TGS (Ticket Granting Service)Issues service tickets
TGT (Ticket Granting Ticket)"Day pass" - proves you're authenticated
Service Ticket"Ride ticket" - access specific service
PrincipalUser or service identity

Kerberos Flow

USER/CLIENT KDC (Domain Controller) SERVICE │ ┌────────────────┬────────────────┐ │ │ │ AS │ TGS │ │ │ │ Authentication │ Ticket Granting│ │ │ │ Service │ Service │ │ │ └────────────────┴────────────────┘ │ │ │ │ │ 1. AS-REQ: "I am john, want TGT" │ │ │ (encrypted with user's password hash) │ │ │─────────────────────────────────────────▶│ │ │ │ │ │ 2. AS-REP: Here's your TGT │ │ │ (encrypted with KDC key + session key) │ │ │◀─────────────────────────────────────────│ │ │ │ │ │ [User now has TGT - valid ~10 hours] │ │ │ │ │ │ 3. TGS-REQ: "I want ticket for FileServer"│ │ │ (includes TGT) │ │ │─────────────────────────────────────────▶│ │ │ │ │ │ 4. TGS-REP: Here's service ticket │ │ │ (encrypted with service's key) │ │ │◀─────────────────────────────────────────│ │ │ │ │ │ 5. AP-REQ: Access FileServer │ │ (presents service ticket) │ │────────────────────────────────────────────────────────────────────────────────▶│ │ │ │ 6. AP-REP: Access granted + optional mutual auth │ │◀────────────────────────────────────────────────────────────────────────────────│

Kerberos Security Risks

  • Kerberoasting: Requesting service tickets and offline-cracking them
  • AS-REP Roasting: Attacking accounts without pre-authentication
  • Golden Ticket: Forged TGT using KRBTGT hash
  • Silver Ticket: Forged service ticket using service account hash
  • Pass-the-Ticket: Stealing and reusing tickets

LDAP

What is LDAP?

LDAP (Lightweight Directory Access Protocol) is a protocol for accessing and maintaining directory services. It's NOT an authentication protocol per se, but is often used for it.

LDAP Analogy

LDAP is like a phone book database:

  • Hierarchical structure (country → company → department → person)
  • You can search for entries
  • You can authenticate by "binding" (proving you're who you claim)

LDAP Structure (DN - Distinguished Name)

# User's Distinguished Name (DN)
CN=John Doe,OU=Sales,OU=Users,DC=company,DC=com

# Breakdown:
# CN = Common Name (the user)
# OU = Organizational Unit (container)
# DC = Domain Component (domain name)

# Reading right to left: company.com → Users → Sales → John Doe

LDAP Bind (Authentication)

# Simple Bind (sends password in clear - use LDAPS!)
ldapsearch -x -H ldap://dc.company.com -D "CN=John Doe,OU=Users,DC=company,DC=com" -w "password"

# Secure LDAPS (port 636)
ldapsearch -x -H ldaps://dc.company.com:636 -D "john@company.com" -w "password"

# Search for user
ldapsearch -x -H ldaps://dc.company.com -b "DC=company,DC=com" "(sAMAccountName=john)"

Always Use LDAPS!

LDAP simple bind sends passwords in cleartext. Always use:

  • LDAPS (port 636): LDAP over TLS
  • StartTLS: Upgrade connection to TLS

RADIUS

What is RADIUS?

RADIUS (Remote Authentication Dial-In User Service) is used for network access authentication - VPNs, WiFi, network device login.

Common RADIUS Servers

  • Microsoft NPS (Network Policy Server): Windows Server built-in
  • FreeRADIUS: Open source, very flexible
  • Cisco ISE: Enterprise NAC solution
  • Aruba ClearPass: Network access control
