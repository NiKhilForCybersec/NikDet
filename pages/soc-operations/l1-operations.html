Part 1: Understanding the L1 Role

What Does an L1 Analyst Do?

L1 analysts are the first line of defense in the SOC. You're the gatekeeper who determines whether security alerts are real threats that need action or false alarms that can be closed.

Primary Goal

Quickly and accurately classify alerts as True Positive (real threat), False Positive (not a threat), or escalate to L2 for deeper investigation.

Time Expectation

Initial triage should take 5-15 minutes per alert. If you can't determine TP/FP in 15 minutes, escalate.

L1 Responsibilities

ResponsibilityWhat This MeansTime Allocation
Alert Monitoring Watch alert queues, acknowledge new alerts promptly Continuous
Initial Triage Quickly assess each alert's validity and severity 5-10 min/alert
Basic Investigation Gather context: who, what, when, where 5-15 min/alert
Documentation Record all findings in ticketing system 5 min/alert
Escalation Pass complex/confirmed incidents to L2 As needed
Basic Containment Execute pre-approved actions (block IP, isolate host) As authorized
User Support Handle security questions, phishing reports As received

What L1 Does NOT Do

  • Deep forensic investigation (that's L2/L3)
  • Malware reverse engineering
  • Create new detection rules
  • Make major containment decisions without approval
  • Communicate directly with executives during incidents

Part 2: Managing the Alert Queue

Priority Order

Work alerts in this order (not first-in-first-out):

PriorityAlert TypeResponse Time
1. Critical Ransomware, active breach, executive systems < 15 minutes
2. High Malware execution, credential theft, C2 traffic < 30 minutes
3. Medium Suspicious behavior, policy violations < 2 hours
4. Low Informational alerts, routine scans < 8 hours

Queue Management Tips

Best Practices
  • Don't cherry-pick easy alerts. Work high priority first, even if they're harder.
  • Acknowledge alerts immediately. This shows others it's being worked.
  • Set realistic SLAs. Don't let alerts age in queue.
  • Communicate during shift changes. Hand off in-progress work.
  • Track your average handle time. Know your pace.

Part 3: Step-by-Step Alert Triage

The Triage Workflow

1
Receive & Acknowledge

Alert appears in queue. Acknowledge it to show you're working on it.

Time: 30 seconds

2
Read the Alert

Understand what the alert is telling you:

  • What triggered the alert? (rule name, description)
  • What system/user is involved?
  • When did it happen?
  • What's the severity?

Time: 1-2 minutes

3
Check for Known FP

Before investigating, check if this is a known false positive:

  • Is there a documented FP pattern for this alert?
  • Has this same alert fired on this user/system before?
  • Is there an active change window that explains this?

Time: 1-2 minutes

4
Gather Context

Collect information to understand if this is malicious:

  • Who is the user? What's their role?
  • What system is affected? Is it critical?
  • What happened before and after the alert?
  • Are there related alerts?

Time: 5-10 minutes

5
Make a Decision

Based on your investigation:

  • False Positive: Document reason, close alert
  • True Positive: Escalate to L2 or take authorized action
  • Needs More Investigation: If >15 min, escalate to L2

Time: 1-2 minutes

6
Document Everything

Record your findings regardless of outcome:

  • What you investigated
  • What you found
  • Why you made your decision
  • Any actions taken

Time: 3-5 minutes

Part 4: Investigation Fundamentals

The Five W's

Every investigation answers these questions:

QuestionWhat to FindWhere to Look
WHO User account, their role, department, manager Active Directory, HR system, asset inventory
WHAT Exact action that triggered alert Alert details, raw logs, process info
WHEN Timestamp, during/outside business hours Alert timestamp, log timeline
WHERE System name, IP, location, network zone Alert details, asset inventory, CMDB
WHY Is there a legitimate reason for this activity? User context, change tickets, business justification

Investigation Queries (KQL Examples)

// 1. Get user's recent activity (last 24 hours)
union DeviceProcessEvents, DeviceNetworkEvents, DeviceFileEvents
| where Timestamp > ago(24h)
| where AccountName == "suspicious.user"
| project Timestamp, ActionType, FileName, ProcessCommandLine, RemoteIP
| sort by Timestamp desc
| take 100

// 2. Get all activity on a specific machine
union Device*
| where Timestamp > ago(24h)
| where DeviceName == "WORKSTATION01"
| summarize EventCount = count() by ActionType
| sort by EventCount desc

// 3. Check if IP is known malicious
ThreatIntelligenceIndicator
| where NetworkIP == "203.0.113.50"
| project Description, ThreatType, ConfidenceScore, Source

// 4. Find related alerts for same user/system
SecurityAlert
| where TimeGenerated > ago(7d)
| where CompromisedEntity contains "suspicious.user"
   or CompromisedEntity contains "WORKSTATION01"
| project TimeGenerated, AlertName, Severity, Status

// 5. Check user's login history
SigninLogs
| where TimeGenerated > ago(7d)
| where UserPrincipalName == "suspicious.user@company.com"
| project TimeGenerated, ResultType, Location, IPAddress, AppDisplayName
| sort by TimeGenerated desc

Red Flags During Investigation

Escalate Immediately If You See:
  • Known malware names (Mimikatz, Cobalt Strike, etc.)
  • Commands attempting to disable security tools
  • Large data transfers to external IPs
  • Multiple systems showing same suspicious activity
  • Executive or privileged accounts compromised
  • Activity outside user's normal working hours from unusual location
  • Registry modifications for persistence
  • Encoded PowerShell commands

Part 5: When and How to Escalate

Escalation Triggers

TriggerWhy EscalateUrgency
Confirmed malware execution Needs containment, forensics, remediation Immediate
Credential theft indicators Attacker may have access to other systems Immediate
Multiple systems affected May indicate lateral movement/larger compromise Immediate
Executive/VIP involved High-value target, needs senior attention High
Critical system affected Business impact concerns High
Can't determine TP/FP in 15 min Needs deeper investigation skills Normal
Outside your authorization Action needed that you can't perform Normal

How to Escalate Properly

A good escalation includes:

ESCALATION TEMPLATE
━━━━━━━━━━━━━━━━━━━━━

Alert: [Alert Name] - [Alert ID]
Severity: [Critical/High/Medium]
Time: [When alert fired]

Affected:
- User: john.doe@company.com (Sales Manager)
- System: WORKSTATION-JD01 (10.10.5.42)
- Location: New York Office

Summary:
Observed encoded PowerShell execution on user's workstation.
Process tree shows Word -> cmd -> PowerShell -enc [base64].

What I Investigated:
1. Verified user exists in AD - confirmed
2. Checked for change tickets - none found
3. Reviewed process tree - suspicious parent/child
4. Checked for related alerts - found 2 more on same system

Why I'm Escalating:
Behavior matches known malware delivery technique.
Cannot determine legitimate business reason.
Multiple indicators suggest potential compromise.

Recommended Action:
Consider isolating workstation pending investigation.

Evidence Attached:
- Screenshot of process tree
- Raw log events
- Timeline of activity

Part 6: Documentation Standards

Why Documentation Matters

  • Continuity: Others can pick up where you left off
  • Metrics: Track FP rates, response times
  • Legal: May be needed for legal proceedings
  • Learning: Build knowledge base for future alerts

Required Fields for Every Alert

FieldContentExample
Alert IDUnique identifierINC-2025-00142
TimestampWhen investigated2025-01-15 14:32 UTC
AnalystWho worked itJohn Smith
ClassificationTP, FP, or EscalatedFalse Positive
SummaryBrief description"Encoded PowerShell from SCCM deployment"
Investigation StepsWhat you checked"Verified parent process, checked change tickets"
FindingsWhat you found"Activity from authorized ConfigMgr deployment"
Decision RationaleWhy you classified it this way"Parent process is legitimate SCCM agent"
Actions TakenWhat you did"None - closed as FP"

Good vs. Bad Documentation

Bad Example

"Checked it, looks fine. FP."

Problems: No details, can't learn from it, no audit trail

Good Example

"Encoded PowerShell alert on WKSTN-042. Verified user jsmith is IT admin. Parent process is CcmExec.exe (SCCM). Correlated with CHG-4521 - scheduled software deployment. Closing as FP - legitimate SCCM activity."

Why good: Complete context, reproducible, builds knowledge

Part 7: Common Alert Types Explained

Alert Type 1: Encoded PowerShell

What It Means

PowerShell command using -enc/-encodedcommand to hide what it's doing.

Why It's Suspicious

Attackers use encoding to evade detection. Legitimate tools rarely need encoding.

How to Investigate

  1. Look at the parent process (what launched PowerShell)
  2. Decode the base64 to see actual command
  3. Check if there's a change ticket or deployment

Common FPs

  • SCCM/ConfigMgr deployments
  • Intune management
  • Legitimate IT automation scripts

Alert Type 2: Suspicious Login

What It Means

Login from unusual location, impossible travel, or after hours.

Why It's Suspicious

Could indicate stolen credentials being used by attacker.

How to Investigate

  1. Check if user is traveling (out of office, travel booking)
  2. Verify the IP/location makes sense
  3. Look at what actions were taken after login
  4. Check for VPN usage (VPN exit nodes can appear as different locations)

Common FPs

  • VPN connections showing exit node location
  • Mobile device on cellular network
  • User actually traveling

Alert Type 3: Malware Detection

What It Means

AV/EDR detected known malware signature or behavior.

Why It's Important

Even if blocked, indicates attack attempt. May have related activity.

How to Investigate

  1. Confirm AV/EDR blocked/quarantined the file
  2. Check how it got there (email, download, USB)
  3. Look for execution attempts
  4. Check for related network activity (C2)

When to Escalate

  • If malware executed before being caught
  • If user clicked something in phishing email
  • If multiple systems have same malware
