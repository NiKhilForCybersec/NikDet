Step-by-Step: Block Legacy Authentication

StepActionDetailsValidation
1Analyze current legacy auth usageEntra ID > Sign-in logs > Filter: Client app = Other clients, Exchange ActiveSyncDocument users/apps using legacy auth
2Migrate users off legacy authUpdate Outlook to modern auth, migrate apps to OAuthRe-check sign-in logs, usage should decrease
3Create CA policy in Report-onlyName: CA001-Block-Legacy-Auth, Users: All, Cloud apps: All, Conditions: Client apps = Other/EAS, Grant: BlockPolicy shows "Report-only" status
4Monitor Report-only impactCA > Insights and reporting > Review "What If" for affected usersUnderstand who would be blocked
5Communicate to affected usersSend notification about upcoming change, provide migration stepsUsers acknowledge and migrate
6Enable policy (On)Edit policy > Enable policy: OnSign-in logs show blocks
7Handle exceptionsCreate exclusion group for temporary exceptions with expiration datesTrack and follow up on exceptions

Common Mistakes & How to Avoid

MistakeConsequencePrevention
Not excluding break-glass accountsIf policy misconfigured, no one can fix itAlways exclude break-glass group from ALL blocking policies
Targeting "All users" immediatelyBusiness disruption, user lockoutsStart with pilot group, expand gradually
Skipping Report-only modeCan't see impact before enablingRun every new policy in Report-only for 1-2 weeks minimum
Too many exclusionsPolicies become ineffectiveTrack all exclusions, require justification, set expiration
Not testing with "What If"Unexpected blocks for legitimate usersUse What If tool to simulate before enabling
Conflicting policiesUnpredictable behaviorDocument all policies, avoid overlapping scopes, use naming conventions

Troubleshooting Conditional Access

IssueDiagnosis StepsSolution
User can't sign in after CA enabled1. Check Sign-in logs for user 2. Look at "Conditional Access" tab 3. See which policy blockedAdd user to exclusion group temporarily, investigate why they don't meet conditions
Policy not applying1. Verify policy is "On" not "Report-only" 2. Check user is in target group 3. Check conditions matchUse "What If" to simulate, verify all conditions
MFA prompt every timeCheck if "Sign-in frequency" is set too low or "Persistent browser session" is disabledAdjust session controls, consider device compliance for reduced prompts
App not working after CACheck if app supports modern auth, check app's Conditional Access supportSome apps need specific CA configuration, check vendor documentation

Implementing DLP

DLP Rollout Phases

PhaseDurationActionsSuccess Criteria
Phase 1: Discovery2-4 weeksEnable audit-only policies for common sensitive types (SSN, credit cards). No user notifications.Understand data patterns, identify high-risk users/locations
Phase 2: Education2 weeksEnable user notifications (tips/warnings). Train users on data handling. Refine patterns based on FPs.Users aware of DLP, FP rate <30%
Phase 3: Warn2-4 weeksEnable "warn with override" for medium-sensitivity. Users can proceed with justification.Override rate <20%, justifications reasonable
Phase 4: BlockOngoingEnable blocking for highest-sensitivity data. Maintain warn for medium. Continue audit for low.No business disruption, incidents decrease

StepActionConfigurationWhy
1Go to Purview compliance portalcompliance.microsoft.com > Data loss prevention > PoliciesCentral DLP management

DLP False Positive Handling

FP TypeExampleSolution
Legitimate business processHR sending W-2 to payroll vendorCreate exception for specific sender/recipient pair with documentation
Test/sample dataTraining documents with example SSNsUse clearly fake numbers (000-00-0000), or exclude specific document libraries
Pattern match on non-sensitive dataPart numbers that look like SSNsAdd negative keywords (part#, SKU, order) to exclude
Specific applicationLine-of-business app that handles SSNs legitimatelyExclude specific application or URL
Encrypted filesPassword-protected ZIP flagged but can't be scannedBlock password-protected files to external, or accept gap
