Palo Alto Security Policies

Complete guide to security policy configuration, App-ID, User-ID integration, NAT policies, and policy optimization.

Palo Alto Policy Philosophy

Palo Alto takes a positive security model:

  • Traditional: "Block bad things" (blacklist)
  • Palo Alto: "Allow only good things" (whitelist)

Instead of "allow port 443", you say "allow Salesforce, Office365, and Zoom" - the ACTUAL applications you need.

NAT Policies

NAT vs Security Policy Order

DNAT (Destination NAT): Happens BEFORE security policy lookup. Security policy sees the POST-NAT destination.
SNAT (Source NAT): Happens AFTER security policy. Security policy sees the PRE-NAT source.

Source NAT (Outbound Internet)

# Hide NAT - translate all internal to single public IP
# set rulebase nat rules Outbound-SNAT source-translation dynamic-ip-and-port interface-address interface ethernet1/1
# set rulebase nat rules Outbound-SNAT from Trust
# set rulebase nat rules Outbound-SNAT to Untrust
# set rulebase nat rules Outbound-SNAT source any
# set rulebase nat rules Outbound-SNAT destination any
# set rulebase nat rules Outbound-SNAT service any

# commit

1Explicit deniesBlock bad IPs, block bad apps
2Critical infrastructureDNS, DHCP, AD traffic

App-ID and "application-default"

application-default means "use the ports this application normally uses."

Example: If you allow "web-browsing" with service "application-default", it allows HTTP on port 80 only. If someone tries web-browsing on port 8080, it won't match.

This prevents port-hopping attacks where malware uses non-standard ports.

Policy Best Practices

Best Practices

  • Use App-ID: Never just allow "any" application
  • Use application-default: Prevents port-hopping
  • Attach security profiles: Every allow rule should have profiles
  • Enable logging: At minimum log-end, ideally log-start too
  • Name rules clearly: "IT-to-Servers-SSH" not "Rule_42"
  • Use tags: Tag rules for auditing and reporting
  • Review hit counts: Zero-hit rules may be unnecessary
  • Commit often: Small commits are easier to troubleshoot

Common Mistakes

  • ❌ Using service "any" instead of "application-default"
  • ❌ No security profiles on allow rules
  • ❌ Overly broad rules (any-any-any-allow)
  • ❌ Forgetting to commit after changes
  • ❌ Wrong policy order (broad rules before specific)
  • ❌ Not logging denied traffic
