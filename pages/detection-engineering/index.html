Detection Engineering

Learn how to build, test, and maintain detection rules that actually catch attackers while minimizing false positives.

What is Detection Engineering?

Detection Engineering is the discipline of creating rules that identify malicious activity in your logs and telemetry. When these rules match suspicious patterns, they create alerts for analysts to investigate.

In simple terms: You write a rule like "alert me when someone tries 10 failed logins in 5 minutes" and the SIEM creates an alert whenever that pattern occurs.

The Challenge: Creating rules that catch real attacks (true positives) without creating too many false alerts that waste analyst time (false positives).
Think of it like this

Smoke Detector Analogy:

  • True Positive: Fire starts → smoke detector goes off → you evacuate. Perfect!
  • False Positive: You burn toast → smoke detector goes off → annoying but safe
  • False Negative: Fire starts → smoke detector doesn't go off → disaster!

Detection engineering is about building "smoke detectors" for cyber attacks that alert on real fires but not every time someone burns toast.

Why Detection Engineering Matters

ProblemWithout Detection EngineeringWith Detection Engineering
Alert Quality 100s of alerts daily, 90% false positives, analysts burned out Focused alerts, high true positive rate, analysts effective

Real Example: Detecting Password Spraying

Step 1 - Identify Need: We want to detect password spray attacks (trying one password across many accounts).

Step 2 - Check Data: We have Azure AD sign-in logs with failed login events.

Step 3 - Write Rule (KQL):

// Detect password spray: Many users, few failures per user, from one IP
SigninLogs
| where ResultType != 0  // Failed logins only
| where TimeGenerated > ago(1h)
| summarize 
    FailedUsers = dcount(UserPrincipalName),  // How many different users?
    TotalFailures = count()                    // Total failed attempts
    by IPAddress
| where FailedUsers > 10          // More than 10 users targeted
| where TotalFailures < FailedUsers * 3  // But few failures per user (spray pattern)

Step 4 - Test: Run against historical data. Did it catch the simulated attack? How many false positives from legitimate systems?

Step 5 - Deploy: Create scheduled analytics rule in Sentinel.

Step 6 - Tune: Add exclusions for known vulnerability scanners, adjust thresholds.

Good vs Bad Detection Rules

AspectBad Rule ❌Good Rule ✓
Logic Looks for "PowerShell" anywhere in logs Looks for PowerShell with encoded commands from unusual parent process
Context Just matches a pattern Considers who, what, when, where
Exclusions None - alerts on everything Has documented exclusions for known legitimate activity
Documentation "Detects bad stuff" Explains what it detects, why, MITRE mapping, response steps
Testing Never tested against real attack Validated with Atomic Red Team or purple team exercise

Key Detection Engineering Concepts

Understanding Detection Metrics

MetricWhat It MeansWhy It Matters
True Positive (TP) Alert fires + it's actually malicious This is what you want!
False Positive (FP) Alert fires + it's actually benign Wastes analyst time, causes alert fatigue
True Negative (TN) No alert + nothing malicious happened Expected normal operation
False Negative (FN) No alert + but attack actually happened WORST CASE - missed the attack!
The Trade-off: Making rules more sensitive catches more attacks (fewer FNs) but also creates more false positives. Making rules more specific reduces FPs but might miss attack variants. Finding the right balance is the art of detection engineering.

Getting Started

Where to Start
  1. Pick one attack technique - Start with something common like "Encoded PowerShell" or "Brute Force Login"
  2. Check your data - Do you have the logs to detect it?
  3. Find existing rules - Check Sigma rules repository before writing from scratch
  4. Test with Atomic Red Team - Run the attack safely and verify your rule catches it
  5. Document everything - What it detects, how to investigate, known FP sources
