Heartbleed (CVE-2014-0160)

HEARTBLEED - THE ATTACK THAT CHANGED EVERYTHING ═══════════════════════════════════════════════════════════════════════════════ THE VULNERABILITY (OpenSSL Heartbeat Extension Bug): ───────────────────────────────────────────────────────────────────────────── TLS Heartbeat: "Are you still there?" keep-alive mechanism NORMAL REQUEST: ┌─────────────────────────────────────────────────────────────────────────┐ │ Client: "Please echo back 5 bytes: 'hello'" │ │ Server: "hello" ✓ Correct │ └─────────────────────────────────────────────────────────────────────────┘ MALICIOUS REQUEST (Heartbleed): ┌─────────────────────────────────────────────────────────────────────────┐ │ Attacker: "Please echo back 65535 bytes: 'x'" │ │ ▲ │ │ │ │ │ Lie! Only sent 1 byte, but asked for 64KB │ │ │ │ Server reads 64KB from memory, starting at 'x' location: │ │ "x" + [64KB of server memory] │ │ │ │ │ └── Could contain: │ │ • Private keys │ │ • Session tokens │ │ • Usernames/passwords │ │ • Source code │ │ • Customer data │ │ │ │ Server: "x[PRIVATE KEY DATA][PASSWORD:admin123][SESSION:abc...]" │ │ ───────────────────────────────────────────────────── │ │ Attacker now has your secrets! │ └─────────────────────────────────────────────────────────────────────────┘ THE BUG (Missing Bounds Check): ───────────────────────────────────────────────────────────────────────────── Vulnerable OpenSSL code (simplified): ┌─────────────────────────────────────────────────────────────────────────┐ │ // Attacker controls 'payload_length' field │ │ payload_length = request->payload_length; // Says 65535 │ │ payload = request->payload; // Actually only 1 byte │ │ │ │ // BUG: No check that payload_length matches actual data! │ │ memcpy(response, payload, payload_length); // Copies 64KB! │ │ │ │ // SHOULD HAVE BEEN: │ │ if (payload_length > actual_length) { │ │ return ERROR; // Reject invalid request │ │ } │ └─────────────────────────────────────────────────────────────────────────┘ IMPACT & RESPONSE: ───────────────────────────────────────────────────────────────────────────── AFFECTED: ~17% of all HTTPS servers (500,000+ sites) REQUIRED ACTIONS: 1. Patch OpenSSL immediately 2. Revoke and replace ALL certificates (private keys may be stolen) 3. Reset all user passwords (sessions may be stolen) 4. Rotate all secrets (API keys, database passwords) 5. Check for signs of exploitation (hard - attack leaves no logs!)

POODLE Attack

POODLE - PADDING ORACLE ON DOWNGRADED LEGACY ENCRYPTION ═══════════════════════════════════════════════════════════════════════════════ THE ATTACK: ───────────────────────────────────────────────────────────────────────────── Step 1: DOWNGRADE ┌─────────────────────────────────────────────────────────────────────────┐ │ Attacker (MITM) intercepts TLS handshake │ │ │ │ Client: "I support TLS 1.2, TLS 1.1, TLS 1.0, SSL 3.0" │ │ │ │ │ ▼ │ │ Attacker blocks all attempts, forces fallback to SSL 3.0 │ │ │ │ │ ▼ │ │ Client and Server negotiate SSL 3.0 (vulnerable!) │ └─────────────────────────────────────────────────────────────────────────┘ Step 2: EXPLOIT CBC PADDING ┌─────────────────────────────────────────────────────────────────────────┐ │ SSL 3.0 CBC padding is not fully specified │ │ Server only checks last byte of padding, ignores rest │ │ │ │ Attacker can: │ │ 1. Capture encrypted HTTPS request (with cookie) │ │ 2. Move encrypted cookie block to padding position │ │ 3. Send modified request to server │ │ 4. Server decrypts → checks padding → accepts/rejects │ │ 5. If accepted, attacker learns 1 byte of cookie │ │ 6. Repeat 256 times per byte │ │ │ │ Result: Full session cookie decrypted in ~15 minutes │ └─────────────────────────────────────────────────────────────────────────┘ DEFENSE: ───────────────────────────────────────────────────────────────────────────── ✅ Disable SSL 3.0 entirely (no legitimate reason to support it) ✅ Enable TLS_FALLBACK_SCSV (prevents downgrade attacks) ✅ Use TLS 1.2+ with GCM mode (no CBC padding issues)

Man-in-the-Middle Attacks

MAN-IN-THE-MIDDLE (MITM) ATTACK PATTERNS ═══════════════════════════════════════════════════════════════════════════════ BASIC MITM (Without TLS): ───────────────────────────────────────────────────────────────────────────── Victim Attacker Server │ │ │ │ ──── HTTP Request ────► │ │ │ (plaintext) │ │ │ │ ──── HTTP Request ────► │ │ │ │ │ │ ◄──── Response ──────── │ │ ◄──── Response ──────── │ │ │ (attacker can modify!) │ │ Attacker sees ALL traffic, can modify anything. Common Cryptographic Mistakes

Critical Cryptographic Mistakes to Avoid

MistakeProblemCorrect Approach
Using MD5/SHA-1Collision attacks provenUse SHA-256 or SHA-3
ECB mode encryptionPatterns visible in ciphertextUse GCM or CBC with random IV
Static IVSame plaintext = same ciphertextRandom IV per message
SHA-256 for passwordsToo fast, enables brute forceUse bcrypt/Argon2 (slow by design)
Unsalted password hashesRainbow table attacksUnique random salt per password
RSA without OAEPPadding oracle attacksUse RSA-OAEP or ECDH
Hardcoded keysKeys in source code leakUse HSM, key management system
Math.random() for cryptoPredictable outputUse crypto.getRandomValues() or /dev/urandom
Rolling own cryptoSubtle bugs, missing edge casesUse tested libraries (OpenSSL, libsodium)
Allowing TLS 1.0/1.1Multiple known attacksTLS 1.2 minimum, prefer TLS 1.3
Static RSA key exchangeNo forward secrecyUse ECDHE for all connections
Ignoring certificate errorsAllows MITMFail closed on cert errors
