PB-TRI-001

Authentication Alert Triage

Quickly triage authentication-related alerts including failed logins, brute force, impossible travel, and suspicious sign-ins.

TierL1
Time5-15 min

Common Authentication Alerts

Alert TypeWhat It MeansSeverity
Brute ForceMultiple failed login attemptsMedium-High
Password SpraySame password tried across many accountsHigh
Impossible TravelLogin from locations that are physically impossibleHigh
Risky Sign-inAzure AD detected anomalous behaviorMedium-High
Legacy AuthUse of deprecated authentication protocolsMedium
New LocationFirst login from unfamiliar locationLow-Medium

Step 1: Gather Alert Context

For any authentication alert, immediately gather:

  • User: Who is the account? VIP? Service account? Regular user?
  • Source IP: Where did the attempt come from?
  • Outcome: Did it succeed or fail?
  • Timing: When? Business hours? Weekend?
  • Volume: How many attempts?

Step 2: Quick Lookups

// KQL: Get full context for the user
let User = "user@domain.com";
SigninLogs
| where TimeGenerated > ago(7d)
| where UserPrincipalName == User
| summarize 
    TotalLogins = count(),
    SuccessfulLogins = countif(ResultType == 0),
    FailedLogins = countif(ResultType != 0),
    UniqueIPs = dcount(IPAddress),
    UniqueLocations = dcount(Location),
    Locations = make_set(Location),
    Apps = make_set(AppDisplayName)
| extend FailureRate = round(toreal(FailedLogins) / TotalLogins * 100, 2)

// KQL: Check if IP is known/corporate
let AlertIP = "1.2.3.4";
SigninLogs
| where TimeGenerated > ago(30d)
| where IPAddress == AlertIP
| summarize 
    TotalUsers = dcount(UserPrincipalName),
    Users = make_set(UserPrincipalName, 10),
    FirstSeen = min(TimeGenerated),
    LastSeen = max(TimeGenerated)

// KQL: Recent activity for the user
SigninLogs
| where TimeGenerated > ago(24h)
| where UserPrincipalName == "user@domain.com"
| project TimeGenerated, IPAddress, Location, AppDisplayName, 
    ResultType, ResultDescription, DeviceDetail, RiskLevelDuringSignIn
| order by TimeGenerated desc

Step 3: Decision Tree

Q1: Did the authentication succeed?

  • NO (Failed) → Check volume. >20 failures = potential brute force. Verify account not locked. Low priority if isolated failures.
  • YES (Success) → Continue to Q2

Q2: Is the source IP known/expected?

  • YES (Corporate IP/VPN/Known) → Likely legitimate. Close as benign unless other indicators.
  • NO (Unknown IP) → Continue to Q3

Q3: Is the location consistent with user's normal pattern?

  • YES → Possible new ISP/device. Contact user to verify if uncertain.
  • NO (Impossible travel) → HIGH PRIORITY - Escalate to L2, consider account compromise.

Q4: Was MFA completed?

  • YES → Reduces likelihood of compromise. User likely legitimate.
  • NO (MFA bypassed or not required) → Higher risk. Investigate legacy auth or conditional access gaps.

Step 5: Escalation Criteria

Escalate to L2/L3 if:

  • Successful login from impossible location AND no MFA
  • Brute force followed by successful login
  • VIP/executive account involved
  • Service account with anomalous activity
  • Multiple accounts targeted from same source
  • Login followed by suspicious actions (mailbox rules, forwarding)
