PB-INV-001

Phishing Investigation Playbook

Complete, step-by-step investigation procedure for reported or detected phishing emails. Covers email header analysis, IOC extraction, scope determination, user impact assessment, and escalation criteria.

SeverityHigh
TierL2 / L3
Time30-90 min
Last Updated2025-01-02
T1566.001 T1566.002 T1566.003 T1598 T1078 T1114

Overview

Phishing is the most common initial access vector, responsible for over 90% of successful breaches. This playbook provides a systematic, thorough approach to investigating phishing incidents to determine the full scope of impact and prevent further compromise.

What This Playbook Covers
  • User-reported suspicious emails
  • Email gateway detected phishing
  • Credential harvesting attempts
  • Malware delivery via email
  • Spearphishing campaigns
  • Internal phishing (compromised account sending)

Objectives

By the end of this investigation, you will have determined:

  1. Validity - Is this actually a phishing email or false positive?
  2. Type - Credential harvesting, malware delivery, or reconnaissance?
  3. Scope - How many users received this email?
  4. Impact - Did anyone interact with it? Were credentials stolen?
  5. IOCs - What indicators can be blocked organization-wide?
  6. Attribution - Is this a targeted attack or spray campaign?

Step 1: Initial Triage (5 Minutes)

Before deep investigation, quickly assess whether this needs immediate escalation or standard processing.

1.1
Gather Basic Information
Collect the essentials from the report:
FieldWhere to Find ItWhy It Matters
Reporter NameTicket/ReportContact for follow-up questions
Reporter EmailTicket/ReportMay need to examine their mailbox
Report TimeTicket timestampCalculate response time SLA
Email Received TimeEmail headersScope search timeframe
Sender AddressEmail headers (From:)Primary search pivot
Reply-To AddressEmail headersOften different in phishing
Subject LineEmailSecondary search pivot
User Action TakenAsk reporterDetermines urgency
1.2
Quick Malicious Indicators Check
Look for obvious red flags that confirm malicious intent:
IndicatorHighly SuspiciousLikely Legitimate
Sender Domain Lookalike (micros0ft.com), free email (gmail for "bank"), newly registered Known vendor domain, internal domain
Display Name vs Email "IT Support" <random@gmail.com> Display name matches email domain
Reply-To Different domain than sender Same as sender or expected
Links Shortened URLs, suspicious TLDs (.xyz, .top), IP addresses Direct links to known vendor sites
Urgency Language "Act immediately", "Account suspended", "Verify now" Normal business tone
Attachments .exe, .js, .vbs, .iso, password-protected .zip .pdf, .docx from known sender
Grammar/Spelling Multiple errors, awkward phrasing Professional writing
Personalization "Dear Customer", generic greeting Uses recipient's actual name
1.3
Immediate Escalation Check
STOP - Escalate Immediately If Any Are True
  • ✅ User confirms they entered credentials on a suspicious site
  • ✅ User opened attachment and system is behaving abnormally
  • ✅ Multiple users (5+) reporting the same email = active campaign
  • ✅ Executive, finance, or IT admin is the target
  • ✅ Email requests wire transfer, gift cards, or sensitive data
  • ✅ Sender appears to be internal compromised account
  • ✅ Known active threat campaign (matching threat intel)

Escalation Path: Notify SOC Lead → Engage L3/IR team → Consider containment before full investigation

1.4
Classify Phishing Type
Determine the attack objective to guide investigation focus:
TypeIndicatorsInvestigation Focus
Credential Harvesting Login page link, "verify account", "password expiring" Check for credential entry, suspicious sign-ins
Malware Delivery Attachment, "invoice", "document", macro-enabled files Check for file execution, process creation, persistence
BEC/Impersonation Executive name, requests action, no links/attachments Check for financial fraud, data theft
Reconnaissance Tracking pixel, read receipt request, no payload Check what info was leaked, future targeting
Callback Phishing Phone number to call, fake invoice/subscription Check if user called, what info was shared

Step 2: Email Header Analysis (10 Minutes)

Email headers contain critical forensic evidence. Analyze them to understand the email's true origin and authentication status.

2.1
Extract Full Email Headers
How to get headers from different clients:
ClientSteps
Outlook DesktopOpen email → File → Properties → Internet Headers
Outlook WebOpen email → ⋯ menu → View → View message details
GmailOpen email → ⋮ menu → Show original
M365 AdminMessage Trace → View message details → Headers
Exchange PowerShellGet-MessageTrackingLog | Get-MessageHeader
2.2
Analyze Key Headers
Critical headers to examine:
HeaderWhat to Look ForRed Flags
From: Display name and email address Display name impersonating known entity, mismatch between name and domain
Reply-To: Where replies are sent Different domain than From address (BEC indicator)
Return-Path: Bounce address, envelope sender Different from From address (spoofing indicator)
Received: Path email took (read bottom to top) Unexpected mail servers, mismatched geography
X-Originating-IP: Source IP of sender VPS, Tor exit node, unexpected country
Message-ID: Unique message identifier Search pivot for finding all recipients
X-Mailer: Email client used Bulk mailer, Python script, unfamiliar tools
Date: When email was sent Timezone mismatch with claimed sender location
2.3
Check Email Authentication Results
Look for the Authentication-Results header:
CheckPass MeansFail MeansInvestigation Action
SPF Email came from authorized IP for domain Sender IP not authorized (possible spoofing) If fail: likely spoofed domain
DKIM Email content was not modified in transit Content was altered or no DKIM signature If fail: may be forwarded or tampered
DMARC Email passes domain's authentication policy Email failed domain owner's requirements If fail: high confidence spoofing
Important Nuance

All Pass ≠ Legitimate: Attackers can set up their own domains with valid SPF/DKIM/DMARC. A "pass" from micros0ft-support.com doesn't make it legitimate—it just means the attacker configured their malicious domain properly.

2.4
Investigate Sender Domain
Research the sender's domain:
  • WHOIS Lookup - When was domain registered? (Recent = suspicious)
  • Domain Age - Less than 30 days is high risk
  • Registrar - Some registrars are abuse-friendly
  • MX Records - Where does the domain receive email?
  • Website - Does the domain have a legitimate website?
  • Lookalike Check - Is it impersonating a known brand?
🔧 WHOIS Commands
# Command line WHOIS
whois suspicious-domain.com

# Check domain age and registration
whois suspicious-domain.com | grep -i "creation\|registered"

# DNS records
dig suspicious-domain.com MX
dig suspicious-domain.com A
dig suspicious-domain.com TXT

Step 3: IOC Extraction (10 Minutes)

Extract all indicators of compromise for blocking, searching, and threat intelligence sharing.

3.1
Extract All URLs
Find all links in the email body and headers:
  • Visible hyperlinks in email body
  • Hidden links (hover to reveal actual URL)
  • Links in attachments (if safe to open in sandbox)
  • Shortened URLs (unshorten before analysis)
  • QR codes (scan in sandbox environment)
URL Defanging

Always defang URLs before sharing in tickets or chat: hxxps://malicious[.]com/path. This prevents accidental clicks.

URL Analysis Checklist

CheckToolRed Flags
VirusTotal scanvirustotal.comAny detections
URLScan renderurlscan.ioLogin form, redirect chain
Domain agewhois<30 days old
SSL certificateBrowser/SSLLabsFree cert, mismatched domain
Redirect chainwheregoes.comMultiple redirects
Known phishingPhishTankListed as phishing
3.2
Extract Domains and IPs
Identify all domains and IP addresses:
  • Sender domain - From the email address
  • Reply-to domain - If different from sender
  • Link domains - All unique domains in URLs
  • Originating IP - From email headers
  • Link target IPs - Resolve domains to IPs
3.3
Extract File Hashes (If Attachments)
For any attachments, calculate hashes:

NEVER open suspicious attachments on your workstation! Use a sandbox (Hybrid Analysis, ANY.RUN) or isolated VM.

Step 4: Scope Determination (10 Minutes)

Identify all users who received this email to understand the full scope of the attack.

4.1
Search for All Recipients
Use multiple search criteria to find all affected users:

Search by Sender (KQL - Microsoft Sentinel)

Sentinel
// Find all recipients of email from specific sender
EmailEvents
| where TimeGenerated > ago(7d)
| where SenderFromAddress =~ "attacker@suspicious-domain.com"
| project 
    TimeGenerated,
    NetworkMessageId,
    SenderFromAddress,
    SenderDisplayName,
    RecipientEmailAddress,
    Subject,
    DeliveryAction,
    DeliveryLocation,
    ThreatTypes,
    ThreatNames
| summarize 
    Recipients = make_set(RecipientEmailAddress),
    TotalCount = count(),
    FirstSeen = min(TimeGenerated),
    LastSeen = max(TimeGenerated)
    by Subject, SenderFromAddress

Search by Subject Line (KQL)

Sentinel
// Find all emails with matching subject
EmailEvents
| where TimeGenerated > ago(7d)
| where Subject contains "Urgent: Verify Your Account"
| summarize 
    Recipients = make_set(RecipientEmailAddress),
    Senders = make_set(SenderFromAddress),
    Count = count()
| extend RecipientCount = array_length(Recipients)

Search by URL in Email (KQL)

Sentinel
// Find all emails containing specific URL
EmailUrlInfo
| where TimeGenerated > ago(7d)
| where Url contains "suspicious-domain.com"
| join kind=inner (
    EmailEvents
    | where TimeGenerated > ago(7d)
) on NetworkMessageId
| project TimeGenerated, RecipientEmailAddress, SenderFromAddress, Subject, Url
| summarize Recipients = make_set(RecipientEmailAddress) by Url

Search by Sender (SPL - Splunk)

Splunk
index=email sourcetype="ms:o365:message" earliest=-7d
    SenderFromAddress="attacker@suspicious-domain.com"
| stats 
    values(RecipientEmailAddress) as Recipients
    count as TotalEmails
    earliest(_time) as FirstSeen
    latest(_time) as LastSeen
    by Subject SenderFromAddress
| eval RecipientCount=mvcount(Recipients)
| convert ctime(FirstSeen) ctime(LastSeen)

Check Delivery Status
Determine where emails were delivered:

Delivered to InboxEmail reached user's inboxCheck for user interaction, consider removal
Delivered to JunkEmail went to spam folderLower risk, but user may still access
QuarantinedEmail held by securityNo user access, review and delete

// Check delivery status for all recipients
EmailEvents

| summarize

Step 5: User Interaction Analysis (15 Minutes)

This is the critical step - determine if any users actually interacted with the phishing email.

5.1
Check for URL Clicks
Determine if anyone clicked links in the email:

SafeLinks Click Events (KQL)

Sentinel
// Find all clicks on phishing URL
UrlClickEvents
| where TimeGenerated > ago(7d)
| where Url contains "suspicious-domain.com"
| project 
    TimeGenerated,
    AccountUpn,
    Url,
    ActionType,
    IsClickedThrough,  // TRUE = user proceeded despite warning
    UrlChain,
    IPAddress,
    NetworkMessageId
| order by TimeGenerated desc

Understanding Click Results

ActionTypeIsClickedThroughMeaningRisk
ClickBlockedFalseUser clicked, SafeLinks blockedLow
ClickBlockedTrueUser clicked through warningHigh - investigate further
ClickAllowedTrueClick allowed (URL not blocked)Medium - check if credential page
NoneN/ANo SafeLinks protectionUnknown - check proxy logs

Web Proxy Logs (If SafeLinks Not Available)

Splunk - Proxy Logs
index=proxy sourcetype="bluecoat:proxysg:access:syslog"
    earliest=-7d
    (url="*suspicious-domain.com*" OR dest_host="suspicious-domain.com")
| stats 
    count as Visits
    values(url) as URLs
    earliest(_time) as FirstVisit
    latest(_time) as LastVisit
    by src_user src_ip
| convert ctime(FirstVisit) ctime(LastVisit)
5.2
Check for Attachment Opens
If the email had attachments, check for execution:

File Download/Open Events (KQL)

Sentinel
// Check for attachment file activity
let AttachmentName = "Invoice_12345.xlsx";
let AttachmentHash = "abc123def456...";  // SHA256 if known
DeviceFileEvents
| where TimeGenerated > ago(7d)
| where FileName contains AttachmentName
    or SHA256 == AttachmentHash
| project 
    TimeGenerated,
    DeviceName,
    AccountName,
    ActionType,  // FileCreated, FileModified, FileRenamed
    FileName,
    FolderPath,
    SHA256,
    InitiatingProcessFileName

Process Execution from Email Attachment

Sentinel
// Check for processes spawned from Office applications
DeviceProcessEvents
| where TimeGenerated > ago(7d)
| where InitiatingProcessFileName in~ ("outlook.exe", "winword.exe", "excel.exe", "powerpnt.exe")
| where FileName in~ ("powershell.exe", "cmd.exe", "wscript.exe", "cscript.exe", "mshta.exe", "rundll32.exe")
| project 
    TimeGenerated,
    DeviceName,
    AccountName,
    InitiatingProcessFileName,
    FileName,
    ProcessCommandLine
| order by TimeGenerated desc
5.3
Contact Users Who Interacted
For users who clicked or opened attachments:
User Interview Questions
  1. Did you click any links in the email?
  2. Did a webpage load? What did it look like?
  3. Did you enter any information (username, password, etc.)?
  4. Did you open any attachments?
  5. Did anything unusual happen after (slow computer, pop-ups, errors)?
  6. Did you download any files?
  7. Did you forward the email to anyone else?

Step 6: Credential Compromise Check (15 Minutes)

If this was a credential harvesting phish and users clicked, check for signs of credential theft and use.

6.1
Check for Suspicious Sign-ins After Click
Look for authentication from unexpected sources after the click time:
Sentinel
// Sign-ins for user after potential credential theft
let ClickTime = datetime(2025-01-02T10:30:00Z);
let AffectedUser = "user@company.com";
SigninLogs
| where TimeGenerated between (ClickTime .. (ClickTime + 72h))
| where UserPrincipalName =~ AffectedUser
| project 
    TimeGenerated,
    UserPrincipalName,
    AppDisplayName,
    IPAddress,
    Location,
    DeviceDetail,
    ResultType,
    ResultDescription,
    RiskState,
    RiskLevelDuringSignIn,
    MfaDetail
| order by TimeGenerated asc

6.2
Check for Inbox Rules (Persistence)
Attackers often create rules to hide their activity:
Sentinel
// Check for new inbox rules created
OfficeActivity
| where TimeGenerated > ago(7d)
| where Operation in ("New-InboxRule", "Set-InboxRule", "Enable-InboxRule")
| where UserId =~ "user@company.com"
| extend RuleDetails = tostring(Parameters)
| project 
    TimeGenerated,
    UserId,
    Operation,
    RuleDetails,
    ClientIP
| order by TimeGenerated desc

Suspicious Inbox Rule Patterns

Rule ActionWhy It's Suspicious
Delete emails with "security" or "password"Hide security notifications
Forward all email to external addressData exfiltration
Move emails to RSS Feeds or hidden folderHide attacker communications
Mark as read and deleteUser won't notice suspicious emails
6.3
Check for OAuth App Consent
Attackers may trick users into granting app permissions:
Sentinel
// Check for OAuth app consent grants
AuditLogs
| where TimeGenerated > ago(7d)
| where OperationName == "Consent to application"
| where InitiatedBy.user.userPrincipalName =~ "user@company.com"
| extend 
    AppName = tostring(TargetResources[0].displayName),
    Permissions = tostring(TargetResources[0].modifiedProperties)
| project TimeGenerated, AppName, Permissions
6.4
Check for Email Forwarding
External forwarding is a major data exfiltration risk:
Sentinel
// Check for mailbox forwarding configuration
OfficeActivity
| where TimeGenerated > ago(7d)
| where Operation in ("Set-Mailbox", "New-TransportRule")
| where Parameters contains "ForwardingSmtpAddress" 
    or Parameters contains "ForwardTo"
    or Parameters contains "RedirectTo"
| project TimeGenerated, UserId, Operation, Parameters

Step 7: Malware Delivery Check (15 Minutes)

If the phishing email contained attachments, check for malware execution.

7.1
Check for Malicious Process Execution
Look for suspicious processes on endpoints that opened attachments:
Sentinel
// Suspicious child processes from Office apps
let Device = "WORKSTATION01";
let StartTime = datetime(2025-01-02T10:30:00Z);
DeviceProcessEvents
| where TimeGenerated between (StartTime .. (StartTime + 24h))
| where DeviceName =~ Device
| where InitiatingProcessFileName in~ (
    "winword.exe", "excel.exe", "powerpnt.exe", "outlook.exe",
    "msedge.exe", "chrome.exe", "firefox.exe"
)
| where FileName in~ (
    "powershell.exe", "cmd.exe", "wscript.exe", "cscript.exe",
    "mshta.exe", "rundll32.exe", "regsvr32.exe", "certutil.exe",
    "bitsadmin.exe", "msiexec.exe"
)
| project 
    TimeGenerated,
    DeviceName,
    AccountName,
    InitiatingProcessFileName,
    FileName,
    ProcessCommandLine,
    FolderPath
7.2
Check for Persistence Mechanisms
Malware often establishes persistence:
Sentinel
// Check for persistence mechanisms
let Device = "WORKSTATION01";
let StartTime = datetime(2025-01-02T10:30:00Z);
DeviceRegistryEvents
| where TimeGenerated between (StartTime .. (StartTime + 24h))
| where DeviceName =~ Device
| where RegistryKey has_any (
    "Run", "RunOnce", "Winlogon", "Userinit",
    "Shell", "AppInit", "Image File Execution"
)
| project TimeGenerated, RegistryKey, RegistryValueName, RegistryValueData, ActionType
7.3
Check for Network Connections
Look for C2 communications or data exfiltration:
Sentinel
// Suspicious outbound connections
let Device = "WORKSTATION01";
let StartTime = datetime(2025-01-02T10:30:00Z);
DeviceNetworkEvents
| where TimeGenerated between (StartTime .. (StartTime + 24h))
| where DeviceName =~ Device
| where ActionType == "ConnectionSuccess"
| where RemoteIPType == "Public"
| summarize 
    Connections = count(),
    DataSent = sum(SentBytes),
    DataReceived = sum(ReceivedBytes),
    Processes = make_set(InitiatingProcessFileName)
    by RemoteIP, RemoteUrl
| order by Connections desc

Decision Tree

Use this flowchart to determine appropriate actions based on your findings:

Q1: Is the email confirmed malicious?

Based on sender analysis, URL/attachment reputation, content analysis

NO → Close as False Positive. Document why it appeared suspicious but was legitimate.
YES → Continue to Q2
Q2: Did any user click links or open attachments?

Check SafeLinks, proxy logs, EDR file events

NO → Remove emails from mailboxes, block IOCs, close as TP-Remediated
YES → Continue to Q3
Q3: Was this credential harvesting or malware delivery?
CREDENTIALS → Go to Q4
MALWARE → Go to Q5
Q4: Did user enter credentials?
NO/UNKNOWN → Reset password as precaution, monitor for 72h, close
YES → Immediately: Reset password, revoke sessions, check for compromise signs. If compromise confirmed → Escalate to IR
Q5: Did malware execute?
NO → EDR blocked execution. Quarantine file, close as TP-Blocked
YES → Immediately: Isolate endpoint, preserve evidence. Escalate to IR for full malware investigation

Common Mistakes to Avoid

Don't Make These Mistakes
  • Opening attachments on your workstation - Always use sandbox
  • Clicking links to "test" them - Use URLScan.io or sandbox browser
  • Only searching by sender - Attackers use multiple addresses; search by subject, URL, hash too
  • Trusting SPF/DKIM/DMARC pass - Attackers can configure these on their own domains
  • Closing after email removal - Always check for user interaction first
  • Not resetting passwords after credential phishing click - Even if unsure creds were entered
  • Forgetting to check inbox rules - Attacker persistence mechanism
  • Not documenting IOCs - Other analysts need these for future reference
  • Waiting to escalate - When in doubt, escalate early

Frequently Asked Questions

Q: The email passed SPF/DKIM/DMARC. Does that mean it's legitimate?

No. Attackers can register their own domains and properly configure email authentication. A "pass" only means the email came from where it claims—it doesn't mean that source is trustworthy. A pass from "micros0ft-support.com" is still malicious.

Q: User says they clicked but didn't enter credentials. Should I still reset their password?

Yes, as a precaution. Users may not realize or remember entering credentials. The credential page may have used browser autofill. Reset the password, revoke sessions, and monitor for 72 hours.

Q: How do I know if MFA would have protected the user?

Modern phishing kits (like EvilGinx) can steal session tokens and bypass MFA. Check if: (1) The phishing page was a real-time proxy, (2) Sign-in logs show MFA was completed on a session you don't recognize, (3) Session tokens were issued to unexpected IPs. MFA helps but isn't a guarantee against sophisticated phishing.

Q: The URL is behind a shortener. How do I analyze it safely?

Use URL unshortening services like CheckShortURL.com, GetLinkInfo.com, or urlscan.io which can follow redirects without exposing you. Never paste shortened URLs directly into your browser.

Q: How long should I monitor after a suspected credential compromise?

Minimum 72 hours of active monitoring. Set up alerts for the affected user's account for: new sign-ins, inbox rule changes, mail forwarding, and OAuth consent. Consider extended monitoring (30 days) for high-value accounts.

Q: Should I block the sender's IP address?

Generally no for email IPs. Attackers use shared infrastructure (cloud providers, email services) and IPs are often short-lived. Block the sender domain instead. Only block IPs if they're clearly dedicated malicious infrastructure and you're blocking at the network level (not email).

Q: What if the phishing email came from an internal compromised account?

This is called "internal spearphishing" (T1534) and is high severity. Immediately: (1) Disable the sending account, (2) Identify all recipients, (3) Trace back how that account was compromised, (4) Escalate to IR as this indicates active attacker presence.
