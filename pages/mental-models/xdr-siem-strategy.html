XDR vs SIEM Detection Strategy

When to use XDR, when to use SIEM, and how to build a complementary detection architecture.

The XDR-First Principle

Let XDR handle what it does best. Don't build SIEM rules for things XDR already detects well. Focus SIEM investment on gaps: management plane, application layer, cross-domain correlation, and third-party integrations.

What XDR Sees Well

DomainXDR CoverageExamples

Identity (Basic)🟡 GoodSign-in anomalies, impossible travel, MFA bypass attempts
Email Threats🟢 ExcellentPhishing, malicious attachments, BEC attempts
Cloud App Access🟡 GoodShadow IT, risky OAuth apps, anomalous access patterns
Network (Endpoint-based)🟡 PartialC2 connections from endpoints, lateral movement

What XDR Misses (SIEM Territory)

DomainXDR CoverageWhy SIEM Needed
Management Plane🔴 WeakXDR doesn't see cloud console actions, IaC changes, CI/CD pipelines
Application Layer🔴 WeakXDR doesn't understand business app logic, API abuse, data exports
Cross-Domain Correlation🔴 WeakIdentity + endpoint + network + app requires SIEM correlation
Network Infrastructure🔴 WeakFirewall, VPN, proxy logs need SIEM for analysis
OT/IoT🔴 WeakNo XDR agent on OT devices, need network-based detection
Compliance/Audit🔴 WeakLong-term retention, audit queries, compliance reporting
Third-Party SaaS🔴 WeakNon-Microsoft SaaS apps need log ingestion to SIEM

The Three Buckets Framework

When migrating or building detections, classify every rule into one of three buckets:

Bucket 1: RETIRE

XDR already detects this → Don't duplicate in SIEM

  • Malware execution
  • Common endpoint behaviors
  • Known attack tools (Mimikatz, Cobalt Strike)
  • Email-based phishing
  • Basic identity anomalies (impossible travel)
  • Ransomware encryption indicators

Action: Retire SIEM rule, ensure XDR alert flows to SIEM for correlation if needed.

Bucket 2: KEEP/REWRITE

SIEM adds value via correlation → Optimize for SIEM

  • Identity + endpoint correlation (sign-in → process execution)
  • VPN + sign-in + privilege changes
  • SaaS admin action + data access spike
  • Multi-stage attack sequences
  • Business context enrichment
  • Cross-tenant correlation

Action: Rewrite with optimal SIEM logic, incorporate XDR signals as inputs.

Bucket 3: BUILD IN SIEM

XDR doesn't cover this → SIEM is the only option

  • Cloud management plane misuse (AWS/Azure/GCP console)
  • Application/API abuse
  • Logging/audit tampering
  • CI/CD pipeline attacks
  • Network infrastructure changes
  • OT/IoT threats
  • Compliance-specific monitoring

Action: Build new detection in SIEM, ensure signals are available.

When to Write SIEM Correlations

Write SIEM correlation when:

  • Multiple asset classes are involved (identity + endpoint + network)
  • Sequence/time/context matters (A then B within X minutes)
  • Actions look legitimate individually but risky in combination
  • Blast radius is high (admin actions, sensitive data)
  • XDR sees only part of the story (endpoint saw it, but not the trigger)
  • Business context is required (HR data vs public data)
The Golden Rule

If misuse can happen without malware, SIEM correlation is usually required.
XDR excels at detecting malicious binaries and known attack tools. It struggles with "living off the land" attacks that use legitimate tools and credentials. That's where SIEM correlation shines.
