Authentication Alert Triage

Rapid triage guide for authentication and sign-in alerts - identify compromised accounts fast.

Why Authentication Triage Matters

The Stakes

Account compromise is the most common attack path. Every authentication alert could be the difference between catching an attacker at the door or letting them in.

Alert TypeIf It's Real...If You Miss It...
Impossible travelAttacker using stolen credsFull account access, data theft, BEC
Password spray successMultiple accounts compromisedLateral movement, mass compromise
MFA fatigue attackUser accidentally approvedAttacker bypasses MFA, full access
Anonymous IP loginAttacker hiding originUntracked malicious access

Rapid Triage Decision Tree

Authentication Alert Triage Flow

Q1: Did the sign-in succeed or fail?

├─ SUCCEEDED → Potential compromise. Continue.

└─ FAILED → Reconnaissance/spray attempt. Check volume.

Q2: Is this a privileged account (admin, exec, service)?

├─ YES → High severity. Immediate verification required.

└─ NO → Standard severity. Continue.

Q3: Can user explain the activity?

├─ YES - traveling, new device → Likely legitimate. Document and close.

├─ NO - wasn't them → Confirmed compromise. Reset credentials immediately.

└─ Can't reach user → Treat as suspicious. Consider temporary disable.

Verification Warning

If account is compromised, the attacker may be reading messages. For high-severity alerts, prefer phone verification over email/chat.

Quick Checks

// KQL - Recent sign-in history for user
SigninLogs
| where TimeGenerated > ago(7d)
| where UserPrincipalName == "user@company.com"
| project TimeGenerated, IPAddress, Location, AppDisplayName, 
    ResultType, RiskLevelDuringSignIn, DeviceDetail
| order by TimeGenerated desc

// KQL - Is this IP used by other users? (VPN indicator)
SigninLogs
| where TimeGenerated > ago(1d)
| where IPAddress == "suspicious-ip"
| summarize Users = make_set(UserPrincipalName), Count = count()

// KQL - What did user do after sign-in?
CloudAppEvents
| where Timestamp > ago(24h)
| where AccountId == "user@company.com"
| project Timestamp, ActionType, Application, ObjectName
| order by Timestamp asc

// KQL - Check for MFA registration changes
AuditLogs
| where TimeGenerated > ago(7d)
| where TargetResources[0].userPrincipalName == "user@company.com"
| where OperationName has_any ("User registered security info", "User deleted security info")
| project TimeGenerated, OperationName, InitiatedBy

What If Scenarios

What If...Then...Rationale
User says they were traveling?Ask where. If matches sign-in location, likely legit. Document.Travel is #1 cause of impossible travel FPs
User can't remember if it was them?Check the app, device, activity. If suspicious, treat as compromise.Err on side of caution
VPN IP but user doesn't use VPN?Personal VPN or proxy. Ask user. Could be policy violation or compromise.VPNs explain many "anomalous" IPs
Password spray with no successes?Block source IP. Check if passwords were close (one character off = targeted).Failed spray may be reconnaissance for later attack
Sign-in from sanctioned country?Should be blocked by CA policy. If not, that's a gap. Investigate origin.May indicate VPN or policy bypass

Escalation Criteria

Escalate to L2 / Incident Immediately When:
  • User confirms sign-in wasn't them
  • Admin or executive account with suspicious sign-in
  • Successful sign-in + MFA registration change
  • Successful sign-in + inbox rule created
  • Password spray with ANY successes
  • Sign-in from known malicious IP (threat intel)
  • Multiple users with similar suspicious sign-ins (campaign)

Can Close at L1 If:

  • User confirms activity (document verification)
  • IP is known corporate VPN
  • Failed sign-in only, account locked as expected
  • Matches documented FP pattern
