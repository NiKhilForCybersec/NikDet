Part 1: Understanding the Problem

Why Do We Need Detection-as-Code?

Let me tell you a story that happens in almost every SOC:

Scenario: The Detection Disaster

Monday 9 AM: Senior analyst Sarah creates a new detection rule for encoded PowerShell. She clicks through the Splunk GUI and saves it.

Wednesday 2 PM: The rule is firing too many alerts. Junior analyst Mike "fixes" it by adding an exclusion in the GUI.

Friday 10 AM: A real attack happens. The rule doesn't fire. Why? Nobody knows what Mike changed.

Next Monday: Sarah tries to figure out what went wrong. There's no history. No documentation. Mike is on vacation.

Result: Hours wasted. Attack missed. Trust in detections damaged.

This happens because of five fundamental problems:

ProblemWhat HappensReal Impact
1. No Version History Changes aren't tracked. No record of who changed what or when. Can't revert bad changes. Can't understand why rules behave differently than before.
2. No Peer Review Anyone can change any rule directly in production. Mistakes go live immediately. No quality control. Junior mistakes affect production.
3. No Testing Rules are only tested when real attacks happen (or don't). Broken rules aren't discovered until it's too late. False negatives go unnoticed.
4. Environment Drift Dev and production have different rules. No single source of truth. Confusion about which version is correct. Rules that work in dev fail in prod.
5. Knowledge Loss Rules exist only in the SIEM. No external documentation. When people leave, knowledge leaves. Team must reverse-engineer existing rules.

What is Detection-as-Code?

Detection-as-Code (DaC) applies software development practices to security detection rules:

Old Way

Create rules in SIEM GUI

No history, no review

Deploy directly to production

→

New Way (DaC)

Write rules as YAML files

Store in Git with full history

Test → Review → Deploy automatically

Part 2: Git Fundamentals (From Zero)

If You Already Know Git

Skip to Part 3. This section is for people who have never used Git before.

What is Git?

Git is a version control system. Think of it like Google Docs' version history, but much more powerful:

  • It tracks every change ever made to your files
  • You can see who made each change and when
  • You can go back to any previous version
  • Multiple people can work on the same files without conflicts

Key Git Concepts Explained

1. Repository (Repo)

What it is: A folder that Git is tracking. Contains your files plus hidden Git data.

Analogy: Like a project folder, but with a time machine built in.

For DaC: Your detection rules repo contains all your YAML rule files.

2. Commit

What it is: A snapshot of your files at a specific moment. Like pressing "Save" but keeping all previous saves.

Analogy: Like taking a photo of your document. You can always go back and look at any photo.

What it includes:

  • The changed files
  • A message describing what changed (you write this)
  • Who made the change
  • When it was made

3. Branch

What it is: A separate line of development. Like making a copy of your folder to experiment with.

Analogy: Imagine you're writing a book. The "main" branch is the published version. You create a "draft" branch to write a new chapter. If the chapter is good, you add it to main. If not, you delete the draft.

For DaC:

  • main branch = Production rules (what's deployed)
  • Feature branches = Rules being developed (not yet deployed)

4. Pull Request (PR) / Merge Request (MR)

What it is: A request to merge your branch into main. Allows others to review before merging.

Why it matters: This is where peer review happens. Other team members can:

  • See exactly what you changed
  • Comment on specific lines
  • Request changes if something is wrong
  • Approve the changes

For DaC: No rule goes to production without being reviewed and approved.

Part 3: YAML Format Explained

Detection rules are written in YAML (YAML Ain't Markup Language). It's designed to be human-readable.

YAML Basics

# YAML BASICS - Everything you need to know

# 1. KEY-VALUE PAIRS
# The most basic structure. Key on left, value on right, colon in between.
name: My Detection Rule
author: John Smith
severity: high
enabled: true

# 2. LISTS (ARRAYS)
# Multiple values under one key. Each item starts with a dash.
tags:
  - attack.execution
  - attack.t1059.001
  - powershell

# You can also write lists on one line:
tags: [attack.execution, attack.t1059.001, powershell]

# 3. NESTED OBJECTS
# Objects inside objects. Use indentation (spaces, NOT tabs!).
logsource:
  category: process_creation
  product: windows

detection:
  selection:
    CommandLine|contains: "-enc"
  condition: selection

# 4. MULTI-LINE STRINGS
# Use | for preserving line breaks:
description: |
  This is line one.
  This is line two.
  All line breaks are preserved.

# Use > for folding into one line (line breaks become spaces):
description: >
  This will all become
  one single line when
  parsed by the computer.

# 5. COMMENTS
# Anything after # is a comment and ignored by the computer.
severity: high  # This is a comment explaining severity

YAML Common Mistakes

YAML Errors That Will Break Your Rules
MistakeWrongCorrect
Using tabs →logsource: (tab character) logsource: (spaces)
Inconsistent indentation Mixing 2 and 4 spaces Always use same number of spaces
Colon in value without quotes description: Error: failed description: "Error: failed"
Special characters without quotes pattern: [suspicious] pattern: "[suspicious]"
Missing space after colon name:My Rule name: My Rule

Part 5: Writing Your First Detection Rule

Step 5.1: Understand the Sigma Rule Format

Sigma is the standard format for detection rules. It's SIEM-agnostic - you write once and convert to any SIEM.

Step 5.2: Complete Sigma Rule Explained

# COMPLETE SIGMA RULE WITH EXPLANATIONS
# File: detections/windows/process_creation/encoded_powershell.yml

title: Encoded PowerShell Command Execution
# ↑ Human-readable name. Be specific but concise.

id: 8e7e3e6d-6a8e-4a5a-9c4e-7f8d9b0c1a2b
# ↑ Unique identifier. Generate with: uuidgen (Linux/Mac) or online UUID generator
#   Never reuse IDs. Never change IDs after creation.

status: production
# ↑ Options: experimental → test → production (lifecycle stages)

description: |
    Detects execution of PowerShell with encoded (Base64) commands.
    Attackers frequently use encoding to obfuscate malicious commands
    and evade simple string-based detection.
# ↑ Explain: What does this detect? Why is it suspicious? 

author: Your Name
# ↑ Your name or team name

date: 2025/01/02
# ↑ When rule was created (YYYY/MM/DD)

modified: 2025/01/02
# ↑ When rule was last changed

references:
    - https://attack.mitre.org/techniques/T1059/001/
    - https://attack.mitre.org/techniques/T1027/
# ↑ Links to documentation, threat intel, attack references

tags:
    - attack.execution
    - attack.t1059.001
    - attack.defense_evasion
    - attack.t1027
# ↑ MITRE ATT&CK mappings. Format: attack.tactic or attack.technique_id

logsource:
    category: process_creation
    product: windows
# ↑ What type of log does this rule apply to?
#   category: process_creation, file_event, registry_event, network_connection, etc.
#   product: windows, linux, azure, aws, etc.

detection:
    selection_process:
        Image|endswith:
            - '\powershell.exe'
            - '\pwsh.exe'
    # ↑ First condition: Process must be PowerShell
    #   Image|endswith means "the Image field ends with"

    selection_encoded:
        CommandLine|contains:
            - ' -enc '
            - ' -encoded '
            - ' -e '
            - ' -ec '
            - ' -encodedcommand '
    # ↑ Second condition: Command line contains encoding flags
    #   CommandLine|contains means "CommandLine field contains any of these"

    filter_known_good:
        CommandLine|contains:
            - 'SomeKnownGoodScript.ps1'
            - 'C:\\Program Files\\LegitApp\\'
    # ↑ Known false positives to exclude

    condition: selection_process and selection_encoded and not filter_known_good
# ↑ Logic: Match PowerShell AND encoded flag AND not a known good
#   Operators: and, or, not, 1 of selection*, all of selection*

falsepositives:
    - Legitimate administrative scripts using encoding
    - SCCM/Intune deployments
    - Some backup software
# ↑ Document expected false positives for analysts

level: medium
# ↑ Severity: informational, low, medium, high, critical

Step 5.3: Sigma Detection Logic Reference

ModifierMeaningExample
contains Field contains the value anywhere CommandLine|contains: 'mimikatz'
startswith Field starts with the value Image|startswith: 'C:\Windows\Temp\'
endswith Field ends with the value Image|endswith: '\cmd.exe'
re Regular expression match CommandLine|re: '.*\s-e[nc]\s.*'
base64offset Match Base64 encoded strings CommandLine|base64offset: 'http'
all All values must match CommandLine|all|contains: ['wget', 'http']

Step 5.4: Condition Logic

# Simple: All conditions in one selection
condition: selection

# AND: Both must match
condition: selection_process and selection_commandline

# OR: Either matches
condition: selection_method1 or selection_method2

# NOT: Exclude matches
condition: selection and not filter

# Combined
condition: (selection_process and selection_encoded) and not filter_known_good

# Match any of multiple selections
condition: 1 of selection_*

# Match all selections
condition: all of selection_*

# Match at least 2 of selections
condition: 2 of selection_*

Part 6: Testing Your Detection Rules

Why Testing Matters

Without testing, you don't know if your rule:

  • Actually detects the attack (false negative risk)
  • Fires on legitimate activity (false positive risk)
  • Has valid syntax (deployment will fail)
  • Works after SIEM conversion

Step 6.4: Test Against Sample Logs

Create test cases with known-good and known-bad log samples:

# File: tests/windows/encoded_powershell_test.yml

rule: detections/windows/process_creation/encoded_powershell.yml

should_match:
  - name: "Basic encoded command"
    log:
      Image: 'C:\Windows\System32\WindowsPowerShell\v1.0\powershell.exe'
      CommandLine: 'powershell.exe -enc SGVsbG8gV29ybGQ='
      ParentImage: 'C:\Windows\System32\cmd.exe'
    
  - name: "Encoded with other flags"
    log:
      Image: 'C:\Windows\System32\WindowsPowerShell\v1.0\powershell.exe'
      CommandLine: 'powershell.exe -NoProfile -WindowStyle Hidden -encodedcommand SGVsbG8='
      ParentImage: 'C:\Windows\explorer.exe'

  - name: "PowerShell Core (pwsh)"
    log:
      Image: 'C:\Program Files\PowerShell\7\pwsh.exe'
      CommandLine: 'pwsh.exe -e SGVsbG8gV29ybGQ='
      ParentImage: 'C:\Windows\System32\cmd.exe'

should_not_match:
  - name: "Normal PowerShell without encoding"
    log:
      Image: 'C:\Windows\System32\WindowsPowerShell\v1.0\powershell.exe'
      CommandLine: 'powershell.exe -ExecutionPolicy Bypass -File script.ps1'
      ParentImage: 'C:\Windows\System32\cmd.exe'

  - name: "Different process entirely"
    log:
      Image: 'C:\Windows\System32\cmd.exe'
      CommandLine: 'cmd.exe /c echo hello'
      ParentImage: 'C:\Windows\explorer.exe'

  - name: "Known good exclusion"
    log:
      Image: 'C:\Windows\System32\WindowsPowerShell\v1.0\powershell.exe'
      CommandLine: 'powershell.exe -enc SGVsbG8= C:\Program Files\LegitApp\script.ps1'

Part 7: Automated Testing with GitHub Actions

GitHub Actions runs tests automatically when you push code. Here's a complete working pipeline:

Step 7.1: Create the Workflow File

# File: .github/workflows/test-and-deploy.yml

name: Test and Deploy Detection Rules

# When does this pipeline run?
on:
  push:
    branches: [ main ]                    # Run on push to main
    paths:
      - 'detections/**'                   # Only if detection files changed
  pull_request:
    branches: [ main ]                    # Run on PRs to main
    paths:
      - 'detections/**'

jobs:
  validate:
    name: Validate Sigma Rules
    runs-on: ubuntu-latest
    
    steps:
      # Step 1: Download the code
      - name: Checkout repository
        uses: actions/checkout@v4

      # Step 2: Set up Python
      - name: Set up Python
        uses: actions/setup-python@v4
        with:
          python-version: '3.11'

      # Step 3: Install Sigma tools
      - name: Install dependencies
        run: |
          pip install sigma-cli
          pip install pysigma
          pip install pysigma-backend-splunk
          pip install pysigma-backend-microsoft365defender

      # Step 4: Validate all rules
      - name: Validate Sigma rules
        run: |
          echo "Validating all Sigma rules..."
          sigma check detections/ --fail-on-error
          echo "✓ All rules are valid!"

      # Step 5: Test conversion to Splunk
      - name: Test Splunk conversion
        run: |
          echo "Testing conversion to Splunk SPL..."
          for rule in $(find detections -name "*.yml"); do
            echo "Converting: $rule"
            sigma convert -t splunk "$rule" > /dev/null
          done
          echo "✓ All rules convert to Splunk successfully!"

      # Step 6: Test conversion to Sentinel
      - name: Test Sentinel conversion
        run: |
          echo "Testing conversion to Microsoft Sentinel..."
          for rule in $(find detections -name "*.yml"); do
            echo "Converting: $rule"
            sigma convert -t microsoft365defender "$rule" > /dev/null
          done
          echo "✓ All rules convert to Sentinel successfully!"

  deploy:
    name: Deploy to SIEM
    needs: validate                       # Only runs if validate passes
    if: github.ref == 'refs/heads/main' && github.event_name == 'push'  # Only on main push
    runs-on: ubuntu-latest
    
    steps:
      - name: Checkout repository
        uses: actions/checkout@v4

      - name: Set up Python
        uses: actions/setup-python@v4
        with:
          python-version: '3.11'

      - name: Install dependencies
        run: |
          pip install sigma-cli pysigma pysigma-backend-splunk

      # Convert and deploy to Splunk (example)
      - name: Convert rules to Splunk
        run: |
          mkdir -p output/splunk
          for rule in $(find detections -name "*.yml"); do
            rulename=$(basename "$rule" .yml)
            sigma convert -t splunk "$rule" > "output/splunk/${rulename}.spl"
          done

      # Add your SIEM deployment script here
      - name: Deploy to Splunk
        env:
          SPLUNK_URL: ${{ secrets.SPLUNK_URL }}
          SPLUNK_TOKEN: ${{ secrets.SPLUNK_TOKEN }}
        run: |
          echo "Deploying to Splunk..."
          # python scripts/deploy_to_splunk.py output/splunk/
          echo "✓ Deployment complete!"

Part 8: Deploying to Your SIEM

Option A: Splunk Deployment Script

# File: scripts/deploy_to_splunk.py
#!/usr/bin/env python3
"""
Deploy Sigma rules to Splunk as saved searches.
"""

import os
import sys
import requests
import subprocess
from pathlib import Path

# Configuration from environment variables
SPLUNK_URL = os.environ.get('SPLUNK_URL', 'https://splunk.company.com:8089')
SPLUNK_TOKEN = os.environ.get('SPLUNK_TOKEN')
SPLUNK_APP = os.environ.get('SPLUNK_APP', 'search')

def convert_to_splunk(sigma_file: Path) -> str:
    """Convert a Sigma rule to Splunk SPL."""
    result = subprocess.run(
        ['sigma', 'convert', '-t', 'splunk', str(sigma_file)],
        capture_output=True, text=True
    )
    if result.returncode != 0:
        raise Exception(f"Conversion failed: {result.stderr}")
    return result.stdout.strip()

def deploy_saved_search(name: str, search: str, description: str = ""):
    """Deploy a saved search to Splunk."""
    url = f"{SPLUNK_URL}/servicesNS/nobody/{SPLUNK_APP}/saved/searches"
    
    payload = {
        'name': name,
        'search': search,
        'description': description,
        'is_scheduled': 1,
        'cron_schedule': '*/15 * * * *',  # Every 15 minutes
        'alert_type': 'number of events',
        'alert_comparator': 'greater than',
        'alert_threshold': 0,
        'actions': 'notable',  # Enterprise Security notable event
    }
    
    headers = {'Authorization': f'Bearer {SPLUNK_TOKEN}'}
    
    response = requests.post(url, data=payload, headers=headers, verify=False)
    
    if response.status_code in [200, 201]:
        print(f"✓ Deployed: {name}")
    elif response.status_code == 409:  # Already exists, update it
        update_url = f"{url}/{name}"
        response = requests.post(update_url, data=payload, headers=headers, verify=False)
        if response.status_code == 200:
            print(f"✓ Updated: {name}")
        else:
            print(f"✗ Failed to update {name}: {response.text}")
    else:
        print(f"✗ Failed to deploy {name}: {response.text}")

def main():
    if not SPLUNK_TOKEN:
        print("Error: SPLUNK_TOKEN environment variable not set")
        sys.exit(1)
    
    detections_dir = Path('detections')
    
    for sigma_file in detections_dir.rglob('*.yml'):
        try:
            print(f"Processing: {sigma_file}")
            spl_query = convert_to_splunk(sigma_file)
            rule_name = f"DaC_{sigma_file.stem}"
            deploy_saved_search(rule_name, spl_query)
        except Exception as e:
            print(f"✗ Error processing {sigma_file}: {e}")

if __name__ == '__main__':
    main()

# File: scripts/deploy_to_sentinel.py
#!/usr/bin/env python3
"""
Deploy Sigma rules to Microsoft Sentinel as Analytics Rules.
"""

import os
import subprocess
from pathlib import Path
from azure.identity import DefaultAzureCredential
from azure.mgmt.securityinsight import SecurityInsights

# Configuration
SUBSCRIPTION_ID = os.environ.get('AZURE_SUBSCRIPTION_ID')
RESOURCE_GROUP = os.environ.get('AZURE_RESOURCE_GROUP')
WORKSPACE_NAME = os.environ.get('AZURE_WORKSPACE_NAME')

def convert_to_kql(sigma_file: Path) -> str:
    """Convert Sigma rule to KQL."""
    result = subprocess.run(
        ['sigma', 'convert', '-t', 'microsoft365defender', str(sigma_file)],
        capture_output=True, text=True
    )
    if result.returncode != 0:
        raise Exception(f"Conversion failed: {result.stderr}")
    return result.stdout.strip()

def deploy_analytics_rule(client, rule_id: str, kql_query: str, 
                          display_name: str, description: str, severity: str):
    """Deploy an analytics rule to Sentinel."""
    
    rule_params = {
        'kind': 'Scheduled',
        'properties': {
            'displayName': display_name,
            'description': description,
            'severity': severity.capitalize(),
            'enabled': True,
            'query': kql_query,
            'queryFrequency': 'PT15M',      # Every 15 minutes
            'queryPeriod': 'PT15M',
            'triggerOperator': 'GreaterThan',
            'triggerThreshold': 0,
            'suppressionDuration': 'PT1H',
            'suppressionEnabled': False,
            'tactics': [],  # Add based on Sigma tags
        }
    }
    
    try:
        client.alert_rules.create_or_update(
            resource_group_name=RESOURCE_GROUP,
            workspace_name=WORKSPACE_NAME,
            rule_id=rule_id,
            alert_rule=rule_params
        )
        print(f"✓ Deployed: {display_name}")
    except Exception as e:
        print(f"✗ Failed: {display_name} - {e}")

def main():
    credential = DefaultAzureCredential()
    client = SecurityInsights(credential, SUBSCRIPTION_ID)
    
    detections_dir = Path('detections')
    
    for sigma_file in detections_dir.rglob('*.yml'):
        try:
            print(f"Processing: {sigma_file}")
            kql_query = convert_to_kql(sigma_file)
            rule_id = sigma_file.stem
            deploy_analytics_rule(
                client, rule_id, kql_query,
                display_name=f"[DaC] {rule_id}",
                description="Deployed via Detection-as-Code",
                severity="Medium"
            )
        except Exception as e:
            print(f"✗ Error: {sigma_file} - {e}")

if __name__ == '__main__':
    main()
