Investigation Decision Framework

Initial Triage Decision Tree

First 5 Minutes - What to Do

Q1: Did the user interact with the phishing email?

├─ NO (reported only) → Lower priority. Analyze email, check other recipients, block sender.

└─ YES (clicked/opened) → Continue to Q2

Q2: What type of interaction?

├─ Clicked link only → Check URL reputation. If credential harvesting, go to Q3.

├─ Opened attachment → ISOLATE ENDPOINT NOW. Check EDR for execution.

└─ Entered credentials → RESET PASSWORD + REVOKE SESSIONS NOW.

Q3: Did the user enter credentials on the phishing site?

├─ NO / Don't know → Check sign-in logs for anomalies anyway

├─ YES → Immediate credential reset, session revocation, MFA re-enrollment

└─ YES + MFA token → Assume full compromise, check for persistence

Step 2: Check User Actions

// KQL - Did user click the link?
UrlClickEvents
| where Timestamp > ago(24h)
| where AccountUpn == "user@company.com"
| where Url contains "suspicious-domain.com"
| project Timestamp, AccountUpn, Url, ActionType, IsClickedThrough, ThreatTypes

// KQL - Sign-in activity after potential credential theft
SigninLogs
| where TimeGenerated > ago(24h)
| where UserPrincipalName == "user@company.com"
| project TimeGenerated, UserPrincipalName, IPAddress, Location, AppDisplayName, 
    ResultType, ResultDescription, DeviceDetail, RiskLevelDuringSignIn
| order by TimeGenerated desc

// KQL - Look for anomalous sign-ins (new location, device, app)
SigninLogs
| where TimeGenerated > ago(7d)
| where UserPrincipalName == "user@company.com"
| summarize 
    Locations = make_set(Location),
    IPs = make_set(IPAddress),
    Apps = make_set(AppDisplayName),
    Devices = make_set(DeviceDetail.displayName)
    by bin(TimeGenerated, 1d)

// KQL - Check for inbox rule creation (persistence indicator)
CloudAppEvents
| where Timestamp > ago(7d)
| where AccountId == "user@company.com"
| where ActionType in ("New-InboxRule", "Set-InboxRule", "UpdateInboxRules")
| project Timestamp, ActionType, RawEventData

Step 3: Identify Campaign Scope

// KQL - Find all recipients of phishing email
EmailEvents
| where Timestamp > ago(7d)
| where SenderFromAddress == "attacker@malicious-domain.com"
    or Subject contains "Urgent: Your account"  // Use actual subject
    or SenderMailFromDomain == "malicious-domain.com"
| summarize 
    Recipients = make_set(RecipientEmailAddress),
    TotalCount = count(),
    DeliveredCount = countif(DeliveryAction == "Delivered"),
    BlockedCount = countif(DeliveryAction == "Blocked")
| extend RecipientList = Recipients

// KQL - Who clicked across the campaign?
UrlClickEvents
| where Timestamp > ago(7d)
| where Url contains "malicious-domain.com"
| summarize ClickedUsers = make_set(AccountUpn), ClickCount = count() by Url

What If Scenarios

What If...Then...Rationale
User says they didn't enter credentials but sign-in logs show new location?Treat as compromised. User may not remember or be embarrassed.Users often underreport. Trust the logs.
Phishing site is already down?Still investigate. Check URL archives, analyze email headers, assume worst case.Attacker may have already harvested credentials.
User has MFA, should I still worry?Yes. Modern phishing can capture MFA tokens in real-time (AitM attacks).Check for MFA-bypassing OAuth consent or session token theft.
EDR shows no malware execution?Good sign, but check for credential theft via web form instead.Not all phishing delivers malware - credential theft is more common.
Same phishing campaign hits us next week?Block more indicators, improve detection, train targeted users.Attackers iterate. Your defenses should too.
Executive was targeted specifically?Escalate to CISO. Check if part of larger campaign. Enhanced monitoring.Executive targeting often means reconnaissance was done.
User clicked but closed page immediately?Still check sign-in logs. Page may have captured session before visible form.Some phishing is instantaneous (redirect attacks).

"It Depends" Scenarios

QuestionIt Depends On...If Yes...If No...
Should I reset the user's password? Did they enter credentials? Any suspicious sign-ins? Yes - reset immediately, revoke sessions, re-enroll MFA Maybe - if only clicked link but no credential entry, monitor closely
Should I isolate the endpoint? Did they open an attachment? Does EDR show execution? Yes - isolate immediately, investigate further No - if only clicked link leading to credential page
Should I notify all recipients? How many received it? Was it blocked for most? Yes if >10 recipients got delivered email No if blocked for all or only 1-2 recipients
Should I block the sender domain? Is it a legitimate domain being spoofed or attacker-controlled? Yes if attacker-controlled domain No - if spoofed legitimate domain, fix DMARC instead
Should I escalate to incident? Evidence of actual compromise? Executive targeted? Multiple victims? Yes - formal incident, involve IR team No - standard investigation, document and close

Escalation Criteria

Escalate to Incident Response When:

  • Confirmed credential compromise with suspicious sign-in activity
  • Malware executed on endpoint
  • Evidence of lateral movement or persistence
  • Executive or privileged user targeted
  • Data exfiltration indicators (forwarding rules, OAuth apps)
  • Multiple users compromised from same campaign
  • BEC activity detected (internal phishing, wire fraud attempt)

Escalate to Management When:

  • Executive targeted even if not compromised
  • Large-scale campaign (50+ recipients)
  • Targeted attack (spear phishing with internal information)
  • Same campaign recurring despite controls

Interview-Ready Answer

"Walk me through how you investigate a phishing incident"

My Answer:

"When I receive a phishing alert or user report, I follow a structured approach that I think of in three phases: Triage, Scope, and Contain.

Phase 1 - Quick Triage (first 5 minutes):
First, I determine the severity by asking one critical question: Did anyone enter credentials? If yes, that's my top priority - I'll immediately reset their password and revoke active sessions before anything else. If they just clicked a link, it's still urgent but gives me slightly more time. If they only reported it without clicking, I can be more methodical.

Phase 2 - Scope the Campaign (next 10-15 minutes):
I never assume it's a single email. I search our email logs for the sender address, subject line, and any URLs or attachment hashes to find all recipients. In Microsoft 365, I use Threat Explorer; in Splunk, I'd search the email sourcetype. This tells me if it's a targeted attack against one person or a broader campaign hitting dozens of users.

Phase 3 - Investigate and Contain:
For anyone who clicked, I check three things: First, endpoint telemetry - did anything download or execute? I'm looking for suspicious processes spawning from the browser. Second, authentication logs - any logins from unusual locations or new devices after the click? Third, email rules - attackers love creating inbox rules to hide their tracks.

For containment, I purge the email from all mailboxes - not just delete, but hard delete so users can't recover it from trash. I block the sender domain and any malicious URLs at the proxy or email gateway. If credentials were compromised, I also check for any changes they might have made - like MFA modifications or app consent grants.

Closing the Loop:
Finally, I document everything including IOCs for threat intel, notify affected users, and if it was a sophisticated attack, I'll work with the team to improve our detection rules - maybe adding the sender domain patterns or URL characteristics to our detection logic."

💡 Pro Tips for Interview:
  • Mention specific tools you've used (Defender, Proofpoint, Splunk, etc.)
  • Show you understand the urgency hierarchy (credentials > clicked > reported)
  • Demonstrate you think about campaign scope, not just individual emails
  • Emphasize the "credential compromise = immediate action" mindset
