Detection Lifecycle

A systematic approach to creating, testing, deploying, and maintaining security detections.

The Detection Lifecycle

Effective detection engineering follows a structured lifecycle to ensure high-quality, maintainable detections:

1. Research

Understand the threat before building a detection.

Inputs

  • Threat intelligence reports
  • MITRE ATT&CK technique documentation
  • Incident post-mortems (what did we miss?)
  • Vulnerability disclosures
  • Red team findings
  • Gap analysis results

Research Questions

QuestionWhy It Matters
What is the attack technique?Understanding the "what"
How is it executed technically?Specific artifacts to detect
What data sources capture it?Feasibility check
Who uses this technique?Threat relevance
What are legitimate uses?False positive assessment

Detection Research Document

Technique: T1059.001 - PowerShell
Description: Adversaries use PowerShell to execute commands and scripts
Data Sources: Process creation (4688), Script Block Logging (4104), Module Logging
Legitimate Use: Admin scripts, SCCM, management tools
Malicious Indicators: Encoded commands, download cradles, bypass flags
Priority: High (commonly used, good detection fidelity)

2. Design

Plan the detection logic before writing code.

Detection Strategy

ApproachProsConsUse When
Signature-based Low FP, fast, precise Easy to evade, brittle Known IOCs, specific tools
Behavior-based Catches variants, harder to evade More FPs, complex TTPs, technique patterns
Anomaly-based Catches unknown threats High FP, needs baseline Rare activities, deviations
Correlation High confidence from multiple signals Complex, slower Attack chains, multi-stage

Design Document Template

Detection Design: Encoded PowerShell Execution

ATT&CK ID: T1059.001, T1027
Objective: Detect PowerShell commands using Base64 encoding
Data Source: DeviceProcessEvents (MDE)
Logic:
- Process = powershell.exe OR pwsh.exe
- CommandLine contains -enc, -encoded, -e followed by base64
- Exclude known admin scripts by hash
Expected FP Rate: Medium (will need tuning)
Severity: Medium (adjust to High if decoded content is suspicious)
Response: Triage playbook PB-TRI-005

3. Implement

Write the detection query/rule.

Implementation Best Practices

  • Start broad, then narrow: Get the basic logic working first
  • Comment your code: Explain the "why" not just "what"
  • Use variables: Make thresholds easy to adjust
  • Consider performance: Time filters first, expensive operations last
  • Include metadata: ATT&CK mapping, author, version

Example Implementation

KQL Detection Rule
// Detection: Encoded PowerShell Execution
// ATT&CK: T1059.001, T1027
// Author: Security Team
// Version: 1.0
// Last Updated: 2025-01-01

let EncodingFlags = dynamic(["-enc", "-encoded", "-e ", "-encodedcommand"]);
let ExcludedHashes = dynamic(["abc123...", "def456..."]); // Known good scripts

DeviceProcessEvents
| where TimeGenerated > ago(1h)
| where FileName in~ ("powershell.exe", "pwsh.exe")
| where ProcessCommandLine has_any (EncodingFlags)
| where not(SHA256 in (ExcludedHashes))
| extend DecodedCommand = base64_decode_tostring(
    extract(@"-e[ncodedcommand]*\s+([A-Za-z0-9+/=]+)", 1, ProcessCommandLine))
| project 
    TimeGenerated,
    DeviceName,
    AccountName,
    ProcessCommandLine,
    DecodedCommand,
    InitiatingProcessFileName,
    SHA256

4. Test

Validate the detection works and doesn't create excessive noise.

Testing Types

Test TypePurposeHow
True Positive Test Does it catch the attack? Run atomic test, verify alert fires
False Positive Test Does it fire on legitimate activity? Run against historical data, review hits
Evasion Test Can it be bypassed? Try variations of the technique
Performance Test Does it run efficiently? Check query execution time

Atomic Red Team Testing

# Test T1059.001 - Encoded PowerShell
Invoke-AtomicTest T1059.001 -TestNumbers 1

# Verify detection fired
# Check SIEM for alert within 5 minutes

5. Deploy

Move to production with appropriate controls.

Deployment Checklist

  • ☐ Detection tested and validated
  • ☐ Runbook/playbook created
  • ☐ ATT&CK mapping documented
  • ☐ Severity level appropriate
  • ☐ Initial exclusions configured
  • ☐ Alert routing configured
  • ☐ Peer review completed
  • ☐ Change ticket submitted

Phased Rollout

  1. Monitor Mode (1-2 weeks): Rule fires but doesn't alert, gather data
  2. Low Severity (1 week): Alerts at informational level
  3. Production: Full severity with automated response if applicable

6. Maintain

Detections require ongoing care and feeding.

Maintenance Activities

ActivityFrequencyPurpose
FP ReviewWeeklyAdd exclusions, reduce noise
Coverage ValidationMonthlyRetest with atomic tests
ATT&CK Update ReviewQuarterlyAlign with framework updates
Performance CheckMonthlyEnsure query efficiency
Relevance ReviewAnnuallyIs this detection still needed?

Detection Health Metrics

  • Alert Volume: Is it generating too many/few alerts?
  • TP Rate: What % of alerts are actionable?
  • Time Since Last TP: Is it still catching real threats?
  • Query Performance: Is it still running efficiently?
