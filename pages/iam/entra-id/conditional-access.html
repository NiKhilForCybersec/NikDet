Conditional Access Deep Dive

Complete guide to Conditional Access policies - the cornerstone of Zero Trust security in Microsoft Entra ID.

What is Conditional Access?

Simple: "If-then" statements for authentication.

IF a user matches certain conditions (who, where, what device, what app)
THEN apply these requirements (MFA, block, allow, require compliant device)

Example: IF user is accessing email FROM outside the corporate network THEN require MFA.

Policy Components

Assignments (WHO and WHAT)

AssignmentOptionsNotes
Users and groups All users, specific users, groups, directory roles, guests Can include AND exclude
Cloud apps or actions All apps, specific apps, user actions (register security info) Can target specific SaaS apps
Conditions Device platforms, locations, client apps, device state, filters Fine-tune when policy applies

Conditions (WHEN)

ConditionOptionsExample Use
Device platforms Windows, macOS, iOS, Android, Linux Require MDM for mobile
Locations Named locations (IP ranges), countries, trusted locations MFA outside corporate network
Client apps Browser, mobile apps, desktop clients, legacy auth Block legacy authentication
Device state Compliant, Hybrid Azure AD joined, filter for devices Only allow managed devices
Sign-in risk (P2) Low, medium, high Block or require MFA for risky sign-ins
User risk (P2) Low, medium, high Force password change for compromised users

Control TypeOptions

Essential Policies (Must Have)

Policy 1: Require MFA for All Users

Why: MFA blocks 99.9% of account compromise attacks.

Name: CA001-Require-MFA-All-Users
State: On

Assignments:
  Users: All users
  Exclude: Emergency access accounts (break-glass)
  
  Cloud apps: All cloud apps
  
Access Controls:
  Grant: Require multifactor authentication

Policy 2: Block Legacy Authentication

Why: Legacy protocols (IMAP, POP3, SMTP) don't support MFA and are easily exploited.

Name: CA002-Block-Legacy-Auth
State: On

Assignments:
  Users: All users
  Exclude: Service accounts that require legacy auth (minimize!)
  
  Cloud apps: All cloud apps
  
  Conditions:
    Client apps: Other clients (legacy authentication clients)
  
Access Controls:
  Grant: Block access

Policy 3: Require MFA for Admins

Why: Admin accounts are high-value targets. Always require MFA.

Name: CA003-Require-MFA-Admins
State: On

Assignments:
  Users: Directory roles:
    - Global Administrator
    - Security Administrator  
    - Exchange Administrator
    - SharePoint Administrator
    - User Administrator
    - Privileged Role Administrator
    - (all privileged roles)
  Exclude: Emergency access accounts
  
  Cloud apps: All cloud apps
  
Access Controls:
  Grant: Require multifactor authentication

Policy 4: Block High-Risk Sign-ins (P2 Required)

Why: Automatically block sign-ins that Identity Protection flags as high risk.

Name: CA004-Block-HighRisk-SignIn
State: On

Assignments:
  Users: All users
  Exclude: Emergency access accounts
  
  Cloud apps: All cloud apps
  
  Conditions:
    Sign-in risk: High
  
Access Controls:
  Grant: Block access

Policy 5: Require Compliant Device for Sensitive Apps

Why: Ensure only managed, secure devices access sensitive data.

Name: CA005-Require-Compliant-Device-Sensitive
State: On

Assignments:
  Users: All users
  Exclude: Guest users (they can't have compliant devices)
  
  Cloud apps: 
    - Microsoft 365 (Exchange, SharePoint, Teams)
    - Sensitive internal apps
  
Access Controls:
  Grant: Require device to be marked as compliant
         OR Require Hybrid Azure AD joined device

Policy 6: Require MFA for Azure Management

Why: Protect Azure resources from unauthorized access.

Name: CA006-Require-MFA-Azure-Management
State: On

Assignments:
  Users: All users
  Exclude: Emergency access accounts
  
  Cloud apps: Microsoft Azure Management
  
Access Controls:
  Grant: Require multifactor authentication

Emergency Access Accounts

Critical: Always Have Break-Glass Accounts!

Emergency access accounts prevent lockout if:

  • MFA service is down
  • Conditional Access misconfiguration
  • Admin accounts compromised
  • Federation service fails

Requirements:

  • Cloud-only accounts (not synced)
  • Excluded from ALL Conditional Access policies
  • Permanent Global Admin role
  • Very strong, unique password (stored securely)
  • Monitor sign-ins closely (alert on any use)
  • At least 2 accounts for redundancy

Named Locations

Create Named Locations

Path: Entra ID → Protection → Conditional Access → Named locations

# PowerShell to create named location
$params = @{
    "@odata.type" = "#microsoft.graph.ipNamedLocation"
    displayName = "Corporate Network"
    isTrusted = $true
    ipRanges = @(
        @{
            "@odata.type" = "#microsoft.graph.iPv4CidrRange"
            cidrAddress = "203.0.113.0/24"
        }
        @{
            "@odata.type" = "#microsoft.graph.iPv4CidrRange"
            cidrAddress = "198.51.100.0/24"
        }
    )
}
New-MgIdentityConditionalAccessNamedLocation -BodyParameter $params

Troubleshooting

What-If Tool

Path: Entra ID → Protection → Conditional Access → What If

Test what policies would apply for a specific user/app/condition without actually signing in.

Sign-in Logs

Path: Entra ID → Monitoring → Sign-in logs

Look for:

  • Conditional Access: Shows which policies applied and their result
  • Failure reason: Why access was blocked
  • Authentication Details: What MFA method was used

Common Issues

IssueCauseSolution
Users blocked unexpectedly Policy too broad Use What-If, check exclusions
MFA not required User excluded or condition not met Check group membership, client app
Compliant device fails Device not enrolled or not compliant in Intune Check Intune compliance status
Legacy auth still working Block policy not applied to app Ensure policy targets the right apps

PowerShell Queries

# Get all Conditional Access policies
Get-MgIdentityConditionalAccessPolicy | Select-Object DisplayName, State

# Get specific policy details
Get-MgIdentityConditionalAccessPolicy -ConditionalAccessPolicyId "policy-id" | Format-List

# Get sign-in logs with CA results
Get-MgAuditLogSignIn -Top 100 | Select-Object UserPrincipalName, AppDisplayName, ConditionalAccessStatus

Best Practices

Conditional Access Best Practices

  • Start in Report-Only: Test policies before enforcing
  • Always have emergency accounts: Excluded from all policies
  • Name policies clearly: CA001-Require-MFA-AllUsers
  • Document everything: Why each policy exists
  • Use groups for exclusions: Easier to manage than individual users
  • Review regularly: Policies can become stale
  • Monitor sign-in logs: Watch for blocked legitimate users
  • Layer policies: Multiple policies can apply - they stack
  • Block by default: Require conditions to grant access
