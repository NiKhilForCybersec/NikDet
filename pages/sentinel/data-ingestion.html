Sentinel Data Ingestion & Parsing

Complete guide to getting data into Sentinel: default tables, custom parsing, Data Collection Rules, ASIM normalization, and storage tiers.

How Data Gets Into Sentinel

Data flows into Sentinel through this pipeline:

📊 Log Source → 🔌 Data Connector / DCR → ⚙️ Transformation (Optional) → 📋 Table → 💾 Storage Tier

Key concepts:

  • Data Connector = Pre-built integration for common sources (Azure AD, M365, etc.)
  • Data Collection Rule (DCR) = Configuration for how data is collected, transformed, and stored
  • Table = Where data is stored (can be default or custom)
  • Storage Tier = Analytics, Basic, or Archive (affects cost and query capability)

Section 1: Default Tables (Pre-Parsed)

When you enable Microsoft data connectors, logs go into default tables that are already parsed with proper fields. This is the easiest path - no configuration needed.

How Default Tables Work

Scenario: Enable Azure AD Sign-in Logs

What you do:

  1. Go to Data Connectors → Azure Active Directory
  2. Check "Sign-in logs" and click Connect

What happens automatically:

  • Logs flow to the SigninLogs table
  • Fields are pre-extracted: UserPrincipalName, IPAddress, ResultType, Location, etc.
  • No parsing configuration needed

Immediately queryable:

SigninLogs
| where TimeGenerated > ago(1h)
| where ResultType != 0
| project TimeGenerated, UserPrincipalName, IPAddress, ResultDescription

Best Practice

For Microsoft sources (Azure AD, M365, MDE, MDO), always use the native data connectors. The tables are pre-parsed, optimized, and often included in your license at no additional ingestion cost.

Section 2: Data Collection Rules (DCRs)

What is a DCR?

A Data Collection Rule (DCR) defines:

  • What to collect - Which logs, which events
  • How to transform - Parse, filter, enrich at ingestion
  • Where to send - Which table, which workspace

DCRs are used for: Azure Monitor Agent (AMA), custom logs, and log transformation.

When to Use DCRs

ScenarioUse DCR?Why
Azure AD, M365, MDE logs No Native connectors handle everything
Windows Event Logs via AMA Yes DCR specifies which Event IDs to collect
Linux Syslog via AMA Yes DCR specifies facilities and severity levels
Custom application logs Yes DCR defines parsing and destination table
Transform/filter existing logs Yes Ingestion-time transformation

Scenario: Collect Windows Security Events via AMA

Goal: Collect only important security events (not all 50+ event types)

Step 1: Create Data Collection Rule

Azure Portal → Monitor → Data Collection Rules → Create

  • Name: DCR-Windows-Security
  • Platform: Windows
  • Data Collection Endpoint: Select or create one
Step 2: Add Data Source

Data source type: Windows Event Logs

// XPath queries for specific events
Security!*[System[(EventID=4624 or EventID=4625 or EventID=4648 or EventID=4672 or EventID=4688 or EventID=4720 or EventID=4726)]]

This collects: Logon success (4624), Logon failure (4625), Explicit credentials (4648), Special privileges (4672), Process creation (4688), User created (4720), User deleted (4726)

Step 3: Set Destination
  • Destination type: Azure Monitor Logs
  • Workspace: Your Sentinel workspace
  • Table: SecurityEvent (default)
Step 4: Associate VMs

Resources → Add resources → Select VMs to collect from

AMA will be installed automatically on selected VMs.

Section 3: Custom Tables & Ingestion-Time Parsing

For non-standard log sources, you can create custom tables with your own schema and parse logs at ingestion time.

Scenario: Ingest Custom Application Logs

Your application produces logs like:

2025-01-04 10:23:45 INFO user=john.doe action=login status=success ip=192.168.1.100 duration=1.23s
2025-01-04 10:24:12 WARN user=jane.smith action=file_download status=blocked ip=10.0.0.50 duration=0.45s
Step 1: Create Custom Table

Log Analytics workspace → Tables → Create → New custom log (DCR-based)

// Table name: CustomAppLogs_CL
// Define schema:
{
  "columns": [
    {"name": "TimeGenerated", "type": "datetime"},
    {"name": "LogLevel", "type": "string"},
    {"name": "User", "type": "string"},
    {"name": "Action", "type": "string"},
    {"name": "Status", "type": "string"},
    {"name": "SourceIP", "type": "string"},
    {"name": "Duration", "type": "real"}
  ]
}
Step 2: Create DCR with Transformation

The transformation uses KQL to parse raw logs:

// Transformation query
source
| parse RawData with TimeStamp:datetime " " LogLevel:string " user=" User:string " action=" Action:string " status=" Status:string " ip=" SourceIP:string " duration=" DurationStr:string
| extend Duration = todouble(replace_string(DurationStr, "s", ""))
| project TimeGenerated=TimeStamp, LogLevel, User, Action, Status, SourceIP, Duration
Step 3: Configure Log Collection

Use Logs Ingestion API or AMA to send logs through the DCR.

# Using Logs Ingestion API
POST https://<DCE-endpoint>/dataCollectionRules/<DCR-ID>/streams/Custom-CustomAppLogs_CL?api-version=2023-01-01
Content-Type: application/json
Authorization: Bearer <token>

[
  {"RawData": "2025-01-04 10:23:45 INFO user=john.doe action=login status=success ip=192.168.1.100 duration=1.23s"}
]
Step 4: Query Your Parsed Data
CustomAppLogs_CL
| where TimeGenerated > ago(24h)
| where Status == "blocked"
| summarize BlockedActions = count() by User, Action
| order by BlockedActions desc

Section 4: ASIM Normalization (Optional)

What is ASIM?

ASIM (Advanced Security Information Model) is Microsoft's normalization framework. It maps different log formats to common field names so ONE query works across ALL sources.

Important: ASIM is optional. You can absolutely work with default tables directly. ASIM is useful when:

  • You have multiple sources for the same data type (e.g., 3 different firewalls)
  • You want to write detection rules that work across sources
  • You're building content for multiple environments

ASIM vs Default Tables

ApproachWhen to UseProsCons
Default Tables Single source, simple queries, learning Direct access, simpler queries, all fields available Different field names per source
ASIM Multiple sources, cross-source analytics One query for all sources, standard field names Parser overhead, some fields may not map

Scenario: Query Authentication Across Multiple Sources

Without ASIM (querying each table separately):

// Query 1: Azure AD
SigninLogs | where ResultType != 0 | project User=UserPrincipalName, IP=IPAddress, Result="Failure"
| union (
// Query 2: Windows
SecurityEvent | where EventID == 4625 | project User=TargetUserName, IP=IpAddress, Result="Failure"
)
| union (
// Query 3: Linux
Syslog | where SyslogMessage contains "Failed password" | extend User=extract(@"for (\w+)", 1, SyslogMessage)...
)

With ASIM (single query):

_Im_Authentication
| where EventResult == "Failure"
| summarize FailureCount = count() by TargetUsername, SrcIpAddr
| where FailureCount > 10

The _Im_Authentication function automatically queries all authentication sources and normalizes fields.

ASIM Schemas Available

SchemaFunctionCovers
Authentication_Im_AuthenticationSigninLogs, SecurityEvent, Syslog auth
Network Session_Im_NetworkSessionFirewalls, netflow, proxy
DNS_Im_DnsDNS query logs
Process Event_Im_ProcessCreateDeviceProcessEvents, SecurityEvent 4688
File Event_Im_FileEventDeviceFileEvents, Sysmon
Web Session_Im_WebSessionProxy logs, web server logs
Recommendation

Start with default tables. Learn the native field names first. Add ASIM later when you have multiple sources and need cross-source detection. Most SOC teams use default tables for 90% of their work.

Section 5: Storage Tiers

Sentinel/Log Analytics offers different storage tiers that affect cost and query capabilities:

Analytics Tier (Default)

Cost: ~$2.76/GB ingestion + retention costs

Retention: 30 days free, up to 2 years paid

Capabilities:

  • Full KQL query support
  • Analytics rules can query this data
  • Workbooks, hunting, all Sentinel features

Use for: Security-critical logs (authentication, endpoint, alerts)

Basic Tier (Low Cost)

Cost: ~$0.65/GB ingestion (76% cheaper than Analytics)

Retention: 8 days interactive, up to 2 years archive

Capabilities:

  • Limited KQL - only basic operators
  • Cannot use in Analytics rules
  • Good for ad-hoc searches

Use for: High-volume, low-security-value logs (verbose app logs, netflow)

Archive Tier (Long-term)

Cost: ~$0.02/GB/month storage

Retention: Up to 12 years

Capabilities:

  • Not directly queryable
  • Must restore to Analytics tier to query
  • Restore takes minutes to hours

Use for: Compliance retention, historical forensics

Configuring Table Tiers

# Set table to Basic tier (Azure CLI)
az monitor log-analytics workspace table update \
  --resource-group MyRG \
  --workspace-name MySentinelWorkspace \
  --name Syslog \
  --plan Basic

# Set retention and archive
az monitor log-analytics workspace table update \
  --resource-group MyRG \
  --workspace-name MySentinelWorkspace \
  --name SecurityEvent \
  --retention-time 90 \
  --total-retention-time 365

Windows/Linux via agent Create DCR → Filter events → Send to SecurityEvent/Syslog
