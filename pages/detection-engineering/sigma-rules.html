Sigma Rules - Complete Guide

Learn how to write detection rules that work across any SIEM platform.

What is Sigma?

Sigma is a universal language for writing detection rules. You write a rule once in Sigma format, then convert it to work in any SIEM (Splunk, Sentinel, Elastic, QRadar, etc.).

The Problem Sigma Solves:

  • Every SIEM has its own query language (SPL, KQL, Lucene, AQL...)
  • Sharing rules between teams/organizations is hard
  • Switching SIEMs means rewriting all your rules

Sigma's Solution: Write once, convert to any format!

Think of it like this

Sigma is like a universal translator for security rules:

  • You write a document in "Universal Security Language" (Sigma)
  • A converter translates it to "Splunk-ese", "Sentinel-speak", or "Elastic-lingo"
  • The meaning stays the same, just the language changes

Like writing a book once and having it automatically translated into every language!

Anatomy of a Sigma Rule

Let's break down a real Sigma rule piece by piece:

title: Failed Login Attempts
id: 12345678-1234-1234-1234-123456789012
status: production
description: Detects multiple failed login attempts which may indicate brute force
author: Your Name
date: 2024/01/15
references:
    - https://attack.mitre.org/techniques/T1110/

logsource:
    product: windows
    service: security

detection:
    selection:
        EventID: 4625
    condition: selection | count() > 5

falsepositives:
    - Users forgetting passwords
    - Service accounts with expired credentials

level: medium

tags:
    - attack.credential_access
    - attack.t1110

Line-by-Line Explanation:

title: Human-readable name for the rule
id: Unique identifier (UUID) - never changes even if rule is updated
status: experimental → test → production (maturity level)
logsource: What type of logs this rule searches (Windows Security logs)
detection: The actual detection logic - what pattern to find
selection: Name for this part of the logic (look for EventID 4625)
condition: When to alert: when selection matches more than 5 times
falsepositives: Known legitimate reasons this might fire (helps analysts)
level: Severity: informational → low → medium → high → critical
tags: MITRE ATT&CK mapping for categorization

Understanding Detection Logic

Basic Matching

detection:
    selection:
        EventID: 4625
        TargetUserName: 'Administrator'
    condition: selection
Meaning: Alert when EventID is 4625 AND TargetUserName is 'Administrator'
Plain English: "Someone failed to log in as Administrator"

OR Logic (Multiple Values)

detection:
    selection:
        EventID:
            - 4625
            - 4771
            - 4776
    condition: selection
Meaning: Alert when EventID is 4625 OR 4771 OR 4776
Plain English: "Any of these authentication failure event types"

AND + OR Combined

detection:
    selection:
        EventID: 1
        Image|endswith:
            - '\powershell.exe'
            - '\pwsh.exe'
    filter:
        ParentImage|endswith: '\explorer.exe'
    condition: selection and not filter
Meaning: Alert when:
  • EventID is 1 (Process Creation) AND
  • Process is PowerShell AND
  • Parent is NOT Explorer (user-initiated is normal)
Plain English: "PowerShell launched by something other than a user clicking it"

String Modifiers (Pattern Matching)

Real-World Examples

Example 1: Detect Encoded PowerShell

title: Suspicious Encoded PowerShell Command
logsource:
    category: process_creation
    product: windows
detection:
    selection:
        Image|endswith:
            - '\powershell.exe'
            - '\pwsh.exe'
        CommandLine|contains:
            - ' -enc '
            - ' -encodedcommand '
            - ' -e '
    condition: selection
level: high
tags:
    - attack.execution
    - attack.t1059.001
What This Detects: PowerShell running with encoded commands - a common attacker technique to hide malicious scripts.
Why It's Suspicious: Normal users rarely use encoded commands. Attackers use them to bypass simple string matching.

Example 2: Detect certutil Download

title: Certutil Used to Download File
logsource:
    category: process_creation
    product: windows
detection:
    selection:
        Image|endswith: '\certutil.exe'
        CommandLine|contains:
            - 'urlcache'
            - '-f http'
            - '-f https'
    condition: selection
level: high
tags:
    - attack.command_and_control
    - attack.t1105
What This Detects: Using certutil.exe to download files - a Living-off-the-Land technique.
Why It's Suspicious: certutil is meant for certificate management, not downloading files. Attackers abuse it because it's signed by Microsoft.

Converting Sigma Rules

Using sigma-cli (Command Line)

# Install sigma-cli
pip install sigma-cli

# Convert to Splunk SPL
sigma convert -t splunk rule.yml

# Convert to Microsoft Sentinel KQL
sigma convert -t microsoft365defender rule.yml

# Convert to Elastic Query
sigma convert -t elasticsearch rule.yml

# Convert entire folder
sigma convert -t splunk ./rules/ -o splunk_rules.txt
Output Example (Splunk): 
index=windows EventCode=1 (Image="*\\powershell.exe" OR Image="*\\pwsh.exe") (CommandLine="* -enc *" OR CommandLine="* -encodedcommand *")

Best Practices

Writing Good Sigma Rules
  1. Be specific: Include enough conditions to reduce false positives
  2. Document well: Future you will thank past you for good descriptions
  3. Test before deploying: Convert and run against historical data first
  4. Include false positives: List known legitimate matches to help analysts
  5. Map to MITRE: Always tag with ATT&CK techniques
  6. Start with existing rules: Don't reinvent the wheel - check SigmaHQ first
