Threat Hunting Methodology

Structured approach to proactively finding threats that evade automated detection.

Why Threat Hunting?

The Fundamental Problem

Automated detections catch known threats. But skilled attackers specifically design their attacks to evade detection. Hunting fills this gap.

Detection vs. Hunting

AspectAutomated DetectionThreat Hunting
ApproachReactive - alerts on known patternsProactive - searches for unknown threats
SpeedReal-time or near real-timePeriodic, scheduled
ScopePre-defined rules and signaturesCreative, hypothesis-driven
CatchesKnown attack patternsNovel attacks, evasion techniques
ResourceAutomated (machine)Human analyst expertise

When Hunting Makes the Difference

ScenarioWhy Detection Missed ItHow Hunting Finds It
Living-off-the-land attackUses legitimate tools (PowerShell, WMI)Look for unusual patterns in legitimate tool usage
Slow and low exfiltrationBelow volume thresholdsAnalyze cumulative data movement over time
Custom malwareNo signature existsHunt for behavioral anomalies, C2 patterns
Insider threatAuthorized access, legitimate credentialsLook for access pattern anomalies
Supply chain compromiseTrusted software, signed binariesHunt for unusual behavior from trusted sources

Hunting Methodologies

Three Main Approaches

ApproachDescriptionWhen to UseExample
Intel-Driven Hunt based on threat intelligence (IOCs, TTPs, actor reports) New threat intel received, industry-targeting campaign "Hunt for Volt Typhoon TTPs in our environment"
Hypothesis-Driven Form hypothesis about attacker behavior, test it No specific intel, general proactive hunting "If an attacker compromised us, they'd need to move laterally..."
Anomaly-Driven Look for statistical outliers from baseline Good data, established baselines "Find users with login patterns unlike their peers"

The Hunting Loop

Iterative Hunting Process
StepActionOutputTime

Practical Hunt Examples

Hunt 1: Unusual Scheduled Tasks

ElementDetails
HypothesisAttackers create scheduled tasks from user-writable locations for persistence
Data neededWindows Event 4698 (task created), Sysmon, EDR task creation events
What to look forTasks running executables from: Downloads, Temp, AppData, user profiles
Expected FPsSome legitimate software installs this way; user-created tasks
Investigation stepsCheck executable reputation, creation time vs. install time, process tree
 
// KQL - Hunt for scheduled tasks from unusual locations
DeviceProcessEvents
| where Timestamp > ago(30d)
| where InitiatingProcessFileName =~ "schtasks.exe" or ActionType == "ScheduledTaskCreated"
| where ProcessCommandLine has_any ("\\Users\\", "\\Temp\\", "\\Downloads\\", "\\AppData\\")
| project Timestamp, DeviceName, AccountName, ProcessCommandLine, InitiatingProcessFileName
| summarize Count = count(), Devices = make_set(DeviceName) by ProcessCommandLine
| order by Count desc

Hunt 2: Beaconing Detection

ElementDetails
HypothesisC2 beacons show regular, periodic communication patterns
Data neededFirewall logs, proxy logs, DNS logs with timestamps
What to look forConnections to same destination at regular intervals (±small jitter)
Expected FPsLegitimate software updates, monitoring agents, heartbeats
Investigation stepsCheck destination reputation, what process is connecting, payload analysis

Hunting Challenges

ChallengeSolution
Too many results to reviewAdd more filters, focus on high-value targets first, use statistical methods to find outliers
No results at allCheck data availability, broaden query, verify hypothesis is testable with available data
Can't tell FPs from TPsDocument the FPs (they become baseline), focus on anomalies from that baseline
Hunt found nothing, was it worth it?Yes - documented gap, proved hypothesis, learned about environment
Found something! Now what?Shift to investigation mode, follow IR procedures, escalate if confirmed threat
Management wants ROI numbersTrack: hunts run, findings, detections created, time savings vs. discovery by other means

Converting Hunts to Detections

When to Create a Detection

Create Detection If...Don't Create Detection If...
Pattern is reliably maliciousToo many false positives to be useful
Query performs well (fast enough)Query is too slow/expensive for real-time
Clear response action existsFinding requires too much human judgment
Pattern is likely to recurOne-time or very rare occurrence

Detection Creation Process

  1. Refine query - Optimize for performance, reduce FPs
  2. Test historically - Run against 30+ days of data
  3. Document FP patterns - What legitimate activity matches?
  4. Create exclusions - Filter out known good
  5. Write response procedure - What should analyst do when it fires?
  6. Deploy in audit mode - Monitor before alerting
  7. Tune and enable - Adjust thresholds, enable alerting
