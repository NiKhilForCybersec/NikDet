SOC Terminology - Complete Understanding

Don't just memorize acronyms - understand what they mean, how they connect, and why they matter. This guide shows you terms in context with real examples.

The Big Picture: How Terms Connect

Before diving into individual terms, see how they all work together:

Tools & Platforms

SIEM - Security Information and Event Management

"The central nervous system of the SOC - collects logs from everywhere and creates alerts"

WHAT A SIEM DOES ═══════════════════════════════════════════════════════════════════════════════ ALL YOUR SYSTEMS │ ┌─────────────────────┼─────────────────────┐ │ │ │ ▼ ▼ ▼ ┌────────┐ ┌────────┐ ┌────────┐ │Firewall│ │ Servers│ │ EDR │ │ logs │ │ logs │ │ alerts │ └───┬────┘ └───┬────┘ └───┬────┘ │ │ │ └───────────────────┼───────────────────┘ │ ▼ ┌─────────────────┐ │ │ │ SIEM │ │ │ │ • Collects │ │ • Normalizes │ │ • Correlates │ │ • Alerts │ │ • Stores │ │ │ └────────┬────────┘ │ ▼ ┌─────────────────┐ │ SOC ANALYST │ │ Dashboard │ │ │ │ 🔴 HIGH Alert │ │ 🟡 MED Alert │ │ 🟢 LOW Alert │ └─────────────────┘ Popular SIEMs: • Splunk (most common in enterprise) • Microsoft Sentinel (cloud-native, Azure focused) • IBM QRadar • Elastic Security • Google Chronicle
Real Example: User logs into VPN from New York at 9 AM. Same user logs into email from Russia at 9:05 AM. Neither system alone sees a problem. But SIEM correlates both events and alerts: "Impossible travel detected!"

EDR - Endpoint Detection and Response

"An agent on every laptop/server that watches everything happening and can respond"

WHAT EDR SEES ON AN ENDPOINT ═══════════════════════════════════════════════════════════════════════════════ Every laptop/server has an EDR agent watching: ┌─────────────────────────────────────────────────────────────────────────────┐ │ LAPTOP-JOHN-01 │ │ │ │ EDR Agent watching: │ │ │ │ PROCESSES FILES NETWORK REGISTRY │ │ ────────── ───── ─────── ──────── │ │ What's running? What's created? What's it What's │ │ Who started it? What's modified? talking to? changed? │ │ Parent process? What's deleted? What ports? Persistence? │ │ │ │ ┌──────────────────────────────────────────────────────────────────────┐ │ │ │ 09:15:23 powershell.exe spawned by outlook.exe │ │ │ │ Command: IEX(New-Object Net.WebClient).DownloadString... │ │ │ │ ⚠️ SUSPICIOUS: Office app spawning PowerShell │ │ │ │ │ │ │ │ 09:15:24 CONNECTION to 185.220.101.34:443 (known C2 server) │ │ │ │ 🔴 BLOCKED - EDR prevented connection │ │ │ │ │ │ │ │ 09:15:24 FILE created: C:\Users\John\AppData\Local\Temp\mal.exe │ │ │ │ 🔴 QUARANTINED - Hash matches known malware │ │ │ └──────────────────────────────────────────────────────────────────────┘ │ │ │ └─────────────────────────────────────────────────────────────────────────────┘ EDR can RESPOND: • Isolate machine from network (one click!) • Kill malicious process • Quarantine file • Collect forensic data Popular EDRs: • CrowdStrike Falcon • Microsoft Defender for Endpoint (MDE) • SentinelOne • Carbon Black • Cortex XDR

🎯 Why EDR Changed Everything

Before EDR (antivirus only): AV scans files against known signatures. If malware is new or "fileless" (runs in memory), AV misses it.

With EDR: Watches behavior, not just files. "PowerShell downloading executable and running it" is suspicious regardless of whether we've seen that specific malware before.

XDR - Extended Detection and Response

"EDR + network + email + cloud + identity all in one view"

EDR vs XDR - WHAT'S THE DIFFERENCE? ═══════════════════════════════════════════════════════════════════════════════ EDR: Sees only endpoints ──────────────────────── ┌─────────┐ │ Laptop │ ◄── EDR can see this └─────────┘ │ │ What about the email │ that delivered the malware? │ What about the network traffic? │ What about the cloud app? │ ▼ ❓ Blind spots XDR: Sees EVERYTHING together ──────────────────────────── ┌─────────────────┐ │ XDR │ │ │ │ Unified view │ │ of the attack │ └────────┬────────┘ │ ┌──────────────┬─────────┼─────────┬──────────────┐ │ │ │ │ │ ▼ ▼ ▼ ▼ ▼ ┌─────────┐ ┌─────────┐ ┌─────────┐ ┌─────────┐ ┌─────────┐ │ Email │ │ Network │ │Endpoint │ │ Cloud │ │Identity │ │ │ │ │ │ │ │ │ │ │ │Phishing │──►│ C2 call │──►│Malware │──►│ Data │──►│Lateral │ │ email │ │ traffic │ │executed │ │exfil │ │movement│ └─────────┘ └─────────┘ └─────────┘ └─────────┘ └─────────┘ XDR shows the FULL attack chain, not just pieces.

🏠 Analogy: Security Cameras

EDR: Camera only inside your house. You see someone walking around, but don't know how they got in.

XDR: Cameras on street, doorbell, inside house, backyard, AND they're all connected. You see: "Suspicious person parked on street → rang doorbell → lock picked → walked through house → left via backyard."

SOAR - Security Orchestration, Automation, and Response

"Automation that does the boring stuff so analysts focus on real threats"

WHAT SOAR AUTOMATES ═══════════════════════════════════════════════════════════════════════════════ WITHOUT SOAR (Manual process): ────────────────────────────── Alert: Phishing email detected Analyst manually: 1. Copy email sender address (30 seconds) 2. Check sender reputation (2 minutes) 3. Copy any URLs in email (30 seconds) 4. Check URLs in VirusTotal (2 minutes) 5. Copy any attachments (30 seconds) 6. Submit to sandbox (5 minutes to get result) 7. Check if other users got same email (5 minutes) 8. If malicious, block sender (2 minutes) 9. Delete from all mailboxes (5 minutes) 10. Document in ticket (5 minutes) Total: ~25 minutes per phishing email With 50 phishing alerts/day = 20+ hours of work! WITH SOAR (Automated playbook): ─────────────────────────────── Alert: Phishing email detected │ ▼ ┌─────────────────────────────────────────────────────────────────────────────┐ │ SOAR PLAYBOOK RUNS │ │ │ │ ✓ Extract sender, URLs, attachments (automatic) │ │ ✓ Check all against threat intel (automatic) │ │ ✓ Submit attachments to sandbox (automatic) │ │ ✓ Query email system for other recipients (automatic) │ │ ✓ If malicious: │ │ ├─ Block sender domain (automatic) │ │ ├─ Delete from all mailboxes (automatic) │ │ └─ Create incident ticket (automatic) │ │ ✓ Enrich ticket with all findings (automatic) │ │ │ │ Time: 2 minutes (no analyst needed) │ │ │ │ Analyst only reviews: HIGH confidence incidents │ │ │ └─────────────────────────────────────────────────────────────────────────────┘ Popular SOAR platforms: • Palo Alto XSOAR (formerly Demisto) • Splunk SOAR (formerly Phantom) • Microsoft Sentinel (built-in automation) • IBM Resilient • Swimlane

Threat Concepts

IOC - Indicator of Compromise

"Evidence that an attack happened - the fingerprints attackers leave behind"

TYPES OF IOCs ═══════════════════════════════════════════════════════════════════════════════ IOCs are like fingerprints. If you see them, something bad happened (or is happening). TYPE EXAMPLE WHERE TO LOOK ──────────────────────────────────────────────────────────────────────────────── IP Address 185.220.101.34 Firewall logs, proxy logs Domain evil-domain.com DNS logs, proxy logs URL http://evil.com/malware.exe Web proxy logs File Hash (MD5) d41d8cd98f00b204e9800998ecf8427e EDR, AV logs File Hash (SHA256) e3b0c44298fc1c149afb... More secure, same use Email Address attacker@phishing.com Email logs Registry Key HKLM\Software\BadMalware EDR, Windows events File Path C:\Windows\Temp\evil.exe EDR, file system logs Process Name mimikatz.exe, psexec.exe EDR, process logs User Agent Mozilla/5.0 (compatible; Malware) Proxy logs REAL ATTACK IOCS: ──────────────────────────────────────────────────────────────────────────────── Cobalt Strike Campaign IOCs: • C2 IP: 185.220.101.34 • C2 Domain: update-microsoft.com • Beacon hash: a1b2c3d4e5f6... • User-agent: "Mozilla/5.0 (compatible; MSIE 10.0)" • Named pipe: \\.\pipe\msagent_* If you see ANY of these in your logs → you might be compromised

❌ Common Misconception

Wrong: "If we block all IOCs, we're safe"

Right: IOCs are reactive - they're evidence of PAST attacks. Attackers change their IPs, domains, and tools constantly. IOCs help with known threats but don't protect against new ones. That's why we need behavioral detection too.

TTP - Tactics, Techniques, and Procedures

"HOW attackers attack - their playbook and methods"

UNDERSTANDING TTPs (MITRE ATT&CK FRAMEWORK) ═══════════════════════════════════════════════════════════════════════════════ TACTIC = The goal (WHY) TECHNIQUE = The method (HOW) PROCEDURE = The specific implementation (EXACT STEPS) Example - Credential Theft Attack: TACTIC TECHNIQUE PROCEDURE (Goal) (Method) (Exact steps) ───────────────────────────────────────────────────────────────────────────── Initial Access Phishing Send Word doc with macro pretending to be invoice Execution User Execution User enables macros, runs embedded PowerShell Credential Access OS Credential Dumping Run Mimikatz to extract passwords from memory Lateral Movement Remote Services Use stolen creds to RDP to other servers Exfiltration Exfiltration Over C2 Upload data to attacker's server via HTTPS WHY TTPs MATTER MORE THAN IOCs: ─────────────────────────────────────────────────────────────────────────────── IOCs change constantly: TTPs change slowly: ───────────────────────── ─────────────────────── Monday: C2 = evil1.com Attackers still use phishing Tuesday: C2 = evil2.com Attackers still dump credentials Wednesday: C2 = evil3.com Attackers still move laterally Blocking IOCs = whack-a-mole Detecting TTPs = lasting protection
💡 Key Insight: The MITRE ATT&CK framework catalogs all known TTPs. When you write detection rules, you should map them to ATT&CK techniques. This helps you understand your coverage: "We detect 60% of credential theft techniques but only 20% of exfiltration techniques."

APT - Advanced Persistent Threat

"Nation-state or highly organized attackers who target specific organizations for months/years"

APT vs REGULAR CYBERCRIME ═══════════════════════════════════════════════════════════════════════════════ REGULAR CYBERCRIME APT ───────────────────── ───────────────────── Goal: Money (ransomware, theft) Goal: Espionage, sabotage, IP theft Target: Anyone vulnerable Target: Specific organizations "Spray and pray" "We want YOUR secrets" Timeframe: Days to weeks Timeframe: Months to YEARS Resources: Limited Resources: Nation-state budget ($millions) Sophistication: Off-the-shelf tools Sophistication: Custom malware, zero-days FAMOUS APT GROUPS: ─────────────────────────────────────────────────────────────────────────────── APT29 (Cozy Bear) Russia SolarWinds attack, targeting governments APT28 (Fancy Bear) Russia Election interference, Olympics hacking APT41 (Winnti) China IP theft from tech/gaming companies Lazarus Group N. Korea Bank theft, cryptocurrency, Sony hack APT33 (Elfin) Iran Oil & gas, aviation targeting WHAT MAKES APTs DANGEROUS: ─────────────────────────────────────────────────────────────────────────────── • They don't give up. Blocked? They find another way in. • They're patient. Willing to wait months for the right opportunity. • They're funded. Can buy zero-days ($100K-$2M each). • They're skilled. Write custom tools that bypass your defenses. • They're stealthy. Hide in your network for years without detection.

C2 / C&C - Command and Control

"The attacker's remote control channel - how they talk to malware they've planted"

HOW C2 WORKS ═══════════════════════════════════════════════════════════════════════════════ After malware is on your system, it needs to "phone home" to get instructions. YOUR NETWORK ATTACKER ──────────── ──────── ┌────────────────┐ ┌────────────────┐ │ Infected Host │ │ C2 Server │ │ │ │ │ │ Malware │ "I'm alive, │ Attacker │ │ (Beacon) │────any commands?"──► Console │ │ │ │ │ │ │◄──"Download this │ "Got one! │ │ │ file and run it" │ Let me poke │ │ │ │ around..." │ │ │ │ │ └────────────────┘ └────────────────┘ C2 COMMUNICATION METHODS: ─────────────────────────────────────────────────────────────────────────────── METHOD HOW IT WORKS WHY ATTACKERS USE IT ─────────────────────────────────────────────────────────────────────────────── HTTP/HTTPS Regular web traffic Blends in with normal browsing DNS Hidden in DNS queries Often not inspected Social Media Commands in Twitter posts Hard to block Twitter Cloud Services Dropbox, Google Drive Looks like legitimate use Email Commands in draft emails Hard to distinguish WHY C2 DETECTION IS CRITICAL: ─────────────────────────────────────────────────────────────────────────────── If you block C2: • Attacker loses control of malware • Can't steal data (exfil usually goes through C2) • Can't move laterally (needs commands) • Attack fails even if malware is still present This is why DNS monitoring and proxy analysis are so important!

Alert Classification - Critical to Understand!

This is one of the most important concepts in SOC work. Every alert you review gets classified.

ALERT CLASSIFICATION MATRIX ═══════════════════════════════════════════════════════════════════════════════ WHAT THE DETECTION SAID ┌─────────────────┬─────────────────┐ │ "THREAT!" │ "No threat" │ │ (Alerted) │ (No alert) │ ────────────────┼─────────────────┼─────────────────┤ REALITY: │ │ │ Actually a │ TRUE POSITIVE │ FALSE NEGATIVE │ threat │ (TP) │ (FN) │ │ ✅ GOOD! │ ❌ BAD! │ │ We caught it │ We missed it │ ────────────────┼─────────────────┼─────────────────┤ REALITY: │ │ │ Not a │ FALSE POSITIVE │ TRUE NEGATIVE │ threat │ (FP) │ (TN) │ │ ⚠️ ANNOYING │ ✅ GOOD! │ │ Wasted time │ Correctly │ │ │ ignored │ └─────────────────┴─────────────────┘ WITH EXAMPLES: ─────────────────────────────────────────────────────────────────────────────── TRUE POSITIVE (TP) - "Real attack, correctly detected" Alert: "Mimikatz detected on FINANCE-SERVER" Reality: Attacker actually ran Mimikatz Action: Investigate immediately! 🚨 FALSE POSITIVE (FP) - "Not an attack, but we alerted anyway" Alert: "Mimikatz detected on IT-LAPTOP" Reality: IT admin running legitimate pen test tool Action: Close as FP, maybe tune the rule BENIGN TRUE POSITIVE (BTP) - "Detected correctly, but it's authorized" Alert: "Port scan detected from 10.1.50.100" Reality: Scheduled vulnerability scan running Action: Close as BTP, document the exception FALSE NEGATIVE (FN) - "Real attack that we MISSED" Alert: (none) Reality: Attacker exfiltrated data Action: We only find out later 😱 This is the WORST outcome - we had no chance to respond

🎯 Why This Matters

SOC quality is measured by these ratios:

  • High TP rate = Catching real threats (good detection)
  • Low FP rate = Not wasting analyst time (good tuning)
  • Zero FN rate = Never missing attacks (ideal but impossible)

The tradeoff: If you make rules too sensitive → more TPs but also more FPs. If you make rules too specific → fewer FPs but might miss attacks (FNs).

Key Metrics

MTTD - Mean Time to Detect

"How long from when an attack STARTS to when we KNOW about it"

MTTD VISUALIZATION ═══════════════════════════════════════════════════════════════════════════════ Attack Timeline: Attack Attacker moves Data stolen Alert Investigation starts laterally fires begins │ │ │ │ │ ▼ ▼ ▼ ▼ ▼ ───────┼─────────────┼───────────────┼─────────────┼───────────┼────► Time │ │ │◄──────────── MTTD ────────────────────────►│ │ │ │ (Detection happened HERE) │ │ │ Everything between attack start and alert = attacker operating freely MTTD BENCHMARKS: ─────────────────────────────────────────────────────────────────────────────── MTTD Rating Context ─────────────────────────────────────────────────────────────────────────────── < 1 hour Excellent Real-time detection, probably automated 1-24 hours Good SOC is actively monitoring 1-7 days Needs work Gaps in detection or coverage > 7 days Poor Major blind spots 197 days Industry avg Without SOC (IBM report)

MTTR - Mean Time to Respond

"How long from when we KNOW about an attack to when we CONTAIN it"

MTTR VISUALIZATION ═══════════════════════════════════════════════════════════════════════════════ Response Timeline: Alert Analyst Investigation Containment Full fires assigned complete actions remediation │ │ │ │ │ ▼ ▼ ▼ ▼ ▼ ───────┼──────────┼───────────┼──────────────┼──────────────┼────► Time │ │ │◄─────────── MTTR ───────────────────►│ │ │ │ (Threat is STOPPED at this point)│ MTTR BENCHMARKS: ─────────────────────────────────────────────────────────────────────────────── MTTR Rating Context ─────────────────────────────────────────────────────────────────────────────── < 1 hour Excellent Automated response or well-drilled team 1-4 hours Good Efficient SOC with good tools 4-24 hours Average Room for improvement > 24 hours Needs work Slow processes, lack of authority
