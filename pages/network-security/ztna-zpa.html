Zero Trust Principles

💡 Interview Answer: What is Zero Trust?

"Zero Trust is a security model based on 'never trust, always verify.' It assumes breach and verifies each request as if it originates from an untrusted network. Key principles include: verify explicitly (authenticate and authorize based on all available data), use least privilege access (limit user access with Just-In-Time and Just-Enough-Access), and assume breach (minimize blast radius and segment access)."

PrincipleTraditional SecurityZero Trust (ZTNA)
Trust Model Trust inside network perimeter Never trust, always verify
Access Scope Network-level (VPN gives subnet access) Application-level (specific apps only)
Verification Once at login Continuous (every request)
Visibility Apps exposed to internet (VPN endpoint) Apps invisible (inside-out connection)
Segmentation Network-based (VLANs) Identity-based (per-app policies)

Components Deep Dive

1. Zscaler Client Connector

What: Lightweight agent installed on user endpoints

Platforms: Windows, macOS, iOS, Android, Linux

Key Functions:

  • Authenticates user with IdP (SAML/OIDC)
  • Reports device posture (OS, encryption, AV, firewall)
  • Intercepts traffic destined for ZPA applications
  • Creates encrypted tunnel to Zscaler cloud
  • Handles both ZIA (internet) and ZPA (private apps)
# Client Connector Requirements Windows: - Windows 10 1809+ or Windows 11 - .NET Framework 4.7.2+ - 100 MB disk space - Admin rights for installation macOS: - macOS 10.15 (Catalina) or later - System Extension approval required - Full Disk Access for posture checks Mobile: - iOS 14+ / Android 8+ - MDM recommended for enterprise deployment

2. App Connector

What: Lightweight VM deployed near your applications

Deployment: VMware, Hyper-V, AWS, Azure, GCP, Docker, Kubernetes

Key Functions:

  • Creates outbound tunnel to Zscaler cloud (port 443)
  • Proxies authorized user traffic to internal apps
  • No inbound firewall rules required
  • Health reporting to Zscaler cloud
# App Connector VM Sizing Small (up to 2,000 users): vCPU: 2 RAM: 4 GB Disk: 8 GB Medium (2,000-5,000 users): vCPU: 4 RAM: 8 GB Disk: 16 GB Large (5,000+ users): vCPU: 8 RAM: 16 GB Disk: 32 GB # Always deploy 2+ connectors per site for HA
Best Practices:
  • Deploy in same network segment as applications
  • Minimum 2 connectors per location for redundancy
  • Place in DMZ or application zone, not user zone
  • Use Connector Groups to organize by location/function

Application Segments Configuration

Application Segments define which internal applications are accessible via ZPA.

Creating Application Segments

# Navigation: Applications → Application Segments → Add # Example 1: Web Application Name: HR-Portal Description: Human Resources self-service portal Domains: - hr.internal.company.com - hrportal.company.local TCP Ports: 443 Connector Group: DC-Chicago-Connectors Health Reporting: Enabled # Example 2: SSH Access Name: Linux-Servers-SSH Description: SSH access to Linux servers Domains: - *.servers.internal IP Ranges: - 10.1.50.0/24 TCP Ports: 22 Connector Group: DC-Chicago-Connectors # Example 3: Multi-Port Application (SAP) Name: SAP-Production Description: SAP ERP system Domains: - sap.internal.company.com IP Ranges: - 10.1.100.50 TCP Ports: 443, 3200-3299, 8000-8100, 44300 UDP Ports: 3200-3299 Connector Group: DC-Chicago-Connectors # Example 4: RDP Access to Windows Servers Name: Windows-Servers-RDP Description: RDP access to Windows servers IP Ranges: - 10.1.60.0/24 TCP Ports: 3389 Connector Group: DC-Chicago-Connectors
⚠️ Common Mistakes:
  • Using wildcards too broadly (*.company.com exposes everything)
  • Forgetting to include all ports an app needs (SAP uses many)
  • Not creating separate segments for different security levels
  • Assigning wrong Connector Group (traffic goes to wrong data center)

Browser Access (Clientless)

Allow access to web applications without installing Zscaler Client Connector.

# Browser Access Configuration Navigation: Applications → Browser Access → Add Application: HR-Portal Internal URL: https://hr.internal.company.com External URL: https://hr.company.zpa.com Authentication: SAML (via IdP) # Access Policy for Browser Access Name: Browser-Access-HR Application: HR-Portal (Browser Access) Users: All Employees Device Posture: None required (clientless) # Features Available: ✓ Web applications ✓ HTML5 RDP (remote desktop in browser) ✓ HTML5 SSH (terminal in browser) ✗ Native applications (requires client)
Use Case: Contractor Access Without Agent

External contractors need temporary access to project management tool but you can't install software on their devices.

Solution: Enable Browser Access for the app. Contractors authenticate via IdP, access app in browser. No client installation needed.

Real-World Use Cases

Use Case 1: Replace VPN for Remote Workforce

Scenario: 5,000 employees, 70% remote. VPN concentrators at capacity.

ZPA Solution:

  1. Deploy App Connectors in each data center (2 per site)
  2. Create Application Segments for all internal apps
  3. Deploy Zscaler Client Connector via MDM
  4. Migrate users in phases (IT → Power users → All)
  5. Decommission VPN after 3-month parallel run

Results:

  • ✅ User experience improved (no VPN connect/disconnect)
  • ✅ Access time reduced from 30 seconds to instant
  • ✅ VPN infrastructure costs eliminated
  • ✅ Security improved (app-level vs network-level access)

Use Case 2: M&A Integration (Acquired Company)

Scenario: Acquire 500-person company. Need to give them access to corporate SAP within 2 weeks. Network integration will take 6 months.

ZPA Solution:

# Day 1-3: Prepare 1. Create new Connector Group: "Acquired-Company-Access" 2. Create Application Segment: "SAP-Acquired-Access" - Same as existing SAP segment - Different Connector Group for traffic separation # Day 3-5: Identity 3. Federate acquired company's IdP with Zscaler - Or create accounts in corporate IdP 4. Create User Group: "Acquired-Company-Users" # Day 5-7: Policy & Deploy 5. Create Access Policy: Name: Acquired-SAP-Access Users: Acquired-Company-Users Apps: SAP-Acquired-Access Posture: Basic 6. Deploy Client Connector to acquired company laptops # Day 7: Go Live - Users can access SAP immediately - No network changes required - Full audit trail

Use Case 3: Privileged Access for IT Administrators

Scenario: IT admins need SSH/RDP to servers. Want to record sessions for compliance.

ZPA Solution:

Troubleshooting Guide

SymptomLikely CauseResolution
User can't access any apps Client Connector not running or not enrolled Check client status: System tray → Zscaler icon → Status. Re-enroll if needed.
"Application not available" App not in Application Segment Verify domain/IP is in a segment. Check ports are correct.
"Access Denied" No policy allows access Check user's group membership. Verify access policy exists.
Posture check failing Device doesn't meet requirements Run posture check: Client → More → Posture. Fix device compliance.
Slow performance Distant App Connector selected Check which connector is serving traffic. Deploy closer connector.
Intermittent connectivity App Connector issues Check connector health in admin portal. Review connector logs.
App works for some users, not others Policy misconfiguration Compare working vs non-working users. Check group membership.
