Hunt: Encoded PowerShell Execution

Hypothesis

Attackers are using Base64-encoded PowerShell commands to execute malicious payloads while evading command-line based detection rules.

ATT&CK Mapping

TechniqueT1059.001 - PowerShell
Sub-techniqueT1027 - Obfuscated Files or Information
TacticExecution, Defense Evasion

Data Requirements

  • Sysmon Event ID 1 (Process Creation) OR
  • Windows Security Event 4688 with command line auditing
  • PowerShell Script Block Logging (Event ID 4104) - optional but helpful

Hunt Queries

// KQL - Microsoft Sentinel
DeviceProcessEvents
| where TimeGenerated > ago(30d)
| where FileName in~ ("powershell.exe", "pwsh.exe")
| where ProcessCommandLine has_any ("-enc", "-encoded", "-e ", "-ec ")
        or ProcessCommandLine matches regex @"[A-Za-z0-9+/=]{50,}"
| extend DecodedCommand = base64_decode_tostring(
    extract(@"[A-Za-z0-9+/=]{50,}", 0, ProcessCommandLine))
| project TimeGenerated, DeviceName, AccountName, 
    ProcessCommandLine, DecodedCommand, 
    InitiatingProcessFileName, InitiatingProcessCommandLine
| sort by TimeGenerated desc
// SPL - Splunk
index=sysmon EventCode=1 
    (Image="*\\powershell.exe" OR Image="*\\pwsh.exe")
    (CommandLine="*-enc*" OR CommandLine="*-encoded*" 
     OR CommandLine="*-e *" OR CommandLine="*-ec *")
| rex field=CommandLine "(?[A-Za-z0-9+/=]{50,})"
| eval decoded=base64decode(encoded_blob)
| table _time, ComputerName, User, CommandLine, decoded, 
    ParentImage, ParentCommandLine
| sort -_time

Analysis Steps

  1. Review encoded commands: Decode Base64 to see actual command
  2. Check parent process: Office apps, browsers = likely phishing. cmd.exe = possible persistence
  3. Look for patterns: Download cradles (IEX, DownloadString), reflective loading
  4. Pivot on user: What else did this user execute?
  5. Pivot on host: What other suspicious activity on this endpoint?

Suspicious Indicators

  • Parent process is Office application or browser
  • Decoded command contains: IEX, Invoke-Expression, DownloadString, WebClient
  • Decoded command references external URLs or IPs
  • Execution during non-business hours
  • User not typically running PowerShell

Hunt: LSASS Credential Dumping

Hypothesis

Attackers have accessed LSASS memory to extract credentials using tools like Mimikatz, ProcDump, or direct memory access.

ATT&CK Mapping

TechniqueT1003.001 - OS Credential Dumping: LSASS Memory
TacticCredential Access

Data Requirements

  • Sysmon Event ID 10 (Process Access) - Required
  • Windows Defender alerts (optional)
  • EDR telemetry (optional)

Hunt Queries

// KQL - Microsoft Sentinel
Sysmon
| where TimeGenerated > ago(30d)
| where EventID == 10
| where TargetImage endswith "\\lsass.exe"
| where GrantedAccess in ("0x1010", "0x1038", "0x1410", "0x1fffff", "0x1f3fff")
| where SourceImage !endswith "\\lsass.exe"
| where SourceImage !endswith "\\csrss.exe"
| where SourceImage !endswith "\\wmiprvse.exe"
| where SourceImage !endswith "\\svchost.exe"
| where SourceImage !has "Windows Defender"
| where SourceImage !has "MsMpEng"
| project TimeGenerated, Computer, SourceImage, TargetImage, 
    GrantedAccess, SourceUser, CallTrace
| sort by TimeGenerated desc

Access Mask Reference

GrantedAccessPermissionsSuspicion Level
0x1010PROCESS_QUERY_LIMITED_INFORMATION + PROCESS_VM_READMedium
0x1410Above + PROCESS_QUERY_INFORMATIONHigh
0x1fffffPROCESS_ALL_ACCESSCritical

Analysis Steps

  1. Identify source process: What process accessed LSASS?
  2. Check legitimacy: Is this a known security tool or system process?
  3. Examine CallTrace: Look for ntdll.dll!NtReadVirtualMemory, dbgcore.dll, or unknown DLLs
  4. Check user context: Who ran the accessing process?
  5. Look for prior activity: How did attacker get to this point?

Suspicious Indicators

  • Source process is procdump.exe, rundll32.exe, or unknown executable
  • Source process running from Temp, AppData, or Downloads
  • GrantedAccess is 0x1fffff (full access)
  • CallTrace contains dbgcore.dll or comsvcs.dll
  • Source user is not SYSTEM or a known security tool service account

Hunt: C2 Beaconing

Hypothesis

Malware is communicating with command and control infrastructure at regular intervals (beaconing behavior).

ATT&CK Mapping

TechniqueT1071 - Application Layer Protocol
TacticCommand and Control

Data Requirements

  • Firewall/proxy logs with connection timestamps
  • Sysmon Event ID 3 (Network Connection) or
  • NetFlow/Zeek conn.log

Hunt Queries

// KQL - Beaconing Detection with Statistics
DeviceNetworkEvents
| where TimeGenerated > ago(24h)
| where RemoteIPType == "Public"
| summarize 
    ConnectionCount = count(),
    TimestampList = make_list(TimeGenerated),
    BytesSentTotal = sum(SentBytes)
    by DeviceName, RemoteIP, RemotePort
| where ConnectionCount > 20
| extend SortedTimestamps = array_sort_asc(TimestampList)
| mv-expand with_itemindex=i Timestamp = SortedTimestamps to typeof(datetime)
| extend NextTimestamp = SortedTimestamps[i+1]
| extend IntervalSeconds = datetime_diff('second', todatetime(NextTimestamp), Timestamp)
| where isnotnull(IntervalSeconds)
| summarize 
    AvgInterval = avg(IntervalSeconds),
    StdDevInterval = stdev(IntervalSeconds),
    MinInterval = min(IntervalSeconds),
    MaxInterval = max(IntervalSeconds),
    ConnectionCount = count()
    by DeviceName, RemoteIP, RemotePort
| extend Jitter = StdDevInterval / AvgInterval
| where Jitter < 0.15  // Low jitter = consistent intervals = suspicious
| where AvgInterval between (10 .. 3600)  // 10 sec to 1 hour intervals
| sort by Jitter asc

Analysis Steps

  1. Calculate interval consistency: Look for low standard deviation (jitter)
  2. Check destination: Is this a known service or suspicious IP?
  3. Examine process: What process is making these connections?
  4. Check threat intel: Is destination IP/domain known bad?
  5. Validate with baseline: Is this normal for this host/user?
