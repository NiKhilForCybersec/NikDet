Account Compromise Investigation

Complete investigation workflow when an account is suspected or confirmed compromised.

Why This Investigation Matters

What Attackers Do With Compromised Accounts
ActionTimeframeBusiness Impact
Read emails, gather intelligenceMinutes to hoursConfidential information exposed
Set up persistence (inbox rules, OAuth apps)Within first hourMaintained access even after password reset
Send internal phishingHoursMore accounts compromised
Send BEC emails (wire fraud)Hours to daysFinancial loss ($125K average BEC)
Access connected systems (SSO)ImmediatelyLateral movement to other apps
Exfiltrate dataHours to daysData breach, regulatory penalties
Sell access to other criminalsDays to weeksRansomware, persistent threat

Key Insight: Attackers work fast. Every hour of delay increases damage exponentially.

Why Speed Matters

Response TimeLikely Attacker ProgressContainment Difficulty
< 1 hourInitial access, reconnaissanceEasy - reset credentials, minimal cleanup
1-4 hoursPersistence established, some data accessModerate - need to find and remove persistence
4-24 hoursInternal phishing sent, data exfiltratedDifficult - multiple users may be compromised
> 24 hoursFull access, BEC attempted, access soldVery difficult - assume worst case

Investigation Decision Framework

Initial Decision: Suspend or Investigate?

To Suspend or Not to Suspend

Critical/executive userStandard user with ambiguous alert

When in doubt: Suspend first, investigate second. A brief disruption is better than a breach.

How to Investigate

Step 1: Gather Sign-In Evidence

// KQL - Complete sign-in history for user
SigninLogs
| where TimeGenerated > ago(30d)
| where UserPrincipalName == "user@company.com"
| project TimeGenerated, IPAddress, Location, AppDisplayName, 
    ClientAppUsed, DeviceDetail, ResultType, RiskLevelDuringSignIn,
    MfaDetail, ConditionalAccessStatus
| order by TimeGenerated desc

// KQL - Identify anomalous sign-ins (baseline comparison)
let user = "user@company.com";
let baseline = SigninLogs
    | where TimeGenerated between(ago(60d) .. ago(7d))
    | where UserPrincipalName == user
    | summarize NormalLocations = make_set(Location), NormalIPs = make_set(IPAddress);
SigninLogs
| where TimeGenerated > ago(7d)
| where UserPrincipalName == user
| extend IsNewLocation = Location !in (toscalar(baseline | project NormalLocations))
| extend IsNewIP = IPAddress !in (toscalar(baseline | project NormalIPs))
| where IsNewLocation or IsNewIP
| project TimeGenerated, IPAddress, Location, IsNewLocation, IsNewIP, AppDisplayName

// KQL - Failed sign-ins followed by success (password spray/brute force)
SigninLogs
| where TimeGenerated > ago(7d)
| where UserPrincipalName == "user@company.com"
| summarize 
    FailedAttempts = countif(ResultType != 0),
    SuccessfulAttempts = countif(ResultType == 0),
    FirstFailed = minif(TimeGenerated, ResultType != 0),
    FirstSuccess = minif(TimeGenerated, ResultType == 0)
    by bin(TimeGenerated, 1h)
| where FailedAttempts > 5 and SuccessfulAttempts > 0

Step 2: Check for Persistence Mechanisms

// KQL - Inbox rules created (persistence)
CloudAppEvents
| where Timestamp > ago(30d)
| where AccountObjectId == "user-object-id"
| where ActionType in ("New-InboxRule", "Set-InboxRule", "UpdateInboxRules")
| project Timestamp, ActionType, RawEventData

// KQL - OAuth apps consented by user
AuditLogs
| where TimeGenerated > ago(30d)
| where OperationName == "Consent to application"
| where InitiatedBy.user.userPrincipalName == "user@company.com"
| project TimeGenerated, 
    AppName = TargetResources[0].displayName,
    Permissions = TargetResources[0].modifiedProperties

// KQL - Email forwarding changes
CloudAppEvents
| where Timestamp > ago(30d)
| where AccountObjectId == "user-object-id"
| where ActionType in ("Set-Mailbox", "Set-MailboxJunkEmailConfiguration")
| where RawEventData has "Forward"
| project Timestamp, ActionType, RawEventData

// KQL - MFA registration changes
AuditLogs
| where TimeGenerated > ago(30d)
| where TargetResources[0].userPrincipalName == "user@company.com"
| where OperationName has_any ("User registered security info", "User deleted security info", "Admin registered security info")
| project TimeGenerated, OperationName, InitiatedBy

What If Scenarios

What If...Then...Rationale
User has MFA and attacker still got in?Check for: AiTM phishing (session token theft), OAuth app consent, MFA fatigue, SIM swapMFA isn't foolproof - attackers have methods to bypass
I reset the password but attacks continue?Look for persistence: OAuth apps, refresh tokens, inbox rules. Revoke ALL sessions, not just password.Password reset alone doesn't revoke active sessions or OAuth
User is traveling and sign-in is legitimate?Document as false positive, but still verify no other indicators. Ask about new devices.Legitimate travel is common, but verify it's really them
Attacker set up email forwarding to external?Remove forwarding, but assume ALL emails have been exfiltrated. Check for sensitive content, notify if PII.Forwarding copies emails in real-time - damage is done
User's account sent phishing to 100 internal users?This is now a major incident. Purge emails, identify who clicked, assume multiple compromises.Internal phishing has high success rate due to trust
Attacker accessed HR/Finance systems via SSO?Scope expands significantly. Check audit logs in those systems. Notify data owners.SSO means one compromise = access to many systems

Containment Actions

Immediate Containment Checklist

ActionCommand/StepsWhy
1. Revoke all sessions Entra ID > User > Revoke sessions
Revoke-AzureADUserAllRefreshToken		 Kicks attacker out immediately
2. Reset password Entra ID > User > Reset password
Generate random password		 Prevents re-authentication
3. Disable account (if severe) Entra ID > User > Block sign-in Complete lockout while investigating
4. Remove inbox rules Get-InboxRule -Mailbox user | Remove-InboxRule Removes persistence mechanism
5. Remove email forwarding Set-Mailbox user -ForwardingAddress $null Stops data exfiltration
6. Revoke OAuth apps Entra ID > User > Applications > Revoke suspicious apps Removes attacker's persistent access
7. Re-register MFA Delete existing methods, have user re-enroll Attacker may have registered their device

Escalation Criteria

Escalate Immediately When:
  • Executive or privileged account compromised
  • BEC emails sent (financial fraud attempted)
  • Internal phishing campaign launched
  • Multiple accounts compromised from same attack
  • Evidence of data exfiltration
  • Attacker accessed sensitive systems (HR, Finance, Source code)
  • Unable to remove attacker access
