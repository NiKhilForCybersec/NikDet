Real Detection Development Process

Here's how detection engineering actually works in organizations:

Step 1: Identify Detection Need 1-4 hours

Triggers in real organizations:

  • Threat intel report mentions technique you can't detect
  • Purple team exercise finds gap
  • Incident post-mortem: "Why didn't we detect this?"
  • MITRE ATT&CK coverage review shows gaps
  • Analyst says "I wish we had an alert for X"

Real Example: Detection Need Identified

Purple team ran Mimikatz during exercise. SOC didn't detect it until 2 hours later when analyst noticed unusual process. Post-mortem action item: "Create detection for LSASS access."

Step 2: Research the Technique 2-8 hours

What you need to understand:

  • How does the attack work technically?
  • What artifacts does it leave?
  • What logs capture this activity?
  • What's the legitimate use (false positive potential)?
Research for LSASS Access Detection:

ATTACK MECHANICS:
- Mimikatz uses OpenProcess() to access lsass.exe
- Requires SeDebugPrivilege
- Reads memory to extract credentials

ARTIFACTS:
- Windows Security Event 4663 (Object Access) - if auditing enabled
- Sysmon Event 10 (Process Access) - best visibility
- EDR telemetry (DeviceProcessEvents in MDE)

LEGITIMATE ACCESS:
- Windows Defender
- Antivirus products
- System processes (csrss.exe, services.exe)
- WerFault.exe (crash dumps)

LOG SOURCES AVAILABLE:
✓ MDE DeviceProcessEvents - have this
✓ Sysmon - deployed on 70% of endpoints
✗ Windows 4663 - not configured (would need GPO change)

Step 3: Write Initial Query 1-4 hours

Start broad, then narrow:

// Version 1: Too broad - will have tons of FPs
DeviceProcessEvents
| where FileName == "lsass.exe"

// Version 2: Better - focus on access events
DeviceEvents
| where ActionType == "ProcessAccess"
| where FileName == "lsass.exe"

// Version 3: Filter out known legitimate
DeviceEvents
| where ActionType == "ProcessAccess"
| where FileName == "lsass.exe"
| where InitiatingProcessFileName !in ("MsMpEng.exe", "csrss.exe", "services.exe", "svchost.exe", "WerFault.exe")
| where InitiatingProcessFolderPath !startswith "C:\\Program Files\\Windows Defender"

Step 4: Test Against Historical Data 2-4 hours

Critical step most people skip:

// Run query against 30 days of data
DeviceEvents
| where TimeGenerated > ago(30d)
| where ActionType == "ProcessAccess"
| where FileName == "lsass.exe"
| where InitiatingProcessFileName !in ("MsMpEng.exe", "csrss.exe", "services.exe", "svchost.exe", "WerFault.exe")
| summarize Count=count(), Hosts=dcount(DeviceName) by InitiatingProcessFileName, InitiatingProcessFolderPath
| order by Count desc

// Results show what would have fired:
// vmtoolsd.exe - 4,521 events (VMware tools - FP, add to exclusion)
// cbdefense.exe - 2,103 events (Carbon Black - FP, add to exclusion)  
// taskhostw.exe - 847 events (legitimate Windows - FP, add to exclusion)
// procdump.exe - 3 events (SUSPICIOUS - investigate these!)
// mimikatz.exe - 1 event (TRUE POSITIVE - from purple team)

Step 5: Validate with Red Team 1-2 hours

Does it actually catch the attack?

  • Run the actual attack in test environment
  • Verify alert fires
  • Check for evasions (does renaming the tool bypass detection?)

Validation Results

✓ Detected: mimikatz.exe

✓ Detected: procdump.exe -ma lsass.exe

✗ Missed: mimikatz renamed to notepad.exe (need to add behavior-based detection)

✗ Missed: comsvcs.dll MiniDump method (different technique, need separate rule)

Step 6: Deploy to Production 30 min - 2 hours

Deployment options:

Silent mode firstRule runs but doesn't alert - just logs matches
Low severity initiallyDeploy as Informational, upgrade after tuning
Limited scopeEnable for subset of hosts first

Common Detection Failures

❌ Failure 1: Deploy Without Testing

What happens: Engineer writes rule, deploys to production same day. Rule fires 500 times overnight. SOC is flooded, disables rule, loses trust in detection engineering.

Real example: "Detect PowerShell with encoded commands" rule deployed without exclusions. SCCM runs encoded PowerShell on every endpoint nightly = 10,000 alerts.

✓ Fix: Always Test Against 30 Days Historical

Run query against historical data. If it returns >100 results/day, you need more tuning before deployment.

❌ Failure 2: Too Specific (Easily Evaded)

What happens: Rule detects "mimikatz.exe" by filename. Attacker renames to "notepad.exe" and bypasses detection.

✓ Fix: Detect Behavior, Not Tools

Instead of filename, detect: process accessing LSASS + not in allowlist + suspicious parent process. Works regardless of tool name.

❌ Failure 3: No Documentation

What happens: Rule fires, analyst doesn't know what it means or how to investigate. Closes as FP without proper triage.

✓ Fix: Every Rule Needs

  • Description: What attack does this detect?
  • Investigation steps: What should analyst check?
  • False positive guidance: Known benign triggers
  • Response actions: What to do if true positive

❌ Failure 4: Set and Forget

What happens: Rule deployed, never reviewed. Environment changes, new software deployed, rule now fires 200 FPs/day. No one noticed until SOC complained.

✓ Fix: Scheduled Reviews

Monthly: Review top 10 noisiest rules. Quarterly: Full detection catalog review. After incidents: Did our detections fire? Why/why not?

Full Example: Building a Detection

Scenario: Detect Kerberoasting

Trigger: Penetration test found Kerberoasting not detected. Need to create detection.

Step 1: Research

KERBEROASTING MECHANICS:
- Attacker requests TGS tickets for service accounts
- Requests use RC4 encryption (weaker, crackable offline)
- Normal users rarely request many TGS tickets

DETECTION APPROACH:
- Event 4769: Kerberos Service Ticket Operations
- Filter: RC4 encryption (0x17)
- Filter: High volume requests from single user
- Filter: Requests for multiple different SPNs

FALSE POSITIVE SOURCES:
- Service accounts legitimately requesting tickets
- Monitoring tools that scan AD
- Admin scripts that enumerate services

Step 2: Initial Query

// Sentinel KQL
SecurityEvent
| where EventID == 4769
| where TicketEncryptionType == "0x17"  // RC4
| where ServiceName !endswith "$"  // Exclude machine accounts
| summarize 
    TicketCount = count(),
    UniqueServices = dcount(ServiceName),
    Services = make_set(ServiceName, 10)
    by Account, IpAddress, bin(TimeGenerated, 1h)
| where TicketCount > 10 and UniqueServices > 5

Step 3: Test Against Historical Data

// 30-day test results:
// 
// Account                    | TicketCount | UniqueServices | Assessment
// ---------------------------|-------------|----------------|------------
// svc_monitoring             | 847         | 156            | FP - monitoring tool
// admin_john                 | 23          | 8              | INVESTIGATE
// YOURCOMPANY\scanner        | 412         | 89             | FP - vuln scanner
// 
// Tuning needed: Exclude svc_monitoring, YOURCOMPANY\scanner

Step 4: Final Detection Rule

// Production Kerberoasting Detection
let excludedAccounts = dynamic(["svc_monitoring", "YOURCOMPANY\\scanner", "svc_backup"]);
SecurityEvent
| where TimeGenerated > ago(1h)
| where EventID == 4769
| where TicketEncryptionType == "0x17"
| where ServiceName !endswith "$"
| where Account !in (excludedAccounts)
| summarize 
    TicketCount = count(),
    UniqueServices = dcount(ServiceName),
    Services = make_set(ServiceName, 10),
    TargetIPs = make_set(IpAddress)
    by Account, bin(TimeGenerated, 1h)
| where TicketCount > 10 and UniqueServices > 5
| extend AlertSeverity = case(
    UniqueServices > 20, "High",
    UniqueServices > 10, "Medium",
    "Low"
)

Step 5: Documentation

DETECTION: Kerberoasting Activity
MITRE ATT&CK: T1558.003
SEVERITY: Medium (escalate to High if >20 services targeted)

DESCRIPTION:
Detects potential Kerberoasting attack where user requests multiple 
Kerberos service tickets with RC4 encryption in short time period.

INVESTIGATION STEPS:
1. Identify the source account - is this a normal user or service account?
2. Check if the account was recently compromised (password reset, unusual login)
3. Review the targeted services - are they high-privilege service accounts?
4. Check for other suspicious activity from same source IP
5. If confirmed, assume targeted service account credentials may be compromised

FALSE POSITIVES:
- Vulnerability scanners (excluded by account name)
- Monitoring tools (excluded by account name)
- Admin scripts performing AD enumeration

RESPONSE:
- If confirmed: Reset passwords for all targeted service accounts
- Enable AES-only authentication for service accounts
- Review service account permissions

Tuning in Production

Tuning Request Process

Real Tuning Request

From: SOC Analyst
Subject: Tuning Request - Suspicious PowerShell Alert

Alert Name: Suspicious PowerShell Encoded Command
False Positive Rate: ~80% (40 alerts/day, 32 are FP)

Pattern Identified:
- All FPs come from SCCM server (SCCM-PROD-01)
- Command is software deployment script
- Runs daily at 2 AM

Requested Change:
Exclude processes where:
- ParentProcess = "CcmExec.exe" (SCCM agent)
- SourceHost = "SCCM-PROD-01"

Verification:
- Confirmed with SCCM admin this is legitimate
- Will not impact detection of attacker-initiated encoded PS

Tuning Decision Framework

ScenarioActionRisk
Known legitimate software causing FPs Add to exclusion list Low - verify software is legitimate
Specific host causing all FPs Exclude host OR investigate why Medium - could be compromised host
Rule too sensitive overall Adjust thresholds Medium - might miss attacks
Can't tune without breaking detection Accept noise OR disable rule High - document decision

After Every Incident

POST-INCIDENT DETECTION REVIEW

Incident: INC-2025-0104 - Phishing leading to credential theft
Date: January 4, 2025

DETECTION ANALYSIS:
1. What alerted us to this incident?
   → User reported suspicious email (not detected by us)

2. Should we have detected this earlier?
   → Yes - attacker accessed OWA from unusual location 2 days before report

3. What detections SHOULD have fired?
   → "Impossible Travel" - was disabled due to high FP rate
   → "New Inbox Rule" - did fire, but was closed as FP incorrectly

4. What new detections do we need?
   → Detection for email forwarding to external domains
   → Better impossible travel with VPN exclusions

ACTION ITEMS:
[ ] Re-enable Impossible Travel with additional tuning
[ ] Create detection for external email forwarding rules
[ ] Review why "New Inbox Rule" alert was closed as FP
