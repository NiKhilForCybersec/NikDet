SASE - Complete Understanding

Q1: What is SASE and what problem does it solve? Basic

The Core Concept

SASE (Secure Access Service Edge, pronounced "sassy") is a cloud-delivered architecture that combines networking and security into one unified service. Instead of having separate boxes for VPN, firewall, proxy, etc., everything is delivered from the cloud.

BEFORE SASE: Multiple Point Solutions ═══════════════════════════════════════════════════════════════════ Data Center Branch Office ┌─────────────────────────┐ ┌─────────────────┐ │ VPN ─────────────────┐ │ │ │ │ Firewall ────────────┤ │◄── MPLS ────►│ Users │ │ Proxy ───────────────┤ │ │ │ │ DLP ─────────────────┤ │ └─────────────────┘ │ CASB ────────────────┘ │ │ │ Remote User │ 5 different products │ ┌─────────────────┐ │ 5 different consoles │◄── VPN ─────►│ Laptop │ │ 5 different policies │ │ (slow!) │ └─────────────────────────┘ └─────────────────┘ Problem: All traffic must go through data center = SLOW Multiple products = COMPLEX VPN can't scale = BOTTLENECK AFTER SASE: Unified Cloud Service ═══════════════════════════════════════════════════════════════════ ┌─────────────────────────────────┐ │ SASE CLOUD │ │ ┌─────────────────────────┐ │ │ │ SD-WAN │ SWG │ CASB │ │ │ │ │ ZTNA │ FWaaS │ DLP │ │ │ │ │ │ │ │ ONE platform │ │ │ │ ONE console │ │ │ │ ONE policy engine │ │ │ └─────────────────────────┘ │ │ │ │ 150+ Global Data Centers │ └───────────────┬─────────────────┘ │ ┌─────────────────────────┼─────────────────────────┐ │ │ │ ▼ ▼ ▼ Branch Office Remote User Cloud Apps (direct to cloud) (direct to cloud) (O365, etc.) Benefit: Users connect to NEAREST cloud = FAST One platform = SIMPLE Cloud scales infinitely = NO BOTTLENECK
🎯 Why This Matters in the Real World

Before COVID: 80% of workers in office, VPN handled the 20% remote. Fine.

After COVID: 70% remote workers. VPN concentrators overwhelmed. IT had to buy more hardware, but couldn't get it (supply chain). Users suffered slow connections. Security gaps emerged from split tunneling.

SASE solves this: Cloud-native, scales instantly, protects users everywhere.

🏠 Real-World Analogy

Old Way (VPN/Data Center): Imagine everyone in a city has to drive to ONE central post office to mail letters, even if they're mailing to their neighbor. Traffic jams, long waits.

SASE Way: There's a post office on every corner. You go to the nearest one. Letters still get scanned for contraband (security), but no traffic jam.

❌ Common Misconception

Wrong: "SASE is just cloud VPN"

Right: SASE includes networking (SD-WAN) + security (SWG, CASB, ZTNA, FWaaS). VPN is just one tiny piece that ZTNA actually replaces.

🔄 Follow-up Questions Interviewers Might Ask
  • "What are the 5 components of SASE?" → SD-WAN, SWG, CASB, ZTNA, FWaaS
  • "When would SASE NOT be a good fit?" → Air-gapped environments, primarily on-prem apps, very small orgs
  • "How does SASE improve user experience?" → Users connect to nearest PoP instead of backhauling through DC

ZTNA & Zero Trust - Complete Understanding

Q3: Explain Zero Trust. What does "never trust, always verify" actually mean? Basic

The Core Philosophy

Zero Trust is a security model that eliminates implicit trust. In traditional security, once you're "inside the network" (via VPN or office), you're trusted. Zero Trust says: location doesn't equal trust.

TRADITIONAL "CASTLE AND MOAT" MODEL ═══════════════════════════════════════════════════════════════════ THE MOAT (Firewall) ┌──────────────────────────────────────┐ │ │ INTERNET │ THE CASTLE │ (Untrusted) │ (Trusted Network) │ │ │ │ │ │ Once inside, you're TRUSTED │ │ │ │ │ │ ┌─────┐ ┌─────┐ ┌─────┐ │ ▼ │ │ HR │ │ SAP │ │Email│ │ ┌─────────┐ │ │ App │ │ │ │ │ │ │Attacker │──X───│ └─────┘ └─────┘ └─────┘ │ └─────────┘ │ │ │ Attacker gets VPN creds... │ ┌─────────┐ │ ...now has access to EVERYTHING │ │ User │──────│ │ │ (VPN) │ │ │ └─────────┘ └──────────────────────────────────────┘ PROBLEM: One breach = entire kingdom falls ZERO TRUST MODEL ═══════════════════════════════════════════════════════════════════ NO perimeter. Every access request is verified. ┌─────────────────────────────────────────────────────────────┐ │ │ │ Every request asks: │ │ ┌──────────────────────────────────────────────────────┐ │ │ │ WHO are you? → Identity (MFA, certificate) │ │ │ │ WHAT device? → Device posture (encrypted? AV?) │ │ │ │ WHERE from? → Location (geo, network) │ │ │ │ WHEN? → Time (business hours?) │ │ │ │ WHY this app? → Need-to-know (role, group) │ │ │ │ HOW sensitive? → Risk level of the resource │ │ │ └──────────────────────────────────────────────────────┘ │ │ │ │ Only if ALL checks pass → Grant MINIMUM necessary access │ │ │ │ User from HR User from Finance │ │ │ │ │ │ ▼ ▼ │ │ ┌─────────┐ ┌─────────┐ │ │ │ HR App │ │ SAP │ │ │ │ ONLY │ │ ONLY │ │ │ └─────────┘ └─────────┘ │ │ │ │ Even if attacker compromises HR user's account, │ │ they can ONLY access HR App - not SAP, not Email │ │ │ └─────────────────────────────────────────────────────────────┘
🏠 Real-World Analogy

Traditional (Castle & Moat): An office building where once you badge into the front door, you can go anywhere - CEO's office, server room, HR files.

Zero Trust: A building where EVERY door requires badge + PIN. Server room requires badge + PIN + biometric. CEO's office requires badge + approval. Even employees who've been there for years badge in at EVERY door.

The Three Zero Trust Principles

Verify Explicitly

Authenticate and authorize based on ALL available data points: identity, device health, location, service requesting, data classification, anomalies.

Use Least Privilege Access

Give users MINIMUM access needed. Just-In-Time access (temporary). Just-Enough-Access (only what's needed for the task).

Assume Breach

Design as if attackers are already inside. Segment everything. Encrypt everything. Monitor everything.

❌ Common Misconception

Wrong: "Zero Trust means don't trust your employees"

Right: It means don't trust NETWORK LOCATION. An employee in the office and an employee at home should have the same verification. Trust the IDENTITY, not the network.

Q4: How does ZPA work? Explain the "inside-out" architecture. Intermediate

Understanding Inside-Out vs Outside-In

This is the most important concept to understand about ZPA. It's fundamentally different from VPN.

TRADITIONAL VPN: "OUTSIDE-IN" CONNECTION ═══════════════════════════════════════════════════════════════════ The Problem: VPN concentrator must be EXPOSED to the internet INTERNET DATA CENTER │ ┌──────────────────────────┐ │ │ │ ▼ │ ┌────────────────────┐ │ Attacker │ │ VPN Concentrator │ │ can SCAN ──────────────────────► │ │ Public IP: │ │ and FIND │ │ 203.0.113.50 │ │ │ │ │ Port 443 OPEN │ │ │ │ └─────────┬──────────┘ │ │ │ │ │ ┌──────┐ │ ▼ │ │ User │───── VPN Tunnel ───────►│ ┌────────────────────┐ │ └──────┘ (INBOUND) │ │ Internal Network │ │ │ │ 10.0.0.0/8 │ │ │ │ │ │ │ │ User can reach │ │ │ │ EVERYTHING │ │ │ └────────────────────┘ │ └──────────────────────────┘ RISKS: 1. VPN server is VISIBLE to internet (can be scanned, attacked) 2. Once connected, user has NETWORK access (can move laterally) 3. Firewall must have INBOUND rules (attack surface) ZPA: "INSIDE-OUT" CONNECTION ═══════════════════════════════════════════════════════════════════ The Magic: NOTHING is exposed to the internet INTERNET ZSCALER CLOUD DATA CENTER │ ┌─────────────┐ ┌──────────────────┐ │ │ │ │ │ ▼ │ BROKER │ │ App Connector │ Attacker │ │ │ (lightweight VM)│ scans... │ Nothing │ │ │ finds NOTHING │ to scan! │ │ Makes OUTBOUND │ │ │ │ │ connection │ │ │ │◄─────────│ to Zscaler │ X │ │ OUTBOUND │ (port 443 OUT) │ Can't attack │ │ │ │ what they │ │ │ NO inbound │ can't see! │ │ │ ports needed! │ │ │ │ │ ┌──────┐ │ │ └──────────────────┘ │ User │──────────────► │ │ │ OUTBOUND │ Brokers │ ┌──────────────────┐ │ │ to Zscaler │ the │ │ Internal App │ └──────┘ │ connection│◄─────────│ (never exposed) │ │ │ └──────────────────┘ └─────────────┘ HOW IT WORKS: 1. App Connector makes OUTBOUND connection to Zscaler (lives in cloud) 2. User makes OUTBOUND connection to Zscaler 3. Zscaler BROKERS the connection between user and app 4. App NEVER has public IP, NEVER exposed to internet SECURITY: 1. No VPN server to attack (nothing visible) 2. No inbound firewall rules (zero attack surface) 3. User only gets access to SPECIFIC APPS (not network)
The App Connector is the key innovation. It sits near your apps and makes an OUTBOUND connection to Zscaler. Your firewall only needs to allow OUTBOUND 443. No inbound rules = nothing for attackers to find.
🏠 Real-World Analogy

VPN (Outside-In): You put your home address on a public bulletin board and say "knock on my door if you want to visit." Anyone can find your house. Burglars included.

ZPA (Inside-Out): Your address is SECRET. When you want visitors, you both go to a trusted meeting point (Zscaler). The meeting point introduces you, then you communicate through them. Your home address is never revealed.

🔄 Follow-up Questions Interviewers Might Ask
  • "What port does the App Connector use?" → Outbound 443 only
  • "What if Zscaler is down?" → Apps become inaccessible (discuss HA/redundancy)
  • "Can attackers intercept the Zscaler connection?" → All traffic is encrypted end-to-end

What Sarah CANNOT Do (Contrast with VPN)

Action With VPN With ZPA
Access HR portal ✓ Yes ✓ Yes (if policy allows)
Ping servers on 10.x network ✓ Yes (full network access) ✗ No (no network access)
Access Finance SAP system ✓ Yes (can reach anything) ✗ No (not in her policy)

🎯 Why This Matters

If Sarah's laptop gets compromised by malware, with VPN the attacker has her full network access - they can move laterally, find servers, exfiltrate data from anywhere.

With ZPA, the attacker can ONLY reach the HR app. No lateral movement possible. The blast radius is contained.

SSL Inspection - Complete Understanding

Q6: How does SSL inspection work? Why is it necessary? Intermediate

The Problem SSL Inspection Solves

Over 90% of web traffic is now encrypted (HTTPS). This is great for privacy, but it creates a security blind spot - malware can hide in encrypted traffic.

THE PROBLEM: ENCRYPTED MALWARE ═══════════════════════════════════════════════════════════════════ WITHOUT SSL Inspection: User Malicious Site │ │ │ 1. User visits https://evil-site.com │ │─────────────────────────────────────────────────► │ │ │ 2. Site sends malware.exe (encrypted) │ │◄───────────────────────────────────────────────── │ │ │ ╔═════════════════════════════════════════╗ │ │ ║ HTTPS ENCRYPTED TUNNEL ║ │ │ ║ 🔒🔒🔒🔒🔒🔒🔒🔒🔒🔒🔒🔒🔒🔒🔒🔒🔒🔒🔒 ║ │ │ ║ ║ │ │ ║ Firewall/SWG sees: ¯\_(ツ)_/¯ ║ │ │ ║ "Looks like random encrypted data" ║ │ │ ║ "I can't scan what I can't see" ║ │ │ ║ ║ │ │ ╚═════════════════════════════════════════╝ │ │ │ ▼ │ User infected! │ Malware was invisible to security tools │

How SSL Inspection Works

User requests │ │ │ https://website.com │ │ │────────────────────────────► │ │ │ │ │ │ 2. Proxy connects to │ │ │ website on behalf │ │ │ of user │ │ │─────────────────────────────► │ │ │ │ │ 3. Why User's Browser Accepts the Proxy Certificate

For SSL inspection to work, the user's device must TRUST the proxy's CA certificate. This is deployed via:
  • GPO (Windows) - pushed to Trusted Root store
  • MDM (mobile/Mac) - profile with certificate
  • Zscaler Client Connector - installs CA automatically
Without this trust, users would see certificate errors on every HTTPS site.
❌ Common Misconception

Wrong: "SSL inspection breaks encryption and is insecure"

Right: Traffic is STILL encrypted on both sides. It's decrypted ONLY inside the proxy (in memory) for inspection, then immediately re-encrypted. The proxy doesn't store the decrypted content.

When NOT to SSL Inspect

CategoryWhy Bypass?Examples
Certificate Pinning App only trusts specific cert, will fail with proxy cert Banking apps, Zoom, Apple services
Privacy/Compliance Legal/ethical concerns about decrypting Healthcare portals, banking sites
Performance Decrypt/re-encrypt adds latency Video conferencing, large downloads

🎯 Why This Matters in Interviews

Interviewers ask troubleshooting questions to see HOW you think, not just WHAT you know. Show a systematic approach:

  1. Start at the user (client-side issues first)

  3. Then check configuration (policy, segments)
  4. Finally check infrastructure (connectors, network)

DLP - Complete Understanding

Q10: How does DLP work in a cloud SWG like Zscaler? Intermediate

Understanding Cloud DLP

DLP (Data Loss Prevention) inspects data in motion to prevent sensitive information from leaving the organization. In cloud SWG, it examines uploads to detect credit cards, SSNs, source code, etc.

HOW CLOUD DLP WORKS ═══════════════════════════════════════════════════════════════════ User uploads file to Dropbox │ ▼ ┌─────────────────────────────────────────────────────────────────┐ │ ZSCALER CLOUD DLP ENGINE │ │ │ │ STEP 1: CONTENT EXTRACTION │ │ ┌─────────────────────────────────────────────────────────┐ │ │ │ File: quarterly_report.xlsx │ │ │ │ │ │ │ │ Extract text from: │ │ │ │ - Excel cells │ │ │ │ - Embedded objects │ │ │ │ - Metadata │ │ │ └─────────────────────────────────────────────────────────┘ │ │ │ │ │ ▼ │ │ STEP 2: PATTERN MATCHING │ │ ┌─────────────────────────────────────────────────────────┐ │ │ │ Check against DLP dictionaries: │ │ │ │ │ │ │ │ ┌──────────────────┐ ┌──────────────────┐ │ │ │ │ │ Credit Card │ │ SSN │ │ │ │ │ │ Pattern: \d{16} │ │ Pattern: \d{3}- │ │ │ │ │ │ + Luhn check │ │ \d{2}-\d{4} │ │ │ │ │ │ │ │ │ │ │ │ │ │ FOUND: 47 cards! │ │ FOUND: 0 │ │ │ │ │ └──────────────────┘ └──────────────────┘ │ │ │ │ │ │ │ │ ┌──────────────────┐ ┌──────────────────┐ │ │ │ │ │ Source Code │ │ Custom: Project │ │ │ │ │ │ Keywords: class, │ │ Codenames │ │ │ │ │ │ def, import │ │ "Project Phoenix"│ │ │ │ │ │ │ │ │ │ │ │ │ │ FOUND: 0 │ │ FOUND: 2 │ │ │ │ │ └──────────────────┘ └──────────────────┘ │ │ │ └─────────────────────────────────────────────────────────┘ │ │ │ │ │ ▼ │ │ STEP 3: POLICY EVALUATION │ │ ┌─────────────────────────────────────────────────────────┐ │ │ │ Policy: "Block Credit Card Upload" │ │ │ │ Threshold: 5+ credit cards │ │ │ │ Action: BLOCK │ │ │ │ │ │ │ │ Match: 47 credit cards found > 5 threshold │ │ │ │ Decision: BLOCK UPLOAD │ │ │ └─────────────────────────────────────────────────────────┘ │ │ │ └─────────────────────────────────────────────────────────────────┘ │ ▼ User sees: "Upload blocked - contains sensitive data" Alert sent to security team Log recorded for compliance
🎯 Why Thresholds Matter

Why not block on 1 credit card? False positives. A single credit card number appears in:

  • Order confirmations ("Your card ending in 4242...")
  • Expense reports (receipts)
  • Test data (4111111111111111 is a test card)

But 47 cards? That's a customer database being exfiltrated. Block it.

🏠 Real-World Analogy

Without DLP: An office where anyone can walk out with boxes of customer files, and security just waves them through.

With DLP: A mailroom that opens every outgoing package, checks for sensitive documents, and stops anything that shouldn't leave. It knows what "sensitive" means because you defined the rules.

Types of DLP Matching

TypeHow It WorksExampleAccuracy
Regex Patterns Match text patterns SSN: \d{3}-\d{2}-\d{4} Medium (many false positives)
Dictionaries Match keyword lists "Confidential", "Internal Only" Low (too many matches)
Exact Data Match (EDM) Hash actual sensitive data Hash of customer SSNs from HR database Very High (exact match only)
Machine Learning Classify document types "This looks like a tax form" High (contextual)
The best DLP strategies combine multiple methods. Use EDM for known sensitive data (customer records), regex for structured data (credit cards), and ML for unstructured documents (contracts, legal).
Q11: How would you handle a DLP policy for source code? Advanced

The Challenge

Developers legitimately use GitHub, Stack Overflow, and code-sharing sites. You can't block all code - but you need to prevent proprietary code leakage.

SOURCE CODE DLP STRATEGY ═══════════════════════════════════════════════════════════════════ APPROACH: Allow legitimate dev work, block exfiltration ┌─────────────────────────────────────────────────────────────────┐ │ LEGITIMATE CODE SHARING │ │ │ │ ✓ github.company.com (corporate GitHub Enterprise) │ │ ✓ stackoverflow.com (questions, not bulk uploads) │ │ ✓ npm publish to private registry │ │ │ └─────────────────────────────────────────────────────────────────┘ ┌─────────────────────────────────────────────────────────────────┐ │ BLOCK THESE SCENARIOS │ │ │ │ ✗ github.com (personal repos) │ │ ✗ pastebin.com (public paste sites) │ │ ✗ chat.openai.com (AI tools with code) │ │ ✗ Personal email attachments with .py, .java, .go │ │ │ └─────────────────────────────────────────────────────────────────┘ DLP RULE CONFIGURATION: ═══════════════════════════════════════════════════════════════════ Rule 1: Block Source Code to Unsanctioned Sites ───────────────────────────────────────────────── Trigger: File types .py, .java, .js, .go, .cs, .cpp, .rb OR content contains: "def ", "class ", "import ", "function ", "private void", "public static" Destination: NOT in whitelist (whitelist: github.company.com, gitlab.company.com) Action: BLOCK Rule 2: Block Proprietary Markers Everywhere ───────────────────────────────────────────────── Trigger: Content contains: - "CONFIDENTIAL" + code patterns - "Copyright [Company Name]" - "PROPRIETARY" - API keys (regex for AWS_SECRET, etc.) Destination: ALL external sites Action: BLOCK Rule 3: Warn on Code to AI Tools ───────────────────────────────────────────────── Trigger: Any code patterns Destination: chat.openai.com, claude.ai, bard.google.com, copilot.github.com Action: WARN (allow with user acknowledgment) Message: "You are about to share code with an AI service. Ensure no proprietary code is included."
🎯 Why This Is Tricky

Block too much: Developers can't work, productivity tanks, they find workarounds (personal phones).

Block too little: Source code ends up on personal GitHub, AI tools, competitors.

Balance: Allow legitimate tools (corporate GitHub), block risky destinations (public repos), warn on gray areas (AI tools).

🔄 Follow-up Questions
  • "What about developers who need to use public GitHub?" → They push to corporate GitHub which mirrors to public (controlled process)
  • "How do you handle AI coding assistants like Copilot?" → Either block, warn, or allow with corporate agreement that sanitizes data
  • "What if developers use VPN to bypass?" → Client Connector enforces DLP regardless of network

CASB - Complete Understanding

Q12: What is CASB and why is it necessary when you already have SWG? Intermediate

SWG vs CASB - Different Problems

SWG vs CASB: WHAT EACH SOLVES ═══════════════════════════════════════════════════════════════════ SWG (Secure Web Gateway) ──────────────────────── Question: "Should this user access this website?" Example: User → facebook.com → SWG says: Block (social media policy) User → malware.com → SWG says: Block (malware category) User → dropbox.com → SWG says: Allow (cloud storage category) SWG doesn't care WHAT the user does on Dropbox. It only decides: allowed or blocked. CASB (Cloud Access Security Broker) ──────────────────────────────────── Question: "What is the user DOING in this cloud app?" Example: User → dropbox.com → SWG: Allow │ ▼ CASB watches: ┌─────────────────────────────────────────────────────┐ │ │ │ Action: Download file │ │ CASB: ✓ Allow │ │ │ │ Action: Upload file │ │ CASB: Check DLP → Block if sensitive │ │ │ │ Action: Share file externally │ │ CASB: ✗ Block (no external sharing policy) │ │ │ │ Action: Create public link │ │ CASB: ✗ Block (no public links policy) │ │ │ └─────────────────────────────────────────────────────┘ THE GAP CASB FILLS ═══════════════════════════════════════════════════════════════════ Without CASB (SWG only): - User can access Dropbox ✓ - User uploads customer database to Dropbox ✓ (SWG doesn't see this) - User shares link publicly ✓ (SWG doesn't see this) - Data breach happens ✗ With CASB: - User can access Dropbox ✓ - User uploads customer database → CASB blocks (DLP policy) - User tries to share externally → CASB blocks (sharing policy) - Data protected ✓

CASB Modes of Operation

ModeHow It WorksProsCons
Inline (Proxy) Traffic flows through CASB Real-time blocking, all traffic visible Adds latency, requires traffic steering
API Connects to SaaS APIs (O365, Box) Deep visibility, can scan existing data Not real-time, limited to API capabilities
Log-based Analyzes SaaS audit logs Easy to deploy, no traffic changes Detection only, can't block
🏠 Real-World Analogy

SWG: A security guard at the office entrance who decides who can enter the building.

CASB: Security cameras and sensors INSIDE the building that watch what people do - are they accessing the file room? Are they photocopying documents? Are they taking photos of whiteboards?

In SASE architecture, CASB and SWG work together. SWG handles the "allow/block website" decision. CASB handles the "what can they DO in allowed cloud apps" decision. Zscaler combines both in ZIA.

Device Posture - Complete Understanding

Q13: Explain device posture checking. Why is it important for Zero Trust? Intermediate

What Device Posture Checks

Device posture verifies that the DEVICE (not just the user) meets security requirements before granting access. This is a core Zero Trust principle: don't just verify WHO, verify WHAT they're using.

WHY DEVICE POSTURE MATTERS ═══════════════════════════════════════════════════════════════════ SCENARIO: John's credentials are valid, but... Without Device Posture: ───────────────────────── John logs in from: Old laptop, Windows 7, no antivirus, no encryption, downloaded from torrent site Policy check: Is John a valid user? YES ✓ Result: ACCESS GRANTED Problem: Malware on John's laptop now has access to corporate applications. Keylogger steals more creds. With Device Posture: ───────────────────────── John logs in from: Old laptop, Windows 7, no antivirus Policy check: - Is John a valid user? YES ✓ - Is device encrypted? NO ✗ - Is AV running? NO ✗ - Is OS supported? NO ✗ (Win7 is EOL) Result: ACCESS DENIED Message: "Your device doesn't meet security requirements. Please contact IT."

Common Posture Checks

DEVICE POSTURE CHECK CATEGORIES ═══════════════════════════════════════════════════════════════════ OPERATING SYSTEM ├── OS Type: Windows 10/11, macOS 12+, iOS 15+, Android 12+ ├── OS Version: Minimum version requirements ├── Patch Level: Updated within X days └── EOL Status: Not end-of-life ENCRYPTION ├── Windows: BitLocker enabled ├── macOS: FileVault enabled └── Mobile: Device encryption on SECURITY SOFTWARE ├── Antivirus: Running and definitions < 24 hours old ├── EDR: CrowdStrike/Defender running ├── Firewall: Enabled └── Specific product: Require specific AV vendor DEVICE MANAGEMENT ├── MDM Enrolled: Intune, Jamf, etc. ├── Domain Joined: Part of corporate AD ├── Certificate: Corporate CA cert present └── Compliance: MDM reports device compliant DEVICE STATE ├── Jailbreak/Root: Not detected ├── Screen Lock: Enabled (max 5 min timeout) ├── Debug Mode: Disabled (Android) └── USB Debugging: Disabled EXAMPLE POSTURE PROFILES ═══════════════════════════════════════════════════════════════════ High Security (Finance, HR systems): ✓ Windows 10 21H2+ or macOS 12+ ✓ BitLocker/FileVault enabled ✓ AV running, updated < 24 hours ✓ Firewall enabled ✓ Domain joined OR MDM enrolled ✓ Corporate certificate present ✓ Screen lock < 5 minutes Standard (General business apps): ✓ Supported OS version ✓ Disk encryption enabled ✓ AV running ✓ Firewall enabled Basic (Contractor access): ✓ Supported OS version ✓ Screen lock enabled ✓ Not jailbroken/rooted
🎯 Why Different Posture Levels?

Not all apps need the same protection.

  • Company intranet (news, cafeteria menu): Basic posture is fine
  • Expense reports: Standard posture
  • Customer PII database: High security posture required

Risk-based approach: Match security requirements to data sensitivity.

❌ Common Misconception

Wrong: "Device posture only matters at login"

Right: Modern ZTNA does CONTINUOUS posture checking. If your AV stops running mid-session, access can be revoked immediately.

ScenarioBest MethodWhy

Q17: How would you migrate 5,000 users from VPN to ZTNA without disruption? Advanced

🎯 Why Phased Migration Matters

Big bang migrations fail. You'll find issues you didn't anticipate:

  • Apps that use weird ports you forgot to document
  • Legacy apps that break with the proxy
  • Users who didn't get the memo
  • Edge cases (contractors, executives with exceptions)

Phased approach lets you find and fix issues with small groups before they affect everyone.
