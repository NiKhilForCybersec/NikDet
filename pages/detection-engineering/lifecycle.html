Apex Financial: Building Priority #1 Detection

🏢 Apex Financial - Month 1: BEC Prevention

After the $340,000 wire fraud incident, Apex's top priority is detecting email-based attacks. The detection engineering team starts with: Suspicious Inbox Rule Creation

This was the exact technique the attacker used - creating a rule to forward payment-related emails.

Step 1: Research the Technique 2 hours

Detection Engineer's Research Notes:

TECHNIQUE RESEARCH: Malicious Inbox Rules

MITRE ATT&CK: T1564.008 (Email Hiding Rules), T1114.003 (Email Forwarding Rule)

HOW ATTACKERS USE THIS:
1. Compromise email account (phishing, password spray)
2. Create inbox rule to:
   - Forward emails to external address (data exfil)
   - Delete emails containing certain keywords (hide tracks)
   - Move emails to hidden folder (hide from user)
3. Monitor silently for days/weeks
4. Strike when opportunity arises (BEC, wire fraud)

WHAT OUR ATTACKER DID (from incident report):
- Rule name: "." (single dot - hard to notice)
- Condition: Subject contains "payment" OR "wire" OR "transfer" OR "invoice"
- Action: Forward to "cfo.backup2024@protonmail.com"

LOG SOURCES:
✓ OfficeActivity (Operation: New-InboxRule, Set-InboxRule, UpdateInboxRules)
✓ Microsoft 365 Audit Logs
✓ Exchange Online PowerShell logs

LEGITIMATE INBOX RULES (False Positive sources):
- Users creating rules for newsletters, folders
- IT creating rules for shared mailboxes
- Automated rules from third-party apps (Slack notifications, etc.)

SUSPICIOUS INDICATORS:
- Forwarding to external domain
- Rule conditions about money/payments
- Rule name is blank, dot, or random characters
- Rule created shortly after first login from new location
- Rule created outside business hours

Step 2: Write Initial Query 1 hour

QUERY EVOLUTION - FROM NOISY TO PRODUCTION-READY ═══════════════════════════════════════════════════════════════════════════════ VERSION 1: Too Broad ───────────────────────────────────────────────────────────────────────────── Query: "Show me ALL inbox rules" ┌─────────────────────────────────────────────────────────────────────────┐ │ 847 events in 7 days │ │ ████████████████████████████████████████████████████████████████████ │ │ │ │ 99% legitimate (newsletters, folder organization, etc.) │ │ UNUSABLE - SOC would drown in alerts │ └─────────────────────────────────────────────────────────────────────────┘ VERSION 2: Better - Focus on Forwarding ───────────────────────────────────────────────────────────────────────────── Query: "Show me inbox rules that FORWARD emails" ┌─────────────────────────────────────────────────────────────────────────┐ │ 23 events in 7 days │ │ █████ │ │ │ │ Still includes internal forwarding (user → assistant) │ │ BETTER - but still too many false positives │ └─────────────────────────────────────────────────────────────────────────┘ VERSION 3: Production-Ready ───────────────────────────────────────────────────────────────────────────── Query: "Forward to EXTERNAL domain" + "Suspicious keywords" + "Red flags" ┌─────────────────────────────────────────────────────────────────────────┐ │ 3 events in 7 days │ │ █ │ │ │ │ 1 policy violation (unauthorized forwarding) │ │ 2 tuned out (legitimate vendors) │ │ USABLE - SOC can handle this volume │ └─────────────────────────────────────────────────────────────────────────┘ THE LAYERING APPROACH: ───────────────────────────────────────────────────────────────────────────── Start broad, then add filters: All inbox rules (847) │ │ + Forwarding only ▼ Forwarding rules (23) │ │ + External domains only ▼ External forwarding (8) │ │ + NOT trusted vendors ▼ Suspicious external (5) │ │ + Suspicious keywords OR red flags ▼ HIGH CONFIDENCE ALERTS (3)

Version 1: Too Broad

// This will fire for EVERY inbox rule - way too noisy
OfficeActivity
| where Operation in ("New-InboxRule", "Set-InboxRule")
| project TimeGenerated, UserId, Operation, Parameters

Result: 847 events in 7 days - mostly legitimate rules. Too noisy.

Version 2: Focus on External Forwarding

// Better - focus on forwarding rules
OfficeActivity
| where Operation in ("New-InboxRule", "Set-InboxRule", "UpdateInboxRules")
| extend RuleParameters = tostring(Parameters)
| where RuleParameters contains "ForwardTo" or RuleParameters contains "RedirectTo"
| project TimeGenerated, UserId, Operation, RuleParameters, ClientIP

Result: 23 events in 7 days - much better, but includes internal forwarding.

Version 3: External Domains Only + Suspicious Patterns

// Production-ready detection
let suspiciousKeywords = dynamic(["payment", "wire", "transfer", "invoice", "bank", "account"]);
let trustedDomains = dynamic(["apexfinancial.com", "apex-financial.com"]);
OfficeActivity
| where TimeGenerated > ago(1h)
| where Operation in ("New-InboxRule", "Set-InboxRule", "UpdateInboxRules")
| extend RuleParameters = tostring(Parameters)
| where RuleParameters contains "ForwardTo" or RuleParameters contains "RedirectTo"
// Extract the forwarding address
| extend ForwardTo = extract(@'"ForwardTo":\s*"([^"]+)"', 1, RuleParameters)
| extend ForwardDomain = tostring(split(ForwardTo, "@")[1])
// Filter to external domains
| where ForwardDomain != "" and not(ForwardDomain has_any (trustedDomains))
// Check for suspicious conditions
| extend HasSuspiciousCondition = RuleParameters has_any (suspiciousKeywords)
// Add context
| extend RuleName = extract(@'"Name":\s*"([^"]*)"', 1, RuleParameters)
| project 
    TimeGenerated,
    UserId,
    Operation,
    RuleName,
    ForwardTo,
    ForwardDomain,
    HasSuspiciousCondition,
    ClientIP,
    RuleParameters

Step 5: Document the Detection 30 min

DETECTION DOCUMENTATION
=======================

Name: Suspicious Email Forwarding Rule Created
ID: APEX-DET-001
MITRE ATT&CK: T1564.008, T1114.003
Severity: High (external + suspicious keywords) / Medium (external only)
Status: Production

DESCRIPTION:
Detects creation or modification of inbox rules that forward email to 
external domains, particularly when rule conditions reference financial 
keywords. This technique was used in the March 2024 BEC incident.

DATA SOURCES:
- OfficeActivity (Microsoft 365 Unified Audit Log)
- Operations: New-InboxRule, Set-InboxRule, UpdateInboxRules

DETECTION LOGIC:
1. Inbox rule created/modified with forwarding action
2. Forwarding destination is external domain (not in trusted list)
3. If rule conditions contain financial keywords → High severity
4. If forwarding to privacy-focused email → High severity

FALSE POSITIVE SOURCES:
- HubSpot marketing integration
- ServiceNow IT ticketing
- QuickBooks/accounting systems
- Known partner/vendor domains
- Personal email forwarding (legitimate but policy concern)

INVESTIGATION STEPS:
1. Identify the user - is this their account or compromised?
2. Check recent sign-in activity for unusual locations/IPs
3. Review the rule conditions and forwarding destination
4. Check if user is aware they created this rule
5. If suspicious, check for other indicators of compromise

RESPONSE ACTIONS:
- High severity: Disable rule immediately, investigate account
- Medium severity: Notify user, verify legitimacy within 4 hours

EXCLUSIONS:
- Forwarding to: hubspot.com, servicenow.com, quickbooks.com, [vendor list]
- Users: shared.info@ (marketing automation)

CREATED BY: Detection Engineering Team
CREATED DATE: April 15, 2024
LAST REVIEWED: [Quarterly review date]

Step 6: Deploy to Production 1 hour

Deployment steps at Apex:

  1. Create Analytics Rule in Microsoft Sentinel
  2. Set severity mapping (High for suspicious keywords, Medium otherwise)
  3. Configure alert grouping (by UserId)
  4. Create automated enrichment playbook (add user details, recent sign-ins)
  5. Set up notification to SOC Teams channel
  6. Monitor for 48 hours in "silent mode" (logs but doesn't alert)
  7. After validation, enable full alerting

Common Detection Failures

❌ Failure 1: Deploy Without Historical Testing

What happens: Engineer writes rule, deploys same day. Rule fires 500 times overnight. SOC disables it, loses trust in detection engineering.

Apex avoided this by: Running every detection against 30 days of historical data before deployment.

❌ Failure 2: Too Specific (Easily Evaded)

What happens: Rule detects "mimikatz.exe" by filename. Attacker renames to "notepad.exe" and bypasses detection.

Apex approach: Detect behaviors (forwarding to external domain) not specific indicators (protonmail.com).

❌ Failure 3: No Documentation

What happens: Rule fires, analyst doesn't know what it means. Closes as FP.

Apex approach: Every detection includes investigation steps, FP guidance, and response actions.
